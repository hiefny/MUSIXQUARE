## 1. 오너 결정

오너의 말은 옮기지 않고 뜻만 적는다.

- **2026-11-11, 재생 화면의 아래 끝:** 9.0.43의 배포 보고에서, 1024x768 iPad를 홈 화면에 설치해 가로로 쓰면 재생 화면 맨 아래 버튼 줄이 홈
  표시줄 위에서 잘려 보인다는 것을 사진과 함께 알리고, 그대로 둘지 본문을 화면 아래 끝까지 늘릴지(늘리면 버튼 아래쪽이 홈 표시줄 자리와
  겹침) 물었다. 오너는 홈 표시줄 자리와 겹쳐도 괜찮다고 답했다.
- **2026-11-11, 이름 맞추기는 다음 App 업데이트에 얹기:** 소리 복구 주인 파일의 이름 맞추기는 보이는 것이 없어 단독으로 내지 않고 다음 App
  업데이트에 얹는다([증분 보고서 §1](audio-recovery-names-2026-11-11.md#1-오너-결정)). 이 열차가 그 다음 App 업데이트다.
- **2026-11-11, 배포 허가(9.0.42 열차 때의 결정):** 배포는 모두 허가했다. 자동 관문(PR 검사, 자동 코드 리뷰, 병합, exact-main CI, 최소 앱 빌드
  확인)이 통과하면 업데이트 창이 뜨는 열차도 따로 묻지 않고 dispatch한다. 기기 확인은 게이트가 아니다.

만든 쪽이 정한 것(오너 결정 아님): 오너의 답은 재생 화면의 사진을 두고 한 것이라, 재생 화면의 본문만 늘리고 목록 탭 넷(플레이리스트, 연결,
설정, 도움말)은 9.0.43의 계약 그대로 뒀다(§3.5).

## 3. 재생 화면을 화면 아래 끝까지 (의도한 변경, [화면 바뀜])

### 3.1 사용자에게 바뀌는 것

- 사이드바 배치이면서 아래 안전 영역이 있는 화면(홈 화면에 설치한 iPad의 가로·세로, 홈 표시줄이 있는 가로 휴대폰)에서 재생 화면이 홈 표시줄
  위에서 끝나지 않고 화면 아래 끝까지 보인다.
- 1024x768 iPad 가로 PWA(위 안전 영역 24px, 아래 20px): 맨 아래 Sync·Media 버튼(세로 705.5 ~ 761.5)이 9.0.43에서는 본문의 아래 끝 748에서
  잘려 위쪽 4분의 3만 보였고 14px쯤 스크롤해야 다 보였다. 이제 스크롤하지 않아도 다 보이고, 버튼 아래쪽 13.5px이 홈 표시줄 자리(748 ~
  768)와 겹친다.
- 화면 구성의 자리는 그대로다. 영상, 제목, 재생 조작부, 채팅 줄, 버튼의 좌표가 9.0.43과 같고, 스크롤할 수 있는 거리도 그대로 74px이며, 끝까지
  스크롤하면 내용이 전처럼 홈 표시줄 위(739.5)에서 끝난다.
- 그대로인 것: 플레이리스트·연결·설정·도움말 탭(홈 표시줄 위에서 끝남), 사이드바, 미디어 고르기와 YouTube 입력 화면, 대화상자, 채팅, 전체
  화면 영상, 넓은 배치(1280x720 이상), 휴대폰 세로 배치, 그리고 아래 안전 영역이 없는 모든 화면(일반 브라우저 창과 데스크톱).

### 3.2 바뀐 코드

`css/style.css`의 사이드바 배치 블록에 규칙 하나를 더했다.

```css
#tab-play.active {
  height: calc(var(--app-height, 100dvh) - var(--safe-top));
  padding-bottom: calc(8px + var(--safe-bottom));
}
```

- 9.0.43은 사이드바 배치의 모든 본문을 위아래 안전 영역만큼 들여 놓았다(`.tab-content.active`의 `top`과 `height`). 목록 탭에서는 그것이
  계약이다: 어느 스크롤 위치에서도 홈 표시줄 자리에 글을 그리지 않는다(9.0.43의 fixture 명세가 고정). 재생 화면은 목록이 아니라 한 화면에
  맞춰 짠 구성이라, 안전 영역 안의 높이가 모자라면 마지막 버튼 줄이 홈 표시줄 위에서 잘렸다.
- 새 규칙은 재생 화면의 본문 하나만 화면 아래 끝까지 늘리고, 같은 값만큼 끝 여백을 늘린다. 그래서 내용 상자(높이에서 위아래 여백을 뺀
  것)는 전과 같고, `#tab-play .tab-body`의 `min-height: 100%`와 자동 여백이 나누는 높이도 같다. 구성이 움직이지 않는 까닭이다.
- 아래 안전 영역이 0이면 두 값이 전과 같다(`height`는 `--safe-bottom`을 빼지 않아도 같고 끝 여백은 8px).
- 브라우저 전체 화면의 대체 화면(`body.has-fake-fullscreen .tab-content.active`)은 뒤 레이어(`states`)라 이 규칙을 이긴다. fixture 명세의 전체
  화면 행이 영상이 화면을 채우는 것을 고정한다.

### 3.5 알려 둘 것과 한계

- 버튼 아래쪽이 홈 표시줄 자리와 겹친다(오너 결정). 홈 표시줄 막대는 화면 가운데에 있어 1024x768에서는 Media 버튼의 왼쪽 아래 가장자리 위에
  놓인다[추론: 흉내 낸 안전 영역에 막대를 그려 본 것이고 기기에서 보지 않음].
- 재생 화면만 늘렸다. 목록 탭 넷은 9.0.43 그대로 홈 표시줄 위에서 끝나므로, 탭을 바꾸면 본문의 아래 끝이 아래 안전 영역만큼 다르다. 바탕색이

## 12. 하지 않은 것과 확인하지 않은 것

- 실기기(iPad, iPhone, Android)에서 보지 않았다. 안전 영역은 fixture의 주입값과 Chromium의 DevTools 흉내다. 실제 `env()` 값, 실제 홈 표시줄
  막대와 버튼이 겹친 모습, 화면 아래 가장자리의 쓸어 올리기 동작과 버튼의 겹침, 회전하는 동안의 배치는 확인하지 못했다.
- WebKit에서는 fixture 명세와 저장소의 WebKit 레인만 돌았다. 실제 방의 명세는 DevTools 명령을 써서 Chromium에서만 돈다.
- 1024x768보다 낮은 iPad 화면은 재지 않았다(§3.5).
- 이름 맞추기의 전후 비교(단위 시험을 시험별로, 번들, 되돌려 비교)는 증분 보고서의 것이고 이 열차는 다시 하지 않았다. 열차는 머리에서 관문을
  다시 돌렸을 뿐이다. 멈춘 시계의 장면은 일부러 만들 수 없어 기기에서 확인하지 못한다(증분 보고서 §11).
- 섞인 버전의 방은 따로 시험하지 않았다(§7).
- 배포 뒤 브라우저 확인은 데스크톱 Chromium의 운영 시작 화면, 배포된 CSS, 업데이트 대화상자뿐이다(§11.3). 운영에서는 안전 영역이 있는 화면과
  기기를 보지 않았다(§9). 로컬 결과는 exact-main-SHA 후보를 대신하지 않았다.
