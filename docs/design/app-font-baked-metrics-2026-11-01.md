9.0.29 앱 글꼴 전환([보고서](app-font-inter-noto-2026-10-31.md))은 Pretendard의 줄 상자를 `size-adjust`와 줄 상자 덮어쓰기
셋(`ascent-override`, `descent-override`, `line-gap-override`)으로 지켰다. Safari는 `size-adjust`는 따르지만 덮어쓰기 셋은
따르지 않는다(web-features 'font metric overrides': Chrome·Edge 87, Firefox 89, Safari 없음). 그래서 아이폰에서는
`line-height: normal`인 줄이 모두 글꼴 파일 자신의 세로 값으로 그려진다. 15px 한글 줄이 18px 대신 약 20px이 되고, 재생목록이
여럿일 때 재생목록 탭 제목이 다른 탭 제목보다 높게 보인다. 이 문서는 그 줄 상자를 글꼴 파일에 구워 넣어 모든 브라우저가 같은
줄 상자를 그리게 한 변경을 기록한다(반올림 경계 옆 크기에 남는 1px 차이는 §3).

## 1. 오너 결정 (2026-11-01 오후)

오너가 아이폰에서 재생목록 탭 제목이 다른 탭 제목보다 높게 보이는 것을 봤다(9.0.29 보고서 §7과 §8 1이 예상한 덮어쓰기 무시
증상). 오너는 CSS `line-height` 고침을 건너뛰고 뿌리에서 고치기로 했다: 줄 상자 값을 글꼴 파일에 구워 넣어 모든 브라우저가 같은
줄 상자를 받게 한다(9.0.29 보고서 질문 8의 답). 릴리스 담당이 구현하며 정한 기본값은 아래와 같다.

1. **시트의 기술자 넷은 남긴다.** Chromium(87+)과 Firefox(89+)는 계속 기술자를 따르고 9.0.29와 똑같이 그린다. 파일에 구운
   값은 덮어쓰기를 무시하는 엔진(iOS·macOS Safari, 옛 엔진)을 위한 것이다.
2. **`hhea`와 OS/2 typo 값을 함께 고치고 fsSelection 7번 비트(`USE_TYPO_METRICS`)를 켠다.** `usWinAscent`·`usWinDescent`는 그대로
   두고, 다른 표는 바이트 그대로 둔다.
3. **구운 사본은 새 트리 `fonts/app/<family>/`에 입력과 같은 파일 이름으로 둔다.** JP, SC, TC 파일은 소개, 사이트맵 페이지,
   `.workshop/landing`과 함께 쓰므로 제자리에서 고칠 수 없다(고치면 그 페이지들의 CJK 줄이 1.448em에서 1.27em으로 바뀐다. 9.0.29
   보고서 §9.1 질문 4의 답과 어긋남). 입력은 그대로 남는다: `fonts/inter`(Google 바이트), `fonts/noto/noto-sans-kr`(`locl` 뺀
   사본), `fonts/noto/noto-sans-{jp,sc,tc}`(Google 바이트). 앱 시트만 `fonts/app`을 가리킨다.
4. **기술자 값은 지금 문자열 그대로다(안 K: 97.96% / 24.82%, 101.29% / 25.66%).** 구운 비율로 바꾸는 안 E와 덮어쓰기 셋을
   빼는 안 D는 오너 질문이다(§9 1, 안 D는 QA 라운드 2에서 더함). 세 안의 글꼴 파일은 같으므로 다시 굽지 않아도 된다.
5. **버전 올리기, 서비스 워커 캐시 변경, 릴리스 기록 §1 변경, GitHub, push는 없다.**

## 2. 무엇을 바꿨나

### 2.1 값

값은 한 곳(`src/i18n/font-metrics.ts`)에 새 필드 `unitsPerEm`, `ascender`, `descender`, `lineGap`으로 더했다(내림은 기준선 아래
거리, 양수). 두 브라우저 엔진 모두 덮어쓰기에 `size-adjust`를 곱한다(Chromium 153과 Playwright WebKit 26.6: 100px 글자에
`size-adjust` 50%와 `ascent-override` 100%면 줄 상자 50px, `size-adjust`가 없으면 100px). 그래서 `size-adjust`는 따르고
덮어쓰기는 무시하는 엔진에서는 파일 값 ÷ unitsPerEm이 덮어쓰기와 같으면 같은 줄 상자가 된다. 구운 값은 Pretendard 값 ÷
`size-adjust` × unitsPerEm을 반올림한 것이고, 덮어쓰기 문자열에 가장 가까운 정수이기도 하다(97.96 × 20.48 = 2006.2, 25.66 × 10
= 256.6).

| 면                                | 표                              | 지금              | 구운 뒤         |
| --------------------------------- | ------------------------------- | ----------------- | --------------- |
| Inter 7개, unitsPerEm 2048        | `hhea` 오름 / 내림 / 줄 간격    | 1984 / -494 / 0   | 2006 / -508 / 0 |
|                                   | OS/2 typo 오름 / 내림 / 줄 간격 | 1984 / -494 / 0   | 2006 / -508 / 0 |
|                                   | fsSelection                     | 0x00C0(이미 켜짐) | 그대로          |
|                                   | `usWinAscent` / `usWinDescent`  | 2269 / 660        | 그대로          |
| Noto Sans KR·JP·SC·TC 433개, 1000 | `hhea` 오름 / 내림 / 줄 간격    | 1160 / -288 / 0   | 1013 / -257 / 0 |
|                                   | OS/2 typo 오름 / 내림 / 줄 간격 | 880 / -120 / 0    | 1013 / -257 / 0 |
|                                   | fsSelection                     | 0x0040            | 0x00C0          |
|                                   | `usWinAscent` / `usWinDescent`  | 1160 / 288        | 그대로          |

- 정수 단위는 소수 둘째 자리 기술자와 똑같을 수 없다. 남는 차이는 Inter 오름 1.1e-4em, 내림 1.5e-4em, CJK 오름 0.9e-4em, 내림
  4.0e-4em이다(모두 반 단위보다 작음, `font-metrics.test.ts`가 고정). 구운 비율은 Inter 2006/2048 = 97.949%와 508/2048 =
  24.805%(기술자 97.96%, 24.82%), CJK 101.3%와 25.7%(기술자 101.29%, 25.66%)다. 그래서 구운 상자는 기술자와 같지 않고, 이
  차이가 픽셀 반올림 경계 옆 크기에서 1px이 된다(§3).
- win 값을 둔 이유: `USE_TYPO_METRICS`가 켜지면 지금의 엔진은 줄 간격을 win에서 받지 않는다(DirectWrite, FreeType, HarfBuzz,
  Fontations는 typo, CoreText는 `hhea`). 글자를 win에 맞춰 자르는 것은 GDI뿐이다. win을 구운 상자로 줄이면 기본 인스턴스에서
  Inter 59 / 8개(wght 900에서 61 / 9개, 베트남어 겹친 대문자, Ǻ 등), JP 19 / 13개(〱〲 등), KR 3 / 3개, SC 5 / 6개, TC 4 / 5개
  글리프가 위 / 아래로 넘어 잘릴 수 있다. 그대로 두면 새로 잘리는 글자가 없다.
- `MVAR`: Inter의 기록은 `stro`, `strs`, `undo`, `unds`, `xhgt`뿐이고 Noto에는 `MVAR`가 없다. 생성기는 `hasc`, `hdsc`, `hlgp`,
  `hcla`, `hcld`가 있는 면을 거절한다.
- CJK typo 값이 880 / -120에서 1013 / -257이 되는 부작용: typo를 표의문자 글자 틀로 읽는 기능(루비, 강조점, 세로 쓰기,
  `text-box-edge`)만 영향을 받는데 앱은 하나도 쓰지 않는다. `BASE`, `vhea`, `vmtx`는 그대로다.

### 2.2 파일과 생성기

- `scripts/fonts/app-face-metrics.mts`(새, 순수 함수): `readLineMetrics`, `bakeLineMetrics`, `sfntChecksumsValid`,
  `unpatchedDifferences`. 굽기는 `hhea` +4/+6/+8, OS/2 +62(fsSelection |= 0x80)와 +68/+70/+72를 쓰고 모든 표 체크섬과
  `head.checkSumAdjustment`(0xB1B0AFBA − 전체 합)를 다시 계산한다. sfnt가 아님, `head`·`hhea`·OS/2 없음, OS/2 버전 4 미만, 다른
  unitsPerEm, 줄 값을 바꾸는 `MVAR`를 거절한다.
- `scripts/fonts/build-app-faces.mts`(새, `npm run generate:app-faces`): 앱 시트가 남기는 면만 굽는다(Inter 7, KR 120, JP 120,
  SC 95, TC 98. 시트 생성기의 범위 코드가 입력 cmap으로 계산하고 `appFaceInputs`로 내보냄). 면마다 차례로(WOFF2 인코더와
  디코더는 재진입이 안 됨) 풀고, 굽고, wawoff2로 다시 싸고, 다시 풀어 쓰기 전에 확인한다: 다시 푼 표가 구운 sfnt와 모두 같음,
  입력과 다른 곳은 `head` checkSumAdjustment, `hhea` 4~9바이트, OS/2 62~63과 68~73바이트뿐, cmap 같음, 체크섬 유효, 줄 값과
  win 값. 기본 방식은 기록, 입력 해시, 상자, 도구 버전이 그대로인 면을 건너뛴다. 기록된 입력·상자로 다시 구운 면은 도구
  버전이 바뀌었어도 기록된 바이트와 같아야 하고, 하나라도 다르면 아무것도 쓰지 않고 면과 두 버전을 적고 멈춘다(QA 라운드
  2에서 고침, §5 3). 새 버전이 같은 바이트를 주면 기록의 도구 버전만 바뀐다. `--record`는 확인한 새 바이트를 받아들이고,
  `--check`는 모든 면을 메모리에서 다시 구워 비교한다(약 85 ~ 93초). `npm run generate:font-sheets`가 쓰기 전에 기본 방식으로
  먼저 돌려서 문서의 갱신 순서(record-font-sources, generate:noto-kr, generate:font-sheets)가 늘 다시 굽는다.
- `fonts/app-faces.json`(새): 메모, 도구 `{ wawoff2: 2.0.1 }`, 가족마다 입력·출력 폴더, 상자, 지킨 win 값, 면마다 입력과
  출력의 sha256·크기. KR 입력 해시는 `fonts/font-sources.json`의 KR shipped, Inter 입력은 Inter source/shipped와 같아야 한다.
- 시트 생성기: 면 주소를 기록의 출력으로 바꾸고 머리 주석에 굽기를 적는다. 미리 받기 표는 구운 파일 크기로 계산한다(같은 조각).
- 참조: `vite.config.ts`의 인라인 제한에 `fonts/app`(4 KiB 미만 면 셋: TC #97 1,656 B, SC #97 2,076 B, SC #4 3,764 B. 빼면
  Vite가 시트 안에 data: URL로 넣음), App 릴리스 경로(`scripts/release-deployment-state.mts`)와 PWA 런타임 경로(`scripts/check-sw-cache-version.mts`)에
  `fonts/app`, 글꼴 가드의 원본 검사(기록과 파일, 아래)와 빌드 검사(빌드된 Inter·CJK 면이 구운 사본과 같은 바이트, 전에는
  Inter와 KR만), `e2e/font-identity.test.ts`의 줄기 표, `fonts/README.md`. 서비스 워커 목록이나 HTML preload에 글꼴 주소를 손으로
  적은 곳은 없다. 주소는 내용 해시라 새 바이트는 새 URL을 받고, 휴대폰은 이 변경을 담은 릴리스를 받는 대로 새 파일을 한 번
  받는다. 빌드는 Inter와 KR 입력 127개(Inter 7, KR 120, 3,765,728 B)를 더는 내보내지 않는다. JP·SC·TC 입력은 소개와 사이트맵
  페이지가 쓰므로 남는다(옛 탭에 미치는 영향은 §7).
- WOFF2 도우미(`scripts/fonts/font-files.mts`): 디코더와 새 인코더의 결과를 복사해서 돌려준다. 둘 다 다음 호출이 덮어쓰는
  WASM 메모리를 가리키는 뷰를 돌려주기 때문이다(전에는 받는 쪽이 곧바로 HarfBuzz에 넘겨 문제가 드러나지 않았다).
- 빠른 가드(`verifyAppFaces`, 몇 초): `guard:font-assets`와 `generate:font-sheets -- --check`가 기록이 있음, `fonts/app`에 기록
  없는 파일 없음, 입력과 출력 해시, 표가 `font-metrics.ts`와 같음, win이 입력과 같고 구운 상자를 담음, 체크섬, 입력과 다른 곳이
  굽기 필드뿐임을 본다. 시트가 기록된 출력만 가리키는 것은 시트 생성기 비교가 본다.

## 3. 바뀌어 보이는 것

    한국어와 영어 모두 1,339px과 1,422px의 PNG만 다르고 1,280, 1,318, 1,450px은 같음을 확인했다. 줄 탐침으로는 라틴 22.8, 26.95,

### 4.4 계획 단계 측정 (같은 바이트)과 WebKit 재측정

커밋한 사본 440개는 계획 단계의 시제품(별도 스크립트)이 만든 사본과 sha256이 모두 같다(440 / 440). 그래서 그때 잰 것이 이
파일에도 그대로 맞는다. 다만 그 WebKit 문장 하나는 틀렸다(아래, QA 라운드 2).

- Chromium 153, 탐침 1,610개(표본 다섯 × 8 ~ 72px을 0.25px 간격, 정수 크기는 400·700): 부모에서 덮어쓰기를 빼면 1,470개가
  다르고, 구운 면에 덮어쓰기를 두면 0개, 빼면 16개(§3의 경계 크기)가 다르다. 13, 15, 28px은 모두 같다.
- 6 ~ 96px을 0.01px 간격으로 본 모델(Chromium의 반올림): 덮어쓰기를 무시하는 엔진에서 Inter만인 줄은 9,001개 가운데
  119개(1.32%), CJK 줄은 175개(1.94%)가 1px 다르다. 정수·반 정수 크기로는 라틴 83.5, 85, 94px과 CJK 14.5, 43.5, 72.5, 89px뿐이다.
  비율은 맞지만 Chromium만의 숫자다. WebKit의 반올림으로는 경계가 다른 소수 크기에 걸린다(§3).
- Playwright WebKit 26.6: 세 덮어쓰기를 모두 따르고 `size-adjust`를 곱한다. 계획 단계는 구운 면에서 덮어쓰기를 둘 때와 뺄 때
  13, 15, 28px 높이와 1,610개의 반올림한 기준선이 같고 화면 찍기(그대로, 구운 면에 덮어쓰기 둠, 뺌)가 바이트까지 같다고 적었다.
  **화면 찍기 부분은 틀렸다(QA 라운드 2가 다시 잼, 아래 표).** WebKit은 덮어쓰기를 오름과 내림의 반올림 없이 쓴다. 그래서
  덮어쓰기를 두면 기준선이 픽셀 사이에 떨어지고(15px 줄 14.33 대 14, 13px 12.11 대 12, 28px 26.94 대 27, 14.5px CJK 17 | 13.64
  대 18 | 14), 휴대폰 시작 화면(393 × 852 @3x, 한국어와 영어, 두 번씩 찍어 안정)이 덮어쓰기를 둘 때와 뺄 때 다르다. 검토가 잰
  시작 화면 값은 역할 배지 기준선 13.906 대 13.5, 탐색 이름표 856.547 대 857이고, Chromium과 덮어쓰기를 뺀 WebKit은 둘 다
  13.5와 857이다. 맞는 것: 굽기는 덮어쓰기를 따르는 WebKit에서 중립이다(덮어쓰기를 둔 WebKit에서 부모 빌드와 이 브랜치 빌드의
  찍기가 같음, 검토). 오너의 아이폰 Safari는 덮어쓰기를 지원하지 않는 것이다(§1의 증상). 그러나 Safari가 이 WebKit처럼
  덮어쓰기를 지원하게 되면 아이폰은 구운 상자를 떠나 Chromium과 다시 달라진다(대부분의 줄에서 기기 픽셀 약 1개, 몇 크기에서 줄
  상자 1px, §7).
- 안 E(기술자를 구운 비율 97.94921875% / 24.8046875%, 101.3% / 25.7%로)는 1,610개 모두에서 구운 면 덮어쓰기 뺌과 같지만,

## 7. 위험

- **모델과 실제 Safari의 차이.** 증거는 Windows의 Chromium과 Playwright WebKit 26.6에서 덮어쓰기를 뺀 모델뿐이다. Windows
  Chromium은 각 면의 typo 값을 읽고 Safari(CoreText)는 `hhea`를 읽는다. 둘이 같다는 것은 브라우저가 아니라 표 검사가 지킨다(§4.1).
  실제 아이폰 Safari가 줄 상자를 다르게 반올림하면 경계 크기에서 1px이 더 다를 수 있다. 오너 아이폰의 iOS 버전을 배포 뒤 확인에서
  적는다(§8).
- **Safari가 덮어쓰기를 지원하게 되면(안 K와 E).** 덮어쓰기를 따르는 WebKit(Playwright WebKit 26.6)은 기술자를 오름과 내림의
  반올림 없이 써서 기준선이 픽셀 사이에 떨어진다(§4.4). Safari가 이것을 내보내면 아이폰은 구운 상자를 떠나 Chromium과 다시
  달라진다. 대부분의 줄에서 기준선이 기기 픽셀 약 1개(15px 줄 0.33px) 어긋나고, 몇 크기에서 줄 상자가 1px 다르다. 기술자가 남아
  있는 한 굽기는 이것을 막지 못하고, 안 D(덮어쓰기 셋을 뺌)만 이 위험이 없다(§9 1). §8에서 아이폰의 기준선이 정수(구운 상자를
  읽음)인지 소수(기술자를 따름)인지 적는다.
- **경계 크기의 1px.** 덮어쓰기를 무시하는 엔진(지금의 Safari)과 따르는 엔진(Chromium, Firefox) 사이에서 1.3 ~ 1.9%의 크기가 1px
  다르다(§4.4, Chromium의 반올림 모델). 앱에서는 고정 크기로 데스크톱 데모 역할 단추(14.5px CJK) 하나이고, 흐르는 크기로는 모든
  방문자가 처음 보는 시작 화면 오버레이(데스크톱 인사 제목이 창 너비 약 1,339px과 1,422px, 온보딩 설명이 약 1,318px, 720px 이상
  너비 배치에서는 창 높이 456 ~ 539px 근처의 띠)와 데스크톱 데모 글이 창 크기 2px 미만의 띠에서 그렇다(§3). 차이는 줄 상자
  1px(줄 높이를 정한 곳은 기준선 0.5px)이다. 안 E와 D는 이것을 없애지만 Chromium과 Firefox를 같은 크기에서 1px 바꾼다(§9 1).
- **엔진 사이의 소수 크기 반올림.** 같은 파일 값으로도 WebKit과 Chromium은 vw·vh에서 나온 소수 크기에서 1px 다를 수 있다(§3).
  어느 안에서도 남고, Pretendard 때도 그랬다.
- **Safari 16 이하와 webOS TV.** 나아지지만 같지 않다(§3).
- **Windows GDI.** win 값을 두었으므로 새 잘림은 없다. 줄 간격을 win에서 받는 오래된 앱은 브라우저가 아니다.
- **공개 페이지.** 소개, 사이트맵, 소개 형제 페이지는 Google의 시트와 파일을 바이트 그대로 쓰고, Pretendard 페이지는 그대로다.
  공개 페이지를 앱 글꼴로 바꾸는 뒤 열차는 구운 면을 써야 한다.
- **다시 받기와 크기.** 모든 사용자가 쓰는 조각을 한 번 다시 받는다. dist가 13.75 MB, 저장소가 약 17.7 MB 는다(§9 2, 3).
  소개와 앱을 모두 여는 ja·zh 방문자는 두 쪽이 다 그리는 JP·SC·TC 조각을 기기마다 두 번 받는다(ja 단계 C 목록만 약 377 KB,
  §4.5, §9 3).
- **배포 때 열려 있는 옛 탭.** 이 변경을 싣는 빌드는 9.0.29·9.0.30 시트가 가리키는 Inter·KR 파일 127개를 내보내지 않는다(§2.2).
  배포 뒤에도 9.0.29·9.0.30으로 도는 페이지(업데이트 창을 아직 받지 않음, 방장이 새로 고침을 미룸, bfcache 복원)는 이미 받았거나
  자기 CacheStorage에 있는 Inter·KR 조각만 그릴 수 있다. 옛 버전의 자산이 사라진 뒤 다른 Inter·KR 조각 요청은 실패하고, 드문
  한글 음절이나 라틴 확장, 키릴, 그리스, 베트남어 글이 새로 고칠 때까지 기기 글꼴로 그려지며, 단계 C는 그 실패에서 멈춘다.
  JP·SC·TC는 소개와 사이트맵이 원본을 계속 쓰므로 영향이 없다. [9.0.29 보고서](app-font-inter-noto-2026-10-31.md)는 같은 종류의
  옛 탭 404를 오너 정책(구버전 무시) 아래 적었다(그 보고서 §3 21, §7). 이것도 그 정책 아래 두고 릴리스 메모에 같은 줄을
  적는다(§10). 옛 탭까지 지키려면 입력 127개(dist 약 3.77 MB)를 한 릴리스 동안 더 내보내 옛 내용 해시 URL을 살려 두고 다음
  릴리스에서 뺀다(§9 4).
- **도구 변경.** wawoff2가 바뀌면 기본 방식(`generate:font-sheets`가 먼저 돌리는 것)이 모든 면을 한 번 다시 굽는다. 기록된
  바이트와 다른 면이 하나라도 있으면 아무것도 쓰지 않고 멈추고(§5 3) `--check`도 실패하며, 확인 뒤 `--record`로 받아들인다. 같은
  바이트면 기록의 도구 버전만 바뀐다. 빠른 가드(`verifyAppFaces`)는 기록된 버전과 설치된 버전의 차이를 보지 않는다. 그래서
  의존성 묶음이 wawoff2를 올려도 가드는 통과하고, 다음 생성 때 위 거절이 바이트를 지킨다.
- **`guard:sw-cache-version`.** 이 브랜치에서는 버전 올리기 없음으로만 실패한다. 버전 올리기는 이 변경을 싣는 릴리스의 몫이다.
- **충돌.** 다른 Phase 6 브랜치가 `css/fonts/app`, `src/i18n/font-*`, `vite.config.ts`를 고치면 시트를 다시 생성해야 한다
  (`npm run generate:font-sheets`가 바뀐 면만 다시 굽는다).

## 8. 배포 뒤 기기 확인

이 변경이 나간 뒤, 게이트 아님. 실제 아이폰에서는 아직 아무것도 재지 않았다. 이 보고서의 Safari 쪽 숫자는 모두 Windows의
모델(Chromium에서 덮어쓰기를 뺌, Playwright WebKit 26.6, §4)이다. 오너가 이 변경을 담은 릴리스 뒤 iOS 17 또는 18 아이폰에서 1을
본다. 기기마다 0을 먼저 한다.

0. **새 빌드인지 먼저 확인:** 업데이트 창을 받아들이고 앱을 다시 연다. 앱에서 새 버전과 빌드(예: 9.0.31 / v804, 그 전에 다른
   앱 업데이트가 나가면 그 번호)를 확인한다. 9.0.29·9.0.30을 담아 둔 기기는 새 HTML, 진입 청크, `locale-fonts` 청크, 시트와 그
   주소를 받기 전까지 옛 파일로 옛 줄 상자를 그린다(이미 열린 페이지나 bfcache, 업데이트 창 대기, 느린 네트워크에서 서비스
   워커의 캐시된 셸). 옛 페이지에서 잰 값은 고침이 실패한 것처럼 보인다. 할 수 있으면 Web Inspector에서 조각이 새 해시의
   `/assets/` 주소에서 오는지 본다.
1. **iPhone Safari(iOS 17, 18, 오너의 버전, 그 버전을 적음):** 15px와 13px의 한글, 라틴, 섞인 줄 높이(18px, 15px)와 재생목록이
   여럿일 때 탭 제목 넷의 높이(같음). 기준선이 정수인지(구운 상자를 읽음, 예상) 소수인지(기술자를 따름, 15px 줄 약 14.33) 적는다
   (§7). 9.0.29 보고서 §8 1의 확인을 잇는다.
2. **iOS 16(`size-adjust` 없음):** 글자 크기와 줄 높이(§3의 숫자).
3. 데스크톱 Safari 한 번(같은 엔진, 데모 단추 14.5px의 1px 포함, 기준선이 정수인지 소수인지).

   D를 더하고 비용을 고쳐 적었다(§3, §4.4, §7).
   - K(이 브랜치): Chromium과 Firefox가 9.0.29와 같은 픽셀이다. 지금의 Safari는 파일 값을 읽어 Chromium과 같지만, 반올림 경계 옆
     크기에서 줄 상자가 1px 다르다. 연속 크기의 1.3 ~ 1.9%이고, 앱에서는 데스크톱 데모 역할 단추(14.5px)와 흐르는 크기의 좁은 창
     크기 띠다(시작 화면 오버레이의 데스크톱 인사 제목과 온보딩 설명, 720px 이상 너비 배치의 창 높이 456 ~ 539px 근처, 데스크톱 데모
     글, §3). Safari가 덮어쓰기를 지원하게 되면 아이폰은 기술자를 반올림 없이 따라 대부분의 줄에서 기준선이 기기 픽셀 약 1개
     어긋난다(§7).
   - E: 기술자가 구운 값과 (빌드에서 넷째 자리까지) 같아져 지금의 Safari와 Chromium이 경계 크기에서도 같다. Chromium과 Firefox는 그 경계 크기에서 9.0.29보다
     1px 바뀐다. Safari가 덮어쓰기를 지원하게 되면 K와 같은 픽셀 사이 기준선이 남는다(추론, §4.4).
   - D: 모든 엔진이 덮어쓰기 지원과 상관없이 파일의 상자를 읽는다. 덮어쓰기를 뺀 WebKit과 Chromium은 0.25px 간격 8 ~ 40px에서
     모두 같다(§4.4). Chromium과 Firefox는 E와 같은 경계 크기에서 1px 바뀐다. 시트에서 덮어쓰기 기술자 1,320개가 빠진다. 고르면
     다음 증분에서 테스트 먼저로 시트 생성기, 기술자 시험, 글꼴 가드와 두 E2E 시험(`font-line-boxes`, `font-baked-pixels`)을
     바꾼다.
   - 어느 안에서도 vw·vh에서 나온 소수 크기는 엔진 사이에 1px 다를 수 있다(§3, Pretendard 때도 그랬음).
   - 권장: D. 오너 결정(모든 브라우저가 파일에서 같은 줄 상자를 받음)에 가장 가깝고 Safari가 덮어쓰기를 지원해도 바뀌지 않으며,
     대가는 Chromium과 Firefox의 경계 크기 1px 한 번이다. 처음 권장이던 K는 WebKit 찍기가 바이트까지 같다는 틀린 문장(§4.4)에
     기대었다. K를 고르면 §7의 "Safari가 덮어쓰기를 지원하게 되면" 위험을 안고 간다.
2. **[화면 그대로] 저장소 크기.** 구운 사본을 새 트리에 두어 저장소가 약 17.7 MB 는다. Inter와 KR을 제자리에서 구우면 3.77 MB
   덜 늘지만 파이프라인이 세 곳으로 갈라지고, "Inter는 받은 바이트 그대로"가 깨지며, 픽셀 시험이 쓰는 입력이 사라진다. 권장:
   지금대로.
3. **[화면 그대로] 배포 크기와 소개·앱이 나눠 쓰던 파일.** JP·SC·TC 앱 사본이 소개가 쓰는 원본 옆에 놓여 dist가 woff2 313개,
   13.75 MB 는다(받는 것은 쓰는 조각뿐). 그리고 소개와 앱이 더는 같은 파일을 나눠 쓰지 않아, 둘을 모두 여는 ja·zh 방문자는 두
   쪽이 다 그리는 조각을 기기마다 두 번 받는다(단계 C 목록만 ja 약 377 KB, zh-hans 343 KB, zh-hant 391 KB, 소개 쪽 어림 JP 507
   KB, SC 708 KB, TC 904 KB, §4.5). 고칠 길은 미뤄 둔 공개 페이지 열차가 소개와 사이트맵을 구운 사본으로 바꾸는 것이고, 그러면 그
   페이지들의 CJK 줄 상자가 바뀐다(§1 3). 권장: 그 열차까지 받아들임.
4. **[화면 그대로, 배포 때 열려 있던 옛 탭만 바뀜] 옛 탭의 Inter·KR 조각.** 이 릴리스는 Inter·KR 입력 127개를 내보내지 않아,
   배포 뒤에도 9.0.29·9.0.30으로 도는 페이지는 아직 받지 않은 Inter·KR 조각을 받지 못하고 그 글자를 새로 고칠 때까지 기기
   글꼴로 그린다(§7). 오너 정책(구버전 무시)대로 둘까요, 입력 127개(dist 약 3.77 MB)를 한 릴리스 동안 더 내보낼까요? 권장:
   정책대로 둠(새로 고치면 풀리고, 9.0.29의 같은 종류도 그렇게 다룸).

## 10. 릴리스 담당이 할 일

- 이 변경을 싣는 App 업데이트를 정한다(따로 내거나 다음 열차와 함께). 그 릴리스가 버전과 SW 캐시 epoch를 올리고(지금 9.0.30 /
  v803), `guard:sw-cache-version`이 통과해야 한다. 대상은 `app`, 업데이트 창이 뜬다.
- 머지 전 PR CI와 exact-main CI, 릴리스, 배포 뒤 확인(§8)은 아직이다. 릴리스 기록 §1과 `release-history.md`는 배포 기록이 적는다.
- 릴리스 메모에 한 줄을 적는다: 배포 뒤에도 9.0.29·9.0.30에 남은 탭은 아직 받지 않은 Inter·KR 조각을 받지 못해 그 글자를 새로
  고칠 때까지 기기 글꼴로 그린다. JP·SC·TC는 영향이 없다. 오너 정책(구버전 무시)에 따른다(§7, §9 4).
- 오너가 §9 1에서 D나 E를 고르면 그 증분을 테스트 먼저로 더하고 이 보고서에 QA 라운드를 더한다.
- 되돌리기: 앞으로 되돌리기(이 변경의 커밋을 되돌리는 커밋과 더 높은 버전·SW 캐시 epoch)가 기본이다. 입력 파일(`fonts/inter`,
  `fonts/noto/noto-sans-kr`, `fonts/noto/noto-sans-{jp,sc,tc}`)은 저장소에 그대로라 내려받기가 필요 없다. 되돌린 시트는 다시
  입력을 가리키고(9.0.29와 같은 바이트라 같은 내용 해시 주소), 빌드는 Inter·KR 입력 127개를 다시 내보낸다. 되돌리면 아이폰의 줄
  상자가 9.0.29처럼 되고(15px 한글 줄 약 20px, 재생목록 탭 제목이 다시 높음) Chromium과 Firefox는 그대로다. 낮은 epoch로 가는
  CLI 되돌리기는 릴리스 기록 §2 9.0.29 절의 열린 항목(낮은 epoch로 가는 App 손 되돌리기의 규칙)을 따른다. 데이터, 바닥, Durable
  Object, D1, 다른 Worker는 바뀌지 않는다.
