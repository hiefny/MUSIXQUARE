## 1. 오너 결정

오너의 말은 옮기지 않고 뜻만 적는다. 모두 2026-11-21이다.

- 증상과 고침(낮 12시대): 오너가 알린 것은 네트워크 없이 방을 열거나 들어가면 네트워크가 없다는 말을 하지 않는다는 것이다. 일반 방은 세션을 만들지
  못했다고 하고, PRO 방은 앱을 업데이트하라고 한다. 오너는 이를 고치기로 했다.
- 진행(12:35): 오너는 고치기 전과 고친 뒤의 그림을 오너가 승인하면 릴리스 담당이 PR, 머지, 배포, 기록을 하도록 승인했다. 그래서 그림을 승인받기 전에는
  PR을 열지 않았다.
- 그림 승인(18시 40분대, rebase 앞): 오너는 권장안을 담은 고치기 전후 그림(§8.6)을 보고 승인했다. 그 권장안이 이 열차의 결정이다.
  1. 문구: 새 키를 만들지 않고 이미 42개 언어에 있는 네트워크 문구 `error.network_issue`를 다시 쓴다(번역 없음. 일반 방 참여가 이미 한 갈래에서 쓰는
     문구).
  2. 범위: 오프라인일 때만 바꾼다. 실패를 처리하는 순간 브라우저가 네트워크 없음을 알리고 그 실패에 서버 응답이 없을 때다. 시도 전에는 아무것도
     확인하지 않는다.
  3. 이 버전의 PRO 런타임을 받기 전에 오프라인으로 PRO 방에 들어가면 지금처럼 새로고침 창을 열되, 제목과 버튼은 그대로 두고 본문만 네트워크 문구로
     바꾼다(창 대신 설정 줄로 보이는 안은 쓰지 않음).
  4. QR: 오프라인에서 QR 디코더를 받지 못하면 카메라 문구 대신 네트워크 토스트를 띄운다.
  5. 그대로 두고 한계로 적는 것(§12): PRO 런타임은 미리 받아 두지 않는다(조사의 어림으로 설치 다운로드가 버전마다 압축 약 52 KB 늘고, 첫 로딩 정책의
     측정과 오프라인 확인이 필요함). 인터넷 없는 네트워크는 브라우저가 온라인으로 알려 지금 문구 그대로다. PRO claim 다시 시도 창과 활성화 계정 창은
     문구 그대로다. 일반 방 설정의 약 3초 경로 사다리는 그대로다. 참여 bootstrap 동안 오프라인이 된 게스트의 방장 연결 끊김 창은 그대로다.

### 3.2 9.0.835에서 바뀌는 것([화면 바뀜])

아래는 모두 실패를 처리하는 순간(방 청크는 그 청크가 실패한 순간) 브라우저가 네트워크 없음을 알리고 서버가 답하지 않은 실패에만 해당한다. 새 글은

1. 방 만들기: 같은 자리의 빨간 줄이 "세션을 만들지 못했어요" 대신 네트워크 문구다. 버튼은 돌아가기(‹)와 '다시 시도' 그대로이고, '다시 시도'는 지금처럼
   새로 시도한다. 해당하는 실패는 모든 경로가 답 없이 실패한 HTTPS 다리의 오류(경로 사다리 뒤), HTTP status 없는 WebSocket 오류, 방장 입장 기한과 peer
   열기 기한이다.
2. 방 번호를 넣고 참여: 코드 칸 아래 "네트워크 오류가 발생했어요"나 "방장이 세션을 종료한 것 같아요" 대신 네트워크 문구다. 코드는 칸에 그대로 있고
   틀린 번호로 표시되지 않는다. 버튼 그대로.
3. 초대 링크로 참여: 초대 화면의 빨간 줄이 2와 같이 바뀐다. 버튼 그대로.
4. PRO 런타임을 받기 전의 PRO 입장(오너가 본 경우): 새로고침 창의 제목 "새로고침이 필요해요"와 버튼 '닫기', '새로고침'은 그대로이고 본문이 네트워크
   문구다. 뒤 화면과 닫은 뒤 화면(줄 없이 돌아가기(‹)와 '새로고침')은 그대로다. 설치된 앱(서비스 워커가 셸을 내주고, 받아 두지 않은 PRO 런타임은
   503으로 답함)에서도 같다. 오프라인에서 새로고침하면 같은 창이 다시 뜨고, 네트워크가 돌아온 뒤 새로고침하면 들어간다[추론: 코드 읽기].
5. PRO 런타임을 받아 둔 뒤의 PRO 입장: "PRO 방에 연결하지 못했어요" 대신 네트워크 문구다. 버튼 그대로이고, 네트워크가 돌아온 뒤 '다시 시도'를 누르면
   새로고침 없이 방이 열린다. 해당하는 실패는 답 없는 요청(요청 기한 포함), 입장 기한, 시작하지 못한 신호 소켓, 시간 안에 열리지 않은 소켓이다.
6. QR 스캔: 디코더를 받지 못하면 토스트가 "카메라를 시작할 수 없어요" 대신 네트워크 문구 두 줄이다. 디코더를 받은 뒤의 실패는 오프라인에서도 카메라
   문구 그대로다.
7. 방 청크가 오프라인에서 실패함(서비스 워커가 맡지 않은 페이지): 새로고침 창의 본문과 설정 줄 "새 버전이 준비되었어요" / "새로고침하면 업데이트가
   적용돼요"가 네트워크 문구다. 창의 제목과 버튼, 설정 화면의 돌아가기(‹)와 '새로고침'은 그대로다. Connect 런타임, 공지, 시각화 스펙트럼의 청크가
   오프라인에서 실패해 여는 새로고침 창도 본문이 같이 바뀐다(스펙트럼은 시각화를 스펙트럼으로 바꿀 때). 서비스 워커가 맡은 페이지는 이 청크들을 미리
   받아 두어 이 길을 타지 않는다.
8. 실패한 순간을 지킴: 문서는 지연 청크의 실패를 붙들어 두므로, 오프라인에서 실패한 청크는 네트워크가 돌아온 뒤 같은 문서에서 돌아가기나 닫기 뒤 다시
   시작해도 새로고침 전까지 네트워크 문구다. 온라인에서 실패한 청크는 뒤에 오프라인에서 다시 만나도 업데이트 문구 그대로다.

## 4. 원인과 조사

### 4.1 원인

- 공통: 방 입장 길의 실패 처리 지점 어디도 브라우저의 네트워크 보고(`navigator.onLine`)를 읽지 않았다. 실패마다 오류의 모양만으로 문구를 골랐고, 그
  모양에는 네트워크가 없다는 것이 들어 있지 않았다. 페이지의 online, offline listener 하나(`src/network/peer.ts`)는 시작한 일반 방의 방장에게만 돈다.
- 방 만들기: `src/ui/setup-host.ts`의 실패 처리가 지연 로드 실패도 최소 빌드 아래 거절(강제 업데이트가 맡음)도 아닌 모든 오류를
  `error.session_create_fail`로 바꿨다. 오류 자체는 보지 않았다. 오프라인에서 닿는 오류는 HTTPS
  다리(`src/network/transport/standard-http-signaling.ts`)의 날 DOM error 이벤트(status null, cause는 fetch의 TypeError)이고, 경로 사다리를 다 돈 뒤에
  온다.
- 일반 방 참여: 같은 이벤트가 게스트의 `network:error`로 `src/ui/setup.ts`에 닿는다. 그 메시지는 빈 글이고 type은 'error'라 어느 갈래에도 맞지 않아
  기본 `error.network_generic`이 나갔다. 네트워크 갈래(type 'network')는 클라이언트의 기한이나 소켓 닫힘 오류가 먼저 와야 타는데, 오프라인에서는
  다리가 닫힘보다 오류 이벤트를 먼저 낸다. 참여 기한(`HOST_UNREACHABLE`)은 `error.host_unreachable`이 됐다.
- PRO 런타임을 받기 전(오너가 본 경우): `src/pro-room/runtime.ts`가 검토한 지연 앱 셸 뿌리(`vite.config.ts`의 `REVIEWED_DEFERRED_APP_SHELL_ROOTS`)에
  없어 서비스 워커가 미리 받아 두지 않는다. 그래서 릴리스마다 첫 PRO 입장은 네트워크가 있어야 하고, 오프라인에서는 서비스 워커가 그 청크를 503으로
  답해(서비스 워커가 맡지 않은 페이지는 가져오기 자체가 실패해) `import()`가 실패한다. `src/pro-room/setup-flow.ts`가 그 실패를
  `LazyFeatureLoadError`로 감싸 `app:lazy-feature-load-failed`를 내고, `src/app.ts`의 복구 창이 앱이 업데이트됐다는 `dialog.feature_refresh_msg`를
  보였다. 최소 빌드 아래 강제 업데이트는 아니다(그 길은 서버의 426 `APP_UPDATE_REQUIRED` 답이 있어야 하고, 오프라인에서는 바닥 읽기를 건너뜀).
- PRO 런타임을 받아 둔 뒤: `src/pro-room/api.ts`가 fetch의 TypeError를 `ProRoomApiError` `NETWORK_ERROR`(status 0)로 감싸고,
  `describeProRoomJoinFailure`는 `ROOM_FULL`과 `RATE_LIMITED`만 따로 다뤄 `pro.connect_failed`가 나갔다.
- 방 청크(서비스 워커가 맡지 않은 페이지): 방 청크의 실패도 `LazyFeatureLoadError`이고, 그 판정(`src/core/lazy-feature-failure.ts`)에 네트워크 정보가
  없어 설정 줄은 `dialog.sw_update_msg`, 창은 업데이트 문구였다. 실패한 청크의 오류에는 오프라인 실패와 릴리스로 지워진 청크를 가를 것이 없다(§4.2).
- QR: `src/ui/setup-qr-scanner.ts`가 jsQR import의 어떤 실패도 'camera-unavailable'로 알렸고, jsQR은 미리 받아 두지 않는다.

### 4.2 조사의 측정

main `1f7a2681`(App 9.0.833 런타임. 그 뒤 9.0.834는 스크롤 막대만 바꿔 이 길들은 운영 9.0.834와 같다)에서 읽기만 한 조사, 12:41 ~ 13:45. 브라우저는
쓰지 않았고 작업 트리에는 아무것도 두지 않았다. 저장소 밖 단위 탐침의 결과:

- 신호(4/4, 실제 `CloudflareSignalingPeer`와 가짜 소켓): 오프라인이면 게스트와 방장 모두 주 WSS, 다른 WSS, HTTPS 다리가 바로 실패하고, 설정이 받는
  오류는 DOM 이벤트(type 'error', phase 'open', status null, cause 'TypeError: Failed to fetch')였다. 모든 경로가 매달리면(인터넷 없는 네트워크) type
  'network'의 입장 기한 오류가 왔다.
- 설정 문구(13/13): 방장은 다리 이벤트, type 'network' 입장 기한, peer 열기 기한 모두 `error.session_create_fail`과 '다시 시도'였다. 게스트는 다리
  이벤트에 `error.network_generic`, type 'network' 기한에 `error.network_issue`(이미 네트워크 문구), 참여 기한에 `error.host_unreachable`이었다.
- PRO: 런타임 청크를 받지 못하면 결과는 reload-required이고 보고된 오류는
  `LazyFeatureLoadError`(`PRO_ROOM_RUNTIME_LOAD_FAILED_RELOAD_REQUIRED`)였으며, 네트워크가 돌아와도 같은 문서에서 다시 reload-required였다(평가 한
  번). 런타임을 받아 둔 뒤의 오프라인 bootstrap은 `ProRoomApiError` `NETWORK_ERROR` status 0에 `pro.connect_failed`, claim 링크는 claim 다시 시도
  창이었다.
- 미리 받기: 이웃 빌드(그 빌드의 `vite.config.ts`, `src/pro-room/setup-flow.ts`, 서비스 워커 소스는 `1f7a2681`과 같음)에서 main 청크가 PRO 런타임
  import에 붙인 청크 19개 가운데 서비스 워커가 미리 받아 두지 않는 것은 PRO 런타임 청크 하나였다.

  가를 것이 없어, 실패한 순간에 적어야 했다.

### 4.3 조사의 검증

설계를 따로 읽은 검증 한 번(13:34, 단위 탐침 하나)이 여섯을 찾았고 모두 설계에 넣었다.

1. (major) 서비스 워커를 막은 브라우저 행이 방 청크를 받기 전에 오프라인이 되면, 오너가 본 길(설치된 앱의 "세션을 만들지 못했어요")이 아니라 방 청크
   실패 길을 탄다. 그래서 일반 방 행은 같은 문서에서 온라인으로 역할을 고르고 한 번 시도해 방 청크를 받은 뒤 오프라인으로 '다시 시도'하고, 방 청크
   실패 길은 따로 F7 행으로 찍었다(§6.2).
2. (minor) PRO 런타임의 실패는 모듈이 사는 동안 붙어 남아, 그 행을 기존 시험 파일에 두면 지나갈 수 없다(탐침으로 확인). 그래서 새 파일
   `setup-runtime-offline.test.ts`가 행마다 모듈을 새로 불러온다.
3. (minor) PRO 소켓 열기 기한 `PRO_ROOM_CONNECT_TIMEOUT`이 PRO의 답 없는 실패 목록에 없었다. 더했다.
4. (minor) Connect 런타임, 공지, 시각화 스펙트럼은 날 오류를 붙들어 두고 다시 보고해, 보고하는 순간의 오프라인을 읽으면 같은 문서에서 네트워크가
   돌아온 뒤 업데이트 문구가 돌아온다. 그래서 세 곳도 실패한 순간에 `LazyFeatureLoadError`로 감싼다.
5. (nit) 참여 bootstrap 동안 오프라인이 된 게스트는 방장 연결 끊김 창을 본다. 그대로 두는 한계로 적고 단위 행으로 고정했다.
6. (nit) 상태 없이 오는 서버 거절 둘(PRO 신호 Worker의 소켓 업그레이드 거절 401, 429, 503과 HTTP 우선 힌트 아래 일반 방 WSS 업그레이드 거절)은 늦은
   오프라인 보고에서 네트워크로 읽힌다. 코드 주석과 한계로 적었고 코드는 바꾸지 않았다.

## 12. 남긴 한계

1. PRO 런타임은 미리 받아 두지 않는다(오너 결정, §1): 릴리스 뒤 첫 PRO 입장을 오프라인에서 하면 여전히 새로고침 창이 뜨고(이제 본문은 네트워크 문구),
   서비스 워커가 맡은 페이지(설치된 앱)에서는 오프라인에서 새로고침하면 같은 창으로 돌아오고(맡지 않은 페이지는 9), 네트워크가 돌아온 뒤 새로고침하면
   들어간다[추론: 코드 읽기, 브라우저에서 새로고침은 해 보지 않음].
2. 인터넷 없는 네트워크(와이파이는 붙었지만 인터넷이 안 됨, 캡티브 포털, VPN이나 가상 어댑터, 신호 호스트만 막힘)는 브라우저가 온라인으로 알려 지금
   문구 그대로다. 런타임을 받기 전의 PRO 입장에서는 업데이트 문구 창도 그대로다.
3. 늦은 오프라인 보고(WebKit은 회복 뒤에도 잠시 오프라인으로 알릴 수 있음): 그동안 실패하면 상태 없이 오는 서버 거절(PRO 신호 Worker의 소켓 업그레이드
   거절 401, 429, 503과 HTTP 우선 힌트 아래 일반 방 WSS 업그레이드 거절)과 릴리스로 지워진 청크도 네트워크 없음으로 읽힌다. '다시 시도'나 '새로고침'은
   같은 행동이다. 시도 전 확인은 없어 늦은 보고가 시도를 막지는 않는다.
4. PRO claim 다시 시도 창과 활성화 계정 창은 문구 그대로다(claim 창은 이미 연결이 중단됐고 링크를 지키고 있다고 알림).
5. 참여 bootstrap 창(게스트의 데이터 채널이 열린 뒤 bootstrap이 끝나기 전)에 오프라인이 된 게스트는 방장 연결 끊김 창을 그대로 본다(단위 행이 고정).
6. 일반 방 설정의 약 3초 경로 사다리 뒤에 안내가 나오는 것은 그대로다. 오프라인이면 바로 안내하려면 사다리를 맡은 공급자를 바꿔야 하고, iOS의 셀룰러와
   와이파이 전환 대비와 얽혀 있다.
7. 프레임 type, 코드나 HTTP status를 지닌 서버 응답은 브라우저가 오프라인으로 알려도 문구 그대로다.
8. 오프라인에서 지연 청크가 실패한 문서는 네트워크가 돌아온 뒤에도 새로고침 전까지 네트워크 문구다(브라우저가 실패한 모듈 가져오기를 문서 동안 붙들 수
   있어 붙들기와 '새로고침'을 그대로 둠).
9. 서비스 워커가 맡지 않은 페이지에서 오프라인 지연 실패의 '새로고침'은 셸을 내줄 서비스 워커가 없어 브라우저 자신의 오프라인 화면을 보일 수
   있다[추론].
10. 기기에서 확인하지 않음: 실제 iPhone, Android, 노트북의 비행기 모드나 끊긴 네트워크, 실제 운영 서버, 오프라인에서 처음 그리는 글자의 글꼴.
