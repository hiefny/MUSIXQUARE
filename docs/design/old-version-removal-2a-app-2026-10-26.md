### A-1 C5-12 Inc 3 (OV-F02)

테스트 `d66d4cbe`, 코드 `23690c92`. 검증한 SHA `23690c92`.

- **방장 규칙(b513b732의 규칙으로):** ICE 복구 뒤 본 레인이 정확한 (연결, 대기열 항목, 세션)을 준비하거나 보내고 있으면
  미리받기가 물러난다. `resumeSuspendedPreloadLane`은 멈춘 레인을 다시 시작하기 전에 `isMainLanePreparingOrActive`를 묻고,
  참이면 다시 시작하지 않고 `yieldPreloadToMainLane`(복구 뒤 `PRELOAD_ABORT` 하나와 Yielding 줄)으로 넘어간다. 이미 다시
  시작한 `unicastPreload`(`restart`)는 `canContinue`에서 끊김 확인 뒤 같은 질의를 물어, 본 레인이 그 짝을 잡으면 다음
  확인에서 멈추고 finally에서 미룬 abort를 보낸다. 경로는 읽지 않는다.
- **지운 것:** 경로 허락 기계 `RestartedPreloadLane`과 `_restartedPreloadLanes`, `settleRestartedPreloadRoutes`,
  `revokeRestartedPreloadYields`, `onPeerIceRecovered`, `preload.ts`의 `orchestrator:peer-type-detected` 리스너.
  `network:peer-ice-recovered`에는 `resumeSuspendedPreloadLane`을 바로 등록한다. 이 기계는 9.0.9부터 방장이 그 연결에
  `local`을 알린 뒤에만, 그 뒤 복구 알림이 없을 때만 다시 시작한 레인이 물러나게 했다. 9.0.14 아래 게스트가 경로가 `local`이
  아니면 본 레인 머리를 버릴 수 있었기 때문이다.
- **남긴 것:** `isMainLanePreparingOrActive`, `yieldPreloadToMainLane`, `sendDeferredPreloadAbort`, Yielding 줄,
  `PRELOAD_ABORT` 규칙. 기기 근거 세 줄(Paused, Resuming, Yielding)은 바이트가 같다. 복구 때 본 레인이 이미 그 짝을 잡고
  있으면 Resuming 줄 없이 Paused와 Yielding만 남는다.
- **주석:** `SuspendedPreloadLane`과 `transfer-send.ts`의 튜플 질의 주석이 물러남을 다시 설명한다. `state:network.hostConn`
  리스너 주석은 '옛 PRO 호스트 연결' 대신 남는 이유(일반방 호스트 연결이 PRO 맥락 전환을 넘어 남을 수 있음)를 적는다(열차 1
  R5 후속, 코드 그대로). C5-0 랩 F4의 단언은 같고, 물러남을 방장의 경로 재판정에 묶던 주석만 고쳤다.
- **bus-pairing:** `orchestrator:peer-type-detected`는 `host.ts`가 계속 보내고 `orchestrator.ts`가 계속 들어 짝이 남는다
  (202/202).

## 배포·회복

**배포 대상.** target `app`, Developer API D1 `false`, `raise_app_build_floor` `false`. 이 갈래는 App 런타임 입력(`src`,
`browser/service-worker.ts`, `public/manifest.webmanifest`, `vite.config.ts`)과 가드·테스트·문서만 바꾸었다. bump가 SemVer와 SW
캐시 epoch를 함께 올리는 마지막 런타임 커밋이 되고, 업데이트 창이 뜨는 배포다. 오너 결정(01:50)대로 자동 게이트가 통과하면
따로 묻지 않는다.

**순서와 조건(계획 §1.3, §3).**

1. 릴리스 W(target `all`, SemVer·SW 캐시 그대로)가 먼저 배포되고 기록된다. A를 W보다 먼저 내지 않는다. W의 신호 Worker
   배포가 바닥 전에 맺어진 옛 방장 소켓을 재접속시켜 거르고(위 '바닥이 거르지 못하는 곳'), W PR이 main에 있고 배포되지
   않았으면 target `app`인 A는 partial-release 게이트(`release-deployment-state.mts`)에서 거절되기 때문이다.
2. W 직후 `app-build-floor.yml` `set min_app_build=787`(같은 값, 검증만)이 통과한다. 실패하면 floor 도구의 forward repair가
   끝날 때까지 기다린다.
3. 배포 직전 `status`로 저장값과 유효값이 787 이상인지 보고 요약 줄을 이 보고서에 적는다. 787 아래면 OV-F01, F02, F03,
   F05, F06을 실은 이 릴리스는 기다린다.
4. 각 열차(W, A, 5B)는 자기 배포 직전에만 main에 머지한다. 머지부터 배포와 기록 PR 머지까지 다른 열차는 머지하지도
   릴리스하지도 않는다. floor workflow는 릴리스와 같은 동시성 그룹이라 릴리스가 돌거나 기다리는 동안 dispatch하지 않는다.
   배포가 실패해 forward repair가 필요하면 그것이 끝날 때까지 기다린다.
5. 먼저 나간 열차가 기록되면 origin/main을 합치고 전체 단위, 가드(room-authority 총합을 다시 잼), 빌드와 예산을 다시
   돈다. 그다음 bump, bump 뒤 최종 검사(`guard:release-identity`, `guard:sw-cache-version`, `build:checked` 전체, 단위, Worker
   단위, 핵심 커버리지, critical E2E, C5-0 랩, 강제 업데이트 랩, 후보 Playwright), 열차 끝 세 렌즈 리뷰(지금 클라이언트,
   완결성, 통신), PR CI, Codex, exact-main CI, Release, 기록 PR 순이다.
