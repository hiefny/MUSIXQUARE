## 질문과 판정

정상적인 min-RTT 표본 교체도 `clock-changed`를 만들 수 있다. 이번 실험에서는
시계 추정이 바뀌는 첫 시도를 제외한 뒤 안정된 다음 시도부터 학습을 계속했다.
5ms 게이트 때문에 학습이 계속 막히는 현상은 아래 브라우저 조건에서 관찰되지
않았다. 즉시 기준을 완화하거나 offset 차이를 drift에 보정할 근거로 삼지 않는다.

이 결과는 모든 네트워크에서의 발생률이나 실제 스피커 첫 음 정렬을 증명하지
않는다. `clock-changed`는 지연값 학습을 제외한다는 뜻이며, 그 자체로 랑데부
재생을 취소하거나 저장된 학습값을 초기화하지 않는다. 일정하게 잘못된 시계도
게이트를 통과할 수 있으므로 eligible 비율과 실제 정렬은 별개다.

제품 소스·설정·버전·시계 정책은 변경하지 않았다. 로컬 검사만 수행했으며
고객방 입장, 원격 CI, 푸시, PR, 병합, 배포는 하지 않았다.

## 실제 브라우저 연결 + 통제한 플레이어

각 조건마다 독립 Chromium context 두 개를 UI로 일반방에 연결했다. 실제
DataConnection의 `sync-ping` 송신과 `sync-pong` 응답만 지연시켰다. 원본 payload,
timestamp, SharedClock 선택/만료 및 실제 rendezvous 실행 코드는 유지했다.
YouTube 제어·heartbeat는 지연하지 않았으므로 전체 WAN을 흉내 낸 검사는 아니다.

기존 fake YouTube helper에서 시간 진행을 켜고 host 호출 지연 0ms, guest 100ms를
넣었다. 재생이 안정된 뒤 시계 표본을 초기화하고 첫 실제 PONG을 받은 다음,
각 조건에서 수동 랑데부 12회와 실제 800ms 학습 표본을 수집했다. 각 조건의
지연은 고정 seed로 만들었으며 브라우저 타이머·스케줄링 지연은 실제 값이다.

| 조건: PING / PONG에 더한 지연       | 표본 | eligible | clock-changed | 기타 제외 | 마지막 학습값 | 최대 네 시점 offset 범위 |
| ----------------------------------- | ---: | -------: | ------------: | --------: | ------------: | -----------------------: |
| 추가 없음                           |   12 |       12 |             0 |         0 |         101ms |                      1ms |
| 각각 1–9ms                          |   12 |       12 |             0 |         0 |         104ms |                      0ms |
| 각각 1–81ms                         |   12 |       12 |             0 |         0 |         103ms |                      1ms |
| 상행 5–15ms / 하행 80–120ms         |   12 |       11 |             1 |         0 |         101ms |                     15ms |
| 20/80ms에서 첫 시도 중 5/5ms로 개선 |   12 |       11 |             1 |         0 |         103ms |                   36.5ms |

총 60개 중 58개 eligible, 2개 clock-changed다. 두 제외 모두 첫 시도에 발생했고,
각각 이후 11회는 eligible이었다. 제외 시 `nextLatencyMs: null`, 실제 학습 상태
0ms 유지도 확인했다. 큰 지터 행의 0건은 이 seed와 실행 결과일 뿐이며, 아래
다중 seed 모형의 초기 시계 결과로 일반화의 한계를 확인한다.

비대칭 조건에서는 첫 시도의 계획/예약 offset -53ms가 호출/표본 때 -38ms로
바뀌었다. 호출 이후 값만 비교하면 변화가 0이지만 네 시점 span 15ms가 되어
게이트가 막았다. 마지막 선택값은 -38.5ms였고, 같은 PC의 두 context라 실제
기기 간 벽시계 차이는 없다. 즉 낮은 제외율과 약 100ms로의 학습 수렴이 시계
추정의 절대 정확도를 보장하지 않음을 직접 보여준다.

## 실제 YouTube 플레이어

모형을 설치하지 않은 두 context에서도 공식 iframe API 예제 영상
`M7lc1UVf-VE`를 로드했다. 3초 간격 8개 관측에서 초기 buffering 이후 양쪽
PLAYING과 미디어 시간 진행을 확인했고, 24초 시점 양쪽 시간은 약 21.21초였다.
YouTube iframe과 실제 영상 화면도 확인했다. 두 위치는 서로 다른 순간에 읽었으므로
단순 차이를 밀리초 음향 정밀도로 해석하지 않는다.

이어서 실제 화면의 Sync 버튼 → 입력 창 → 완료를 8회 반복했다. 첫 자연 발생
`youtube-sync`가 수신된 뒤의 8회 모두 eligible, clock-changed 0건, offset span은
최대 1ms였다. 학습값은 `22 → 39 → 46 → 53 → 60 → 61 → 65 → 65ms`였다.
호스트/게스트의 플레이어 위치와 각각의 `Date.now()`를 함께 읽어 같은 시점으로
환산한 위치 차이는 첫 표본 약 -78.3ms, 마지막 약 -6.4ms였다. 중간 값은 단조롭게
줄지 않았으며, 이 수치는 IFrame API의 추정 재생 위치이지 실제 소리 측정이 아니다.

별개로 **제로스타트 직후 첫 Sync 클릭의 준비 공백**을 확인했다. 처음 두 실행은
첫 PLAYING 관측에서 4초 뒤 클릭하고 12초 안에 학습 표본을 기대해 timeout됐다.
계측을 붙인 두 번째 실행에서는 `standardStarts: 0` 및 "No host playback data yet,
try again in a moment"를 확인했다. 시계 게이트나 버퍼 단계에서 거절된 것이 아니라
아직 host playback snapshot이 없어 시작 자체가 거절됐다.

세 번째 실행은 같은 초기 클릭을 보존하고 첫 자연 `youtube-sync` 수신 이후 다시
클릭했다. 초기 안내가 한 번 더 나온 뒤 재클릭과 후속 7회가 정상 진행됐다.
실제 프레임은 이후 3초 간격으로 계속 도착했다. 첫 유효 snapshot은 원시 기록
`1791789502785ms`, 첫 재시도 계획은 `1791789503247ms`다. 새 프레임을 만들어
주입하거나 제품 타이머·게이트를 바꾸지 않았다.

코드상 PLAYING 관측은 음소거 예열 중에도 가능하다. 실제 release 후 zero-start는
2.75초간 일반 heartbeat를 억제하고, 이후 3초 주기의 첫 heartbeat 전까지는
snapshot이 없을 수 있다. UI는 `no-data` 응답을 안내하고 자동 재시도하지 않는다.
따라서 한 번 클릭한 뒤 기다리기만 해서는 그 클릭의 학습 표본이 생기지 않는다.
이를 heartbeat 영구 중단이나 C11 회귀로 판정하지 않는다. 짧은 준비 상태에서
클릭을 보류·재시도하는 UX 개선 여부는 후속 검토로 남겼다.

## 실제 모듈을 호출한 대량 시계 모형

8개 seed, 7개 지연 분포, 5개 시작 조건과 lead/buffer 민감도 조합으로
**150,400회**를 실행했다. 실제 `registerPing/processSyncPong` 및
`captureRendezvousClock/createRendezvousCalibration`을 호출했다. PONG 처리
5,522,745회이며, 완료된 시도에서 실제 학습 게이트와 독립 네 시점 판정의 불일치는
0건이었다. 네트워크, 이벤트 시간과 입력 drift는 모형이며 실제 브라우저 재생
150,400회 또는 별도 회귀 테스트 150,400개라는 뜻은 아니다.

아래는 완료되고 네 시점 모두 보정된 시도 중 offset span >5ms 비율이다. 각 칸은
3,200시도로 시작하며 release abort는 분모에서 제외한다. **현장 발생 확률이 아니다.**

| 지연 분포                                     | 첫 PONG 직후 | 표본을 90초 모은 뒤 |
| --------------------------------------------- | -----------: | ------------------: |
| 고정 대칭 / 함께 변하는 대칭 / 작은 독립 지터 |           0% |                  0% |
| 각 방향 `5 + Exp(평균 15)` ms                 |       45.16% |                  0% |
| 지속 비대칭                                   |       41.06% |                  0% |
| 일부 요청에서 한 방향만 큰 지연               |       12.37% |                  0% |
| 각 방향 `5 + Exp(평균 75)` ms                 |       62.06% |               3.34% |

중간 지터 초기 제외 1,445개 중 1,155개, 큰 지터 초기 제외 1,958개 중 1,521개는
마지막 선택 RTT와 실제 offset 오차가 모두 개선됐다. 개선된 시계라도 그 작업의
학습 기준이 바뀐 것은 같으므로, 이것만으로 잘못된 제외라 판정하지 않는다.
큰 지터의 90초 조건은 seed별 2.5–4.75%였다.

정밀한 최저 RTT 표본이 60개 제한으로 밀려나거나, PING을 120초 중단한 뒤 첫
PONG으로 만료되는 조건도 별도로 만들었다. 전자는 큰 지터에서 22.28%, 후자는
큰 지터에서 83.80%였다. 최저 표본이 해당 순간에 제거되도록 구성한 조건부
스트레스이며 장기 세션의 일반 발생률이 아니다. 랑데부 계획 시점에 PONG이 하나도
없던 조건은 네 시점의 보정 요건 때문에 완료된 시도 전부 학습에서 제외됐다.

이 모형은 1Hz PING, 실제 min-RTT·동률·60개/120초 표본 관리, 1.5초 예약 여유,
800ms 관측을 쓴다. 패킷 손실, 실제 미디어, OS 시계 스텝, oscillator drift,
브라우저 정지·실제 슬립은 포함하지 않았다. 시계 getter 자체는 표본을 만료시키지
않으며 유효 PONG 수신 때만 만료·재선택이 일어난다.

## 실행·증거와 한계

- 브라우저 첫 묶음: 6 pass / 0 fail / 0 skip, 6.0분. 실제 YouTube 관측 1개와
  12회씩 수행한 통제 조건 5개다. 실제 영상 관측 테스트의 통과만을 재생 성공의
  근거로 삼지 않았으며, 저장된 state/time과 스크린샷을 별도로 확인했다.
- 실제 UI 추가 검사: 최초 두 실행 각각 1 timeout. 위 준비 공백으로 sample이
  생긴다는 기대가 성립하지 않았다. 초기 클릭 결과를 기록하고 자연 snapshot 뒤
  재클릭한 최종 실행은 1 pass / 0 fail / 0 skip, 1.0분, 유효 학습 표본 8개다.
  초기 timeout을 숨기거나 최초부터 모든 UI 클릭이 성공했다고 보고하지 않는다.
- 첫 scratch 서버 설정은 cwd 오류, 이어서 Vite 기동 120초 초과로 검사 전에
  중단됐다. 전용 cwd, native config loader, scratch watch 제외, index.html
  dependency entry를 지정한 뒤 실행했다. 제품 결함이나 게이트 실패로 세지 않는다.
- 전용 localhost 포트 4491/9151, 익명 계정 응답 mock, 실제 로컬 P2P 사용.
  로컬 TURN API 503/STUN-only, headless WakeLock 경고가 있었다. 이 경고를
  원격 릴레이나 잠금 환경 검증 성공으로 해석하지 않는다.
- 전체 Vitest·전체 E2E·WebKit·원격 CI는 재실행하지 않았다. 이번은 특정 가설의
  로컬 실험이며 exact-main 배포 후보 검증이 아니다.
- iPhone/Android 실기, Bluetooth 출력, 독립 녹음은 없다. 두 context는 같은 PC의
  OS 시계를 공유한다. 시뮬레이션으로 실제 기기별 음향 출력 지연을 확정하지 않는다.

로컬 재실행 명령(저장된 scratch harness 필요):

```powershell
$env:MXQR_E2E_APP_PORT='4491'
$env:MXQR_E2E_PEER_PORT='9151'
node node_modules/@playwright/test/cli.js test --config scratch/standard-browser-simulation-2026-10-12/playwright.config.mts
npx tsx scratch/standard-clock-rate-simulation-2026-10-12/run.ts
```

Node는 저장소 지정 24.20.0을 사용했다. 원시 JSON, flight recorder와 스크린샷은
`scratch/standard-browser-simulation-2026-10-12/`에, 대량 모형 소스·seed·집계·예제
trace는 `scratch/standard-clock-rate-simulation-2026-10-12/`에 보관한다. scratch는
Git에 포함되지 않는 이 PC의 로컬 실험 자료다. `release-record.md` §2에 이번에
관찰한 초기 Sync 준비 공백의 UX 검토만 추가했다. 운영 상태·실기 확인의 완료
판정·배포 범위는 바꾸지 않았다.
