# 대용량 로컬 오디오 재생 제안

- 작성일: 2026-09-23
- 상태: 제안. 새 재생 엔진은 구현하거나 활성화하지 않았다.
- 작업 범위: `mxqr_beta`. main, 원격 저장소, 프로덕션은 변경하지 않는다.

권장 방향은 **구간 디코딩 + 제한된 PCM 버퍼 + 기존 AudioContext 시계**다.
일반 파일의 전체 AudioBuffer 재생을 유지하면서, 큰 파일을 위한 두 번째
엔진을 검증한다. 엔진 선택 기준과 미지원 기기 처리는 검증 후 결정하며,
이번 경고 제거를 새 재생 방식이나 제한 완화의 승인으로 해석하지 않는다.

## 현재 메모리가 커지는 두 지점

`src/player/decode.ts`는 전체 Blob을 ArrayBuffer로 읽고 `decodeAudioData()`로
전체 PCM을 만든다. 수신 측 `src/storage/ramstore.ts`도 파일 전체 청크를
모은 뒤 Blob을 만든다. PRO 다운로드의 `src/pro-room/media-transfer.ts`는
파일 크기만큼 ArrayBuffer를 먼저 할당한다.

따라서 다음 두 작업은 별개다.

1. **디코딩 메모리 제한:** 재생 위치 근처만 PCM으로 풀고 지난 구간을 해제한다.
2. **수신 메모리 제한:** 압축 파일도 필요한 구간만 요청하고 지난 구간을 해제한다.

1번만 해도 긴 MP3 등에 유리하지만, 전체 압축 파일은 여전히 메모리에 남는다.
수 GB 파일까지 다루려면 2번까지 필요하다. 파일 선택으로 받은 호스트의 File은
필요한 범위만 읽을 수 있지만, 게스트의 수신 경로는 별도로 바꿔야 한다.

계산 예시로 48 kHz·스테레오·Float32 PCM은 1시간에 약 1,318 MiB이고,
10초 분량은 약 3.66 MiB다. 원본 파일, 디코더 내부, 복사본, 효과 처리의
메모리는 제외한 값이다. 다채널·고샘플레이트에서는 더 커진다. 따라서
버퍼는 시간뿐 아니라 바이트 수로도 제한해야 한다.

## 방식 비교

| 방식                                     | 장점                                                                    | MUSIXQUARE에서의 제약                                                                                                 | 판단                                                  |
| ---------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `<audio>` + Web Audio 효과               | 전체 PCM을 앱이 직접 보관하지 않아도 된다. 비교적 단순하다.             | 재생 시작·seek를 기존 AudioBuffer처럼 오디오 시각에 직접 예약할 수 없다. 전체 Blob URL이면 압축 파일 메모리는 남는다. | 빠른 시제품에는 좋지만 정밀 동기화의 우선안은 아니다. |
| MSE / ManagedMediaSource                 | 미디어 조각을 순차 공급하고 재생된 구간을 버릴 수 있다.                 | 포맷에 맞는 컨테이너·세그먼트 준비가 필요하다. 출력은 미디어 요소이므로 위 동기화 제약도 남는다.                      | 브라우저가 관리하는 스트리밍 후보.                    |
| WebCodecs + Worker + AudioWorklet        | 구간별 PCM을 얻고, 기존 AudioContext 안에서 샘플 위치를 제어할 수 있다. | 컨테이너 해석, seek 인덱스, 버퍼 관리와 브라우저별 코덱 지원 검사가 필요하다.                                         | 정밀 동기화를 위한 우선 실험안.                       |
| 증분 WASM 디코더 + 같은 출력 엔진        | WebCodecs가 없는 기기나 미지원 코덱을 보완할 수 있다.                   | CPU·배터리·배포 크기·라이선스 검토가 필요하다. 전체 파일을 메모리에 넣는 변환기는 목적에 맞지 않는다.                 | 필요한 포맷에 한정한 보완안.                          |
| 호스트가 PCM 또는 재인코딩한 오디오 전송 | 게스트의 원본 코덱 지원에 덜 의존한다.                                  | 호스트 부담과 전송량이 커진다. 손실 코덱 재인코딩은 음질도 바꾼다. 별도의 시각 정보가 필요하다.                       | 정밀 파일 재생의 첫 선택으로 권하지 않는다.           |

`<audio>` 출력도 `createMediaElementSource()`를 통해 Web Audio 효과에
연결할 수 있다. 효과 지원과 정확한 예약 시작은 서로 다른 문제다.
[MDN 문서](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/createMediaElementSource)

`decodeAudioData()`는 완전한 파일을 대상으로 한다. 임의의 바이트 크기로
`blob.slice()`한 뒤 반복 호출하는 것만으로는 올바른 구간 디코딩이 되지 않는다.
컨테이너·프레임 경계, 디코더 상태, 시작 지연과 끝 패딩을 처리해야 한다.
[MDN 문서](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData)

Safari의 WebCodecs AudioDecoder는 26.0에 추가됐다. 구버전 Safari에 이
방식을 그대로 적용할 수는 없다. 또한 API의 존재가 모든 코덱의 지원을
뜻하지 않으므로 `isConfigSupported()`와 실제 디코딩을 모두 확인해야 한다.
[WebKit 출시 설명](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/),
[WebCodecs 명세](https://www.w3.org/TR/webcodecs/)

iPhone에는 Safari 17.1부터 ManagedMediaSource가 있지만, AirPlay 대체 소스를
제공하거나 remote playback을 비활성화해야 하는 조건이 있다. 이를 모든
원본 파일에 바로 적용할 수 있는 스트리밍 API로 취급하지 않는다.
[WebKit 설명](https://webkit.org/blog/14735/webkit-features-in-safari-17-1/)

## 권장 엔진 구조

```text
File 범위 읽기 / 인증된 구간 수신
        ↓
컨테이너 파서 + 시간/바이트 인덱스
        ↓
Worker의 연속 디코더 (WebCodecs 또는 검증된 WASM)
        ↓
크기가 제한된 PCM 큐
        ↓
AudioWorklet → 기존 FilePlaybackRoute → 효과·볼륨·비주얼라이저
```

AudioWorklet은 Web Audio의 별도 오디오 스레드에서 동작한다. 따라서
주기적인 JavaScript 타이머로 청크를 하나씩 재생하는 대신, 오디오 프레임
기준으로 버퍼를 소비하는 구조를 실험한다. 네트워크 처리와 디코딩은
실시간 출력 스레드 밖에서 수행한다.
[MDN 문서](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorklet)

공통 엔진 계약은 `duration`, `canRenderAt(position)`,
`scheduleStart(deadline, position)`, `stop`, `dispose` 수준부터 분리한다.
현재 `_state.ts`, `transport.ts`, `network/sync.ts`의 AudioBuffer 존재 여부에
묶인 준비 판정을 실제 재생 구간의 준비 상태로 바꾸는 작업이 필요하다.

필수 유지 조건은 다음과 같다.

- 기존 공유 시계, `file-play-timing.ts`의 절대 시작 시점, 출력 지연 보정과
  수동 싱크 값을 사용한다. 엔진마다 별도의 방 타임라인을 만들지 않는다.
- 방 재생 위치와 기기별 실제 출력 위치를 구분한다. 수동 싱크에 필요한
  앞·뒤 구간을 확보하며, 큰 오프셋 때문에 버퍼를 무한히 늘리지 않는다.
- seek·반복·곡 전환마다 세대 번호를 바꾸고 오래된 디코더 출력과 예약을
  버린다. 큐 항목 ID, 방/전송 세션, 파일 버전을 함께 검증한다.
- 디코더 시작 지연, 패딩, 리샘플링을 정규화해서 같은 샘플 위치를 가리킨다.
  블록마다 독립적으로 리샘플링하여 경계 오차나 클릭음을 만들지 않는다.
- 청크 끝·일시적인 버퍼 부족을 곡 끝으로 간주하지 않는다. 곡 전환 권한은
  기존 호스트에 유지한다. 버퍼 부족 기기는 현재 방 시점으로 재합류한다.
- 입력·디코더 대기열·출력 큐를 모두 제한한다. 소비 속도보다 빨리 디코딩하여
  결국 전체 곡을 PCM으로 쌓지 않는다. 소비한 AudioData와 전송 버퍼는 해제한다.
- 다음 곡 준비가 현재 곡의 버퍼를 고갈시키지 않게 우선순위를 둔다.
  백그라운드 중 Worker가 정지하는 상황도 실기로 확인한다.
- SharedArrayBuffer를 전제해 앱 전체의 격리 헤더를 변경하지 않는다.
  먼저 전달 가능한 버퍼 풀로 검증하고, 추가 최적화는 YouTube·인증 경로와
  함께 별도로 평가한다.

## 단계별 검증

1. 기존 AudioBuffer 엔진을 공통 계약 뒤에 두고 동작 동일성을 검증한다.
2. 전송 방식은 그대로 두고 한 포맷에서 제한 PCM 엔진을 실험한다.
   WAV PCM으로 출력·seek 정확성을 먼저 검증하고, 실제 사용 빈도가 높은
   MP3의 프레임 인덱스·연속 디코딩·gapless 정보를 검증한다.
3. iPhone Safari/PWA, Android, Windows에서 기존 엔진과 섞인 방을 검사한다.
   시작, 연속 seek, 이전 곡, 끝부분 반복, 늦은 참여, 프리로드 순서 변경,
   큰 수동 싱크, 네트워크 단절·재합류, 백그라운드를 포함한다.
4. 긴 곡을 반복·탐색해도 메모리가 일정 범위에서 유지되는지 측정한다.
   버퍼 길이는 시작 대기시간과 다르며, 기존 시작 지연을 무조건 늘리지 않는다.
5. 별도 변경으로 P2P와 원격 전송에 구간 요청·취소·재요청·무결성 검증을 넣는다.
   인증된 HTTP Range/206 지원도 현재 전체 응답 경로와 분리해 검증한다.

Standard 원격과 PRO의 파일당 200 MiB 제한은 이 제안으로 자동 해제되지 않는다.
원격 제한을 높이는 작업은 저장 비용·만료·권한·재시도 정책까지 별도로 다뤄야 한다.
같은 네트워크여도 전달 정책에 따라 원격 저장소 경로를 사용할 수 있다.
OPFS 역시 압축 데이터 저장의 별도 선택지일 뿐 전체 PCM 문제를 해결하지 않으며,
현재 [RAM-only 정책](browser-media-storage-policy.md)을 변경하는 별도 검증이 필요하다.
