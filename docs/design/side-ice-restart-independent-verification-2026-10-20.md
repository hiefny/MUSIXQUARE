# 보조 제어 연결 ICE restart 독립 검증 (2026-10-20)

- Status: 오너 요청으로 구현 세션과 분리해 수행한 독립 검증이다. 검증 세션에는 오너의 실기
  관찰과 기대 결과를 주지 않았고, 절차와 합격 기준을 실행 전에 고정했다. 배포 기록이 아니다.
- Baseline: main `0ae3698d` (운영 8.11.23 / v732 런타임). Candidate: `ee8dcd28` (보조 연결
  ICE restart 브랜치에 같은 main을 병합한 커밋). 릴리스 커밋은 여기에 App·캐시 식별자만 올린다.

## 방법

Windows 11, headless Chromium 153.0.8010.12, 한 PC의 호스트·게스트 페이지, 실제 제품 협상과
파일 입력. 게스트 페이지의 P2P 패킷만 CDP로 끊고 시그널링 WebSocket은 유지한 뒤 복구했다.
두 버전을 같은 절차로 실행별 브라우저 하나씩, 순서대로 돌렸다. 시나리오는 (a) 직접 파일 전송을
마치고 재생 중, (b) 일반 전송 중, (c) 다음 곡 미리받기 중이고, 끊김 길이는 10·17·25초다.
16회 모두 유효했다(끊긴 동안 게스트 P2P 수신 0바이트, 오류 0, 재실행 0).

사전 기준: C1 끊김 대화상자·HOST_DISCONNECTED 없음, C2 연결 복구, C3 재생 지속(±30ms),
C4 제어 메시지가 정확히 한 번 순서대로 도착하고 복구 후 방장 제어가 1초 안에 반영,
C5 전송이 같은 연결에서 재개 없이 정확한 SHA로 완료.

- 10초 끊김은 두 버전 모두 ICE 자체 회복으로 유지됐다. 복구 후 방장 제어 4~5개가 약 0.1초에
  순서대로 도착했고 재생 잔차는 10ms 이내였다.
- 보조 연결이 `failed`에 닿는 17초 끊김에서만 차이가 났다. 운영 버전은 세션을 잃었고 후보는
  보조 연결을 ICE restart로 복구해 대화상자 없이 제어를 이어 갔다.
- 25초 끊김은 원래 연결의 기존 15초 유예 때문에 두 버전 모두 끝났다. 후보는 대화상자가
  4.6초 늦게 떴다.
- 두 버전 공통 C5 실패는 ICE restart와 무관한 기존 동작이다. 일반 전송은 `file-resume`으로
  청크 1~2개를 다시 받아 SHA까지 정확히 완료했다(사전 기준이 재개 없는 완료만 통과로 정함).
  미리받기는 방장이 자기 원래 연결의 `disconnected`를 감지한 순간 중단했고 복구 뒤 다시
  시작하지 않았다.
- 주소 변경(와이파이→LTE 같은 IP 변경)은 시스템·방화벽·네트워크 설정을 바꾸지 않고는 이 PC에서
  흉내 낼 수 없어 시도하지 않았다.

구현 세션의 별도 랩(같은 `ee8dcd28`, 8초 끊김과 보조 연결 failed 유도)도 같은 결론이었다: 짧은
끊김은 두 버전 모두 유지, 보조 연결 failed에서 운영 버전만 세션을 잃음, 미리받기 중단은 공통.
오너의 운영 8.11.23 실기 관찰(짧은 와이파이 끄기 후 복구, 미리받기 취소, 일반 다운로드 복구,
파일을 직접 받은 뒤 와이파이→LTE에서 연결 끊김)과도 어긋나지 않는다.

## 방법상 기록

- 공용 shaping 모듈은 최상위 `offline:false`를 함께 보내 규칙별 `offline`을 덮어쓴다. 또 HTTP/WS
  예외 패턴 `ws://*/*`가 포트가 붙은 로컬 주소와 맞지 않아 첫 점검에서는 시그널링도 함께 막혔다.
  검증 세션은 `ws://*:*/*`로 고친 사본으로 다시 점검한 뒤 본 실행을 했다. 이전 라운드들의 로컬
  시그널링도 같은 패턴을 썼으므로 P2P 측정값이 아니라 입장·협상 신호에만 shaping이 걸렸을 수 있다.
- 한국어 로캘 대화상자 문구를 분석기가 놓친 것을 고쳐 새 분석 파일을 따로 썼다. 판정은 같다.
