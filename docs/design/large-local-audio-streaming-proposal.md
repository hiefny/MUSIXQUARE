# 대용량 로컬 오디오: 기본 엔진과 구간 디코딩 엔진

- 작성·구현 확인: 2026-09-23
- 상태: `mxqr_beta` 로컬 구현. 프로덕션 배포 전이며 실제 iPhone 검증은 아직 하지 않았다.
- 범위: 기본 AudioBuffer 엔진을 영구적으로 유지하고, 메모리 요구량이 큰 트랙만 별도 엔진으로 준비한다.
- 원격 저장소·main·프로덕션 변경과 전송 용량 제한 완화는 포함하지 않는다.

## 선택 정책

`src/player/large-file-policy.ts`가 트랙 준비 전에 기기별 엔진을 선택한다.
일반 파일은 지금까지의 전체 `decodeAudioData()` → AudioBuffer 경로를 사용한다.
작은 파일까지 새 엔진으로 통일하는 것이 목표가 아니다.

길이·채널·출력 샘플레이트를 얻은 경우 다음 두 값 중 하나라도 기준을
**초과**하면 구간 디코딩을 선택한다. 경계값과 같은 경우에는 기본 엔진을 쓴다.

| 기기 분류                           | 예상 PCM | 해당 트랙 자체의 디코딩 작업 메모리 |
| ----------------------------------- | -------: | ----------------------------------: |
| iOS/iPadOS                          |  192 MiB |                             320 MiB |
| 기타 모바일 또는 메모리가 적은 기기 |  256 MiB |                             448 MiB |
| 일반 데스크톱                       |  384 MiB |                             768 MiB |
| 높은 메모리 용량이 확인된 데스크톱  |  512 MiB |                           1,024 MiB |

PCM 추정에는 기존 메모리 원장의 25% 여유분이 들어간다. 트랙 자체의
작업 메모리는 이 PCM과 해당 원본 파일의 두 표현을 합친 값이다.
이 값은 실제 기기 RAM의 강제 상한이나 재생 가능 보장이 아니다.

다른 트랙의 잔존 PCM, 동시 전송, 회수되지 않은 이전 버퍼를 포함하는
`estimatedWorkingSetBytes`는 엔진 선택에 쓰지 않는다. **큰 트랙 다음의
작은 트랙은 자체 크기를 다시 평가해 기본 엔진으로 돌아온다.**
재생 중에 메모리 원장이 바뀌었다는 이유로 엔진을 교체하지 않는다.

메타데이터가 불확실하면 원장의 임의 64배 확장 추정을 선택 기준으로 쓰지
않는다. 이때는 확인된 원본 크기가 200 MiB를 초과하는 경우만 새 엔진을
선택한다. 길이나 채널 정보를 알 수 없는 작은 압축 파일은 기본 엔진에서
실제 디코딩을 시도하므로, 모든 고메모리 파일을 미리 식별할 수는 없다.

## 구현한 재생 경로

```text
기존 방식으로 확보한 전체 File / Blob
        ↓
Mediabunny BlobSource + 컨테이너/프레임 해석
        ↓
MP3·FLAC·AAC: Worker의 증분 WASM 디코더
PCM: Mediabunny의 구간 PCM 디코더
        ↓
짧은 AudioBuffer 구간
        ↓
기존 AudioContext의 절대 시각에 AudioBufferSourceNode 예약
        ↓
기존 FilePlaybackRoute → 효과·볼륨·비주얼라이저
```

`src/player/large-audio/index.ts`는 엔진이 필요한 때 지연 로딩된다.
MP3는 `mpg123-decoder`, FLAC은 `@wasm-audio-decoders/flac`, AAC는
`@wasm-audio-decoders/aac`를 사용해 Worker에서 프레임 단위로 처리한다.
전체 파일을 WASM 입력으로 복사하거나 곡 전체의 PCM 배열을 만들어 두는
경로는 추가하지 않았다. AAC도 브라우저의 `AudioDecoder` 유무에 의존하지
않고 같은 FAAD2 WASM 디코더를 사용한다.

새 엔진은 MP3·FLAC·아래 AAC 프로필·Mediabunny에 명시된 PCM 코덱을 허용한다. PCM은
16/24/32비트 정수, 32/64비트 실수, 8비트 signed/unsigned와 해당 big-endian
변형, μ-law·A-law다. 실제 회귀 검증 파일은 MP3·FLAC·16비트 PCM WAV다.
Opus·Vorbis는 WebCodecs 디코더가 있더라도 현재 새 엔진에서 허용하지 않는다.
초기 지연·끝 패딩·탐색 후 타임라인 검증이 끝나지 않았기 때문이다.
허용된 코덱도 트랙의 `canDecode()`와 실제 초기 디코딩을 확인한다.
**새 엔진에 필요한 디코더가 없거나 준비가 실패하면
기존 실패 처리를 따르며, 큰 파일을 다시 전체 디코딩하는 자동 fallback은 없다.**
작은 파일의 기존 지원 범위는 기본 엔진이 계속 담당한다.

이번 구현은 AudioWorklet이 아니다. 짧은 AudioBuffer들을 기존
AudioContext 시계에 미리 예약한다. 100 ms 펌프 타이머는 준비한 구간을
공급하는 역할이며 실제 청크 시작을 타이머 호출 시각에 맞추지 않는다.
MP3 탐색은 앞선 0.5초를 디코딩해 프레임 의존성을 준비하고, 시작 지연과
끝 패딩 정보를 트랙 타임라인에 반영한다. 실제 기기 간 출력 일치 정도는
별도 검증 항목이다.

## AAC: 압축 프로필과 파일 포장

AAC-LC와 HE-AAC는 소리를 압축하는 **프로필**이고, M4A는 MP4 기반의
**컨테이너**다. `.aac` 파일은 보통 각 프레임에 헤더를 붙인 ADTS 스트림이다.
같은 AAC-LC 소리를 M4A와 ADTS에 각각 담을 수 있으므로 확장자만으로
디코딩 프로필·출력 채널·시작 지연을 판단하지 않는다. M4A에는 AAC가 아닌
ALAC 등이 들어갈 수도 있으며, 파일 확장자가 새 코덱의 허용 조건은 아니다.

이번 AAC 경로의 범위는 다음과 같다.

| 프로필                    | 처리하는 포장        | 출력에서 확인하는 사항                       |
| ------------------------- | -------------------- | -------------------------------------------- |
| AAC-LC                    | M4A/MP4, ADTS `.aac` | 초기 필터 준비, 실제 채널 순서, 시작·끝 트림 |
| HE-AAC v1 (LC + SBR)      | M4A/MP4, ADTS `.aac` | 코어와 다를 수 있는 실제 출력 샘플레이트     |
| HE-AAC v2 (LC + SBR + PS) | M4A/MP4, ADTS `.aac` | 실제 스테레오 출력과 샘플레이트, 시간 정렬   |

프로필 식별은 LC의 `mp4a.40.2`, HE의 `.5`, HE v2의 `.29`와 LC/HE의
앞자리 0 표기를 허용한다. ADTS 안의 SBR/PS 확장은 헤더가 LC로 표시되어도
실제 디코더 출력을 확인한다. xHE-AAC, Main/LTP/SSR 등 다른 프로필과
ADIF·LOAS/LATM 포장 전체를 지원한다는 뜻은 아니다. 현재 ADTS 파서는
헤더의 채널 구성이 0인 PCE 형식이나 한 ADTS 프레임에 여러 AAC 블록을
넣는 경우를 거부한다. 작은 파일의 기본 엔진 지원 범위는 바꾸지 않았다.

AAC 프레임을 임의 위치에서 하나만 디코딩하면 오류가 없어도 기대한 PCM과
다를 수 있다. AAC 탐색에서는 앞선 1초를 준비하고, 실제 요청 위치 앞의 PCM을
버린다. M4A의 단순 edit list와 iTunes `iTunSMPB` 정보를 반영해 인코더
초기 지연과 끝 패딩 때문에 기본 엔진과 곡 길이·위치가 갈리지 않도록 한다.
모든 AAC에 고정된 2,112샘플 트림을 적용하지 않는다. 검증한 단일 오디오
edit만 허용하며, 앞에 빈 구간을 삽입한 edit 목록이나 여러 구간을 조립한
목록은 명시적으로 실패 처리한다. 빈 선행 구간 파일은 시간 정렬은 맞았지만
곡 끝의 기본 디코더 파형과 차이가 남아 이번 허용 범위에 포함하지 않았다.
끝 위치는 실제 패킷 범위를 넘지 않는다.
[W3C AAC 등록 문서](https://www.w3.org/TR/webcodecs-aac-codec-registration/),
[Apple의 AAC 초기 지연 설명](https://developer.apple.com/library/archive/technotes/tn2258/_index.html)

FAAD2와 브라우저 기본 디코더의 출력이 모든 프로필에서 비트 단위로 같다는
보장은 하지 않는다. 특히 HE-AAC v2의 PS 스테레오 복원에는 파형 차이가 있다.
시간 정렬·곡 길이와 탐색 후 동일 디코더의 출력 일관성을 각각 검증한다.
LC 모노에서는 FAAD2가 동일한 두 PCM 평면을 반환할 수 있어 채널별 실제
출력을 확인한다. 이를 HE-AAC v2의 서로 다른 스테레오 평면을 하나로 합치는
처리와 혼동하지 않는다. 다채널 AAC는 FAAD2의 채널 순서를 Web Audio 순서로
바꾸며, 실제 5.1 파일을 회귀 대상으로 포함한다.

`@wasm-audio-decoders/aac` 0.0.1을 사용하는 로컬 베타 구현이다. 아래의
검증 파일을 통과한 것과 모든 AAC 파일·실제 iPhone에서 검증한 것은 구분한다.

## 메모리와 지연의 범위

현재 설정은 원본 읽기 캐시 2 MiB, 초기 준비 목표 1초 또는 PCM 2 MiB,
재생 선행 예약 목표 8초 및 PCM 16 MiB다. 준비는 청크 경계에서 끝난다.
이는 브라우저 전체 메모리의 엄격한 16 MiB 상한이 아니다. 다음 청크,
파서·디코더 내부 큐와 WASM 메모리, 효과 처리, 원본 파일 등이 별도로 있다.
한 출력 청크가 16 MiB보다 크면 정상 청크로 예약하지 않고 실패 처리한다.

예를 들어 48 kHz·스테레오·Float32 PCM은 1시간에 약 1,318 MiB지만
10초는 약 3.66 MiB다. 구간 디코딩의 목적은 이 PCM의 장기 보관량을 줄이는 것이다.

**전체 압축 파일의 수신과 보관은 변경하지 않았다.** P2P와 원격 경로에서
확보한 File/Blob은 여전히 RAM에 남는다. 새 엔진이 전체 파일을 받은 뒤
일부를 디코딩한다고 해서 수신 자체가 네트워크 스트리밍이 되지는 않는다.

먼 위치로 seek하면 파서와 디코더가 그 위치를 준비해야 하므로 기본 엔진보다
로딩이 생길 수 있다. 준비 시간은 고정 추가 대기시간이 아니다. 재생할 구간의
준비가 끝나면 기존 시작 시각·수동 싱크 보정으로 출력을 예약한다.

ADTS `.aac`에는 M4A의 샘플 테이블 같은 탐색 인덱스가 없으므로 처음에
프레임 헤더를 순회해 길이와 위치를 조사한다. 긴 파일에서는 이 과정의 로딩과
프레임 수에 비례하는 파서 메타데이터가 추가된다. PCM 보관량을 제한한다고
초기 인덱스 작성 시간이나 전체 브라우저 메모리가 상수가 되지는 않는다.

## 동기화와 수명 계약

공통 `FilePlaybackResource`는 AudioBuffer 또는 `LargeAudioTrack`이다.
새 트랙 계약은 길이·샘플레이트·채널 수·보유 PCM 크기와
`prepare(position, signal)`, `createPlayback(...)`, `dispose()`를 제공한다.

- 방장, 게스트의 수신 완료, 프리로드 승격, 데모 파일 준비가 같은 선택 경로를 쓴다.
- 기존 공유 시계, 절대 시작 시각, 출력 지연 보정, 기기별 수동 싱크를 유지한다.
  참가 기기마다 엔진이 달라도 별도의 방 타임라인은 만들지 않는다.
- 곡 변경이나 더 최근의 재생 의도로 소유권이 바뀌면 이전 준비·출력 결과를 폐기한다.
  취소된 Worker 결과가 도착해도 새 곡을 덮어쓰지 않는다.
- 새 엔진은 참조 소유권이 마지막으로 해제될 때 iterator·출력·입력을 정리한다.
  이전 곡의 준비 Promise나 게스트 복구 경로도 같은 수명 계약을 따른다.
- 늦게 도착한 PCM을 뒤로 밀어 재생하지 않고 지난 샘플을 건너뛰어 원래 시각을 따른다.
  청크 하나의 종료나 일시적인 버퍼 부족은 곡 종료가 아니다.
- Worker 오류·메시지 오류·응답 시간 초과는 준비 실패로 전달한다.
  미완료 요청을 무기한 기다리지 않는다.

## 안내

초기 준비에 **성공한 경우에만**, 그 기기의 시스템 채팅에 다음 안내를 표시한다.

> 이 트랙은 매우 커서 사용 중 지연이 발생할 수 있어요.

키는 `chat.large_track_playback_system_message`이며 42개 언어에 있다.
숫자로 예상 메모리를 안내하던 문구는 복구하지 않는다. 안내는 방 전체로
전송하지 않고 일반방·PRO에서 해당 큐 항목당 세션 내 한 번 표시한다.
큐 항목이 없는 데모 파일은 Blob identity로 중복을 막는다. 초기 준비가
실패하거나 취소된 트랙에는 이 안내를 표시하지 않는다.

새 엔진 경로에서는 기존의 별도 200 MiB 용량 경고를 함께 표시하지 않는다.
기본 엔진 경로의 기존 일반방 용량 안내 조건은 유지한다.

보장은 아니다. Worker는 번들에 포함된 디코더 코드로 Blob URL을 만들고,
WASM을 브라우저 내에서 실행한다. 미디어 파일을 코드로 평가하거나 원격
서비스에 보내 디코딩하지 않는다. 기존 CSP의 `worker-src 'self' blob:`와
`'wasm-unsafe-eval'` 범위에서 동작하며 새 외부 출처나 JavaScript
`'unsafe-eval'` 권한을 요구하지 않는다.

## 검증 범위와 남은 실기 확인

단위 검증에는 선택 경계, 작은 곡→큰 곡→작은 곡, 방장/게스트/프리로드/데모의
교체, 준비 취소·실패, 리소스 정리와 안내 시점이 포함된다.
2026-09-23 로컬 검증 결과는 다음과 같다.

- 최종 전체 단위 테스트: 450개 파일, 9,198개 통과, 기존 1개 건너뜀.
  AAC 프로필·컨테이너·트림·Worker 수명, MP3 헤더 경계와 수동 싱크 준비
  실패 시 기존 출력 유지도 포함한다.
- 이번 AAC 확장 후 관련 Chromium 브라우저 테스트 23개: MP3·M4A·ADTS의
  호스트·게스트 작은 곡→큰 곡→작은 곡 및 서로 다른 엔진 조합 6개,
  AAC 검증 15개, 기존 MP3·FLAC·WAV 검증 2개를 통과했다.
- AAC의 정상 합성 파일 13개를 시작·소수점 탐색·중간·끝에서 비교해
  총 120개의 채널별 PCM 결과를 확인했다. 모노·스테레오·5.1과 ISO/iTunes
  트림, 명시적·암묵적 HE 프로필을 포함한다. 테스트에서 시간 정렬 차이는
  1샘플 이내였으며, HE v2는 PS 파형 차이와 같은 디코더의 탐색 복원을
  구분해 검사했다. 브라우저의 `AudioDecoder`를 끈 상태에서도 통과했다.
- 실제 MP3·FLAC·WAV의 기존 디코더 대비 시작·중간·끝 정렬도
  1샘플 이내였다. 이는 해당 테스트 파일과 Chromium의 결과다.
- 15분 WAV와 900초를 넘는 ADTS의 구간 준비, 취소, 10분 시계 점프 후
  위치 복구와 제한된 PCM 보관을 확인했다. 실제로 10분 동안 기기를
  백그라운드에 둔 실험은 아니다. 검증되지 않은 선행 빈 edit 파일의 거절과
  전체 디코딩 fallback 부재도 확인했다.
- 전체 타입 검사·린트, 프로덕션 빌드와 보안·초기 전송량·서비스 워커 자산 검사를
  통과했다. 원격 CI나 프로덕션 배포는 실행하지 않았다.

브라우저 테스트 결과와 실제 iPhone 결과를 혼동하지 않는다.
**현재 문서의 구현 확인만으로 iPhone Safari/PWA 실기 검증이 완료된 것은 아니다.**

공개 적용 전에 실제 iPhone Safari/PWA와 Android·Windows가 섞인 방에서 다음을
확인한다: 시작, 연속 seek, 이전 곡, 곡 끝 반복, 중도 참여, 프리로드 순서 변경,
큰 수동 싱크, 네트워크 단절·재합류, 잠금·백그라운드 복귀, 장시간 메모리 추이.
MP3·AAC의 native/WASM 간 시작·끝 위치와 FLAC 다채널 파일도 포함한다.

원본 구간만 수신하는 네트워크 프로토콜, OPFS, SharedArrayBuffer 기반 출력,
모든 파일의 엔진 통일은 이번 구현에 포함하지 않는다. Standard 원격과 PRO의
파일당 200 MiB 제한은 그대로다. P2P의 안전한 크기·청크 무결성 제한도 유지한다.
압축 파일 메모리까지 줄이는 수신 개선은
[RAM-only 정책](browser-media-storage-policy.md)과 별도로 검증할 작업이다.
