| 기준 SHA  | `cab7cb73` (main, 9.0.2 머지본)                                                                 |

| 함께 싣기 | 미배포 9.0.2(G5, [보고서](pro-direct-receive-deadline-2026-10-22.md))를 함께 배포(오너 결정)    |

## 왜 고쳤나

- **G6.** PRO SFU 구독이 실패하면 재시도 정리가 코디네이터 구독 키를 지웠다. 그래서
  백오프 재시도마다 같은 공유인데도 수신 대기를 내렸다가(이전 트랙 표시 복원, 재생 주인
  해제, 정지) 다시 시작했다. 재시작은 `stopAllMedia`, 받는 파일 전송·원격 공유 대기
  취소, `system-audio:host-started`를 매번(최대 30초마다) 다시 돌렸다. 9.0.1 보고서에서
  후속 후보로 남긴 항목이다.
- **G7.** 오디오 컨텍스트 복구에서 사용자의 탭(대화상자 또는 Media Session 재생)으로
  시작한 재개가 750ms 안에 끝나지 않으면, 호출한 쪽은 이미 "안 됨"을 받고 떠난 뒤였다.
  늦게 끝난 재개는 시계 확인 단계로 넘어가지만 그 확인을 맡을 주인이 없었다. 원인이
  시계 멈춤이면 새로고침 전까지 복구되지 않았고, 잠금 화면에서 누른 재생이 숨김 상태로
  확인되는 경우는 느린 재개 없이도 같은 상태에 갇혔다. 블루투스 경로 전환처럼 재개가
  느린 기기에서 생길 수 있다.

두 수정 모두 [자원 소유권 장부](resource-ownership-registry.md)의 원칙(시도마다 마감
주인 하나, 기존 주인에 합치기)을 따른다.

## 바뀐 것

- **G6.** 재시도 정리가 구독 키를 유지한다. 같은 발행의 재시도는 이미 가진 수신 대기
  안에서 다시 구독한다. 새 발행이나 라이브가 아닌 상태, 로컬 소유자, 방 전환, 서비스
  초기화는 지금처럼 수신 대기를 내린다. SFU 재시도는 SFU 경로에서만 일어나고 구독 키에
  발행 종류가 들어가므로, 9.0.2의 LAN-direct 마감과 겹치지 않는다.
- **G7.** 기존 주인(`src/audio/context-recovery.ts`)만 고쳤다. 새 타이머·플래그·단계는
  없다.
  - 제스처 재개가 호출 쪽 마감 뒤에 끝나면, 주인이 이미 가진 자동 시계 확인을 예약한다.
    마감 안에 끝나면 지금처럼 호출 쪽이 확인한다.
  - 화면이 다시 보일 때, 시계 확인 대기 중인 시도는 원인과 상관없이 확인을 돈다. 자동
    재개 자체는 지금처럼 상태 중단 원인에만 하고, 시계 멈춤 원인은 사용자의 탭으로만
    재개한다.
  - 사용자가 그사이 일시정지했으면 확인이 시도를 거두고 재합류하지 않는다(사용자 동작
    우선). 시계가 아직 멈춰 있으면 완료로 치지 않고 다시 준비해 안내를 다시 띄운다.
  - 마감 뒤 회복의 재합류는 대화상자가 아니라 주인이 `audio-context-recovered`로 낸다.
- **테스트 도구(C1).** 실제 수명 순서를 흉내 내는 AudioContext 가짜와 오디오 컨텍스트
  주인들의 현재 동작을 고정하는 테스트를 더했다. G7의 재현과 검증이 이 도구 위에 있다.
- 장부 RO-01의 마감 주인 설명과 고정 테스트를 맞췄다.

## 그대로 둔 것

- 시계 멈춤 원인에서 재개 약속이 끝나기 전에 늦은 `running` 상태 이벤트가 먼저 오면,
  두 번째 탭을 요구하거나(이벤트 순서에 따라) 시계 확인 없이 정리되는 경로가 남는다.
  테스트에 "Known gap (Phase 7)"로 고정했고, 상태 이벤트 처리를 하나로 모으는 Phase 7
  일이다.
- 재생 요청 쪽이 주인의 180ms 확인 도중 컨텍스트를 멈추면 시계 멈춤 시도가 다시 재개
  대기로 돌아간다. 9.0.3 전부터 있던 두 주인 문제이고, 이 수정으로 닿는 경로가 하나
  늘었다.
- 잠금 해제용 Media Session 재생이 750ms 뒤에 끝나면, 그 재생이 내던 자체 재합류는
  나오지 않는다. 수정 전에도 그 의도는 사라졌다.

## 호환성

통신 형식, 저장 레코드, D1, 비밀값, 바인딩 변경 없음. 브라우저 앱과 App Worker의 관리자
버전 표기만 바뀌므로 target `app`이다.

## 검증과 한계

- **G6 재현:** 새 테스트 2개가 9.0.1 소스(`c08b6c39`)에서 실패했다(3분 재시도 동안
  `stopAllMedia`와 시작 알림 9번, 주인 해제 8번). 수정 후 각각 1번, 0번이다. 새 발행으로
  옮기면 정확히 한 번 더 시작한다. 9.0.2 위로 옮긴 뒤에도 통과한다.
- **G7 재현:** 수정 전 소스에서 오디오 컨텍스트 소유 테스트 65개 중 14개가 실패했다

  65개 통과, 이 모듈들을 가져오는 테스트 파일 60개(2,044개) 통과다.

  타당성·보정 관점이 2라운드에서 승인했다. G7은 세 관점이 1라운드에서 승인했다.
- 전체 검사(`6212a818`, 로컬): 타입 검사, lint, 서식, 빌드 통과. 단위 테스트 620개 파일
  13,994개 통과. 가드(dead-exports, bus-pairing, import-graph, lifecycle-writes,
  release-identity, sw-cache-version, resource-ownership) 통과. 핵심 브라우저 검사 59개
  통과(Chromium). 로컬 결과는 정확한 main SHA 배포 후보를 대신하지 않는다.
- 실기기는 확인하지 않았다. PRO 방에서 SFU 구독이 계속 실패할 때 재생 정지·알림이
  한 번만 나오는지, iOS에서 블루투스·경로 전환으로 750ms보다 느린 재개가 회복되는지가
  실기기 확인 항목이다.
