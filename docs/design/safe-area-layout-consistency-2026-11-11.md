  회전이 아니라 이미 있는 반응형 배치를 따른다. 처음에는 검증과 PR까지만 맡겼다.

- **2026-11-11, 배포 허가(9.0.42 열차 때의 결정):** 배포는 모두 허가했다. 자동 관문(PR 검사, 자동 코드 리뷰, 병합, exact-main CI, 최소 앱 빌드
  확인)이 통과하면 업데이트 창이 뜨는 열차도 따로 묻지 않고 dispatch한다. 기기 확인은 게이트가 아니다.

### 3.2 바뀐 코드

- `index.html`: 헤더 안에 `.header-safe-content` 하나를 두고 로고, 로딩 문구, 계정·도움말 버튼을 그 안으로 옮겼다. 진행 표시 배경은 헤더의 직계로
  남아 가장자리까지 채운다.
- `css/style.css`: 물리적 가장자리 토큰 `--safe-physical-left`, `--safe-physical-right`를 더했다(`--safe-left`, `--safe-right`는 글 방향의 시작·끝).
  헤더의 안쪽 여백을 그 경계로 옮기고, 사이드바 배치의 본문 영역·미디어 고르기·YouTube 입력 화면을 `top`과 높이로 안전 영역만큼 들였다. 사이드바의
  탭 줄은 안전 영역을 뺀 높이의 가운데에 놓는다. 대화상자 바깥 여백은 `max(여백, 안전 영역)`이고 최대 높이는 `--dialog-available-height` 하나다.
  세로 iPad PWA만 보정하던 `html.ios-standalone` 블록을 지웠다. 시작 화면의 두 칸에 위아래 안전 영역을 넣었다.
- `css/desktop.css`: 넓은 배치의 `body`가 안전 영역 토큰을 확대 비율로 한 번 환산한다. 재생 칸, 설정 칸, 미디어 고르기에 아래 안전 영역을 넣었다.
- `css/rtl.css`: 오른쪽에서 왼쪽 언어의 시작·끝 토큰과 물리 토큰을 따로 정하고, 로딩 문구의 좌우를 명시한다(옛 TV 브라우저용 CSS 낮추기가 논리
  속성을 `:dir()`로 바꾸지 않도록).
- `src/ui/chat.ts`: `getChatDrawerLiveSafeTopInset`이 화면 높이를 넘은 만큼을 위 여백에 더한다(한 줄).

  밑으로 들어감). 이제는 배경만 화면 위로 늘어나고 머리 부분은 제자리다(1024x768, 위 24에서 300px 당길 때 머리의 위가 24 → 2.7이던 것이 24 그대로).
  안전 영역이 없는 기기에서도 같아서, 끝까지 올린 채팅에서는 당김이 눈에 보이지 않는다. 절반 높이에서의 당김은 그대로다. 이 PR의 의도대로다.
- **사이드바 배치의 본문 끝:** 본문 영역이 홈 표시줄 위에서 끝나므로 스크롤하는 내용이 그 선에서 잘린다(휴대폰 배치는 내용이 아래 탭 줄 밑으로
  지나간다). 의도대로다.
- **가로 휴대폰의 시작 화면:** 오른쪽 칸의 폭 320px은 그대로이고 노치 쪽 안전 영역을 그 안에서 뺀다. 버튼이 47px 좁아진다(264 → 217).

## 4. 검토에서 찾은 결함: 재생 탭이 아닌 탭의 영역이 화면 밖으로 밀림 (의도한 변경, [화면 바뀜])

### 4.1 무엇이 잘못됐나

PR 머리 `7e1e5e2c`에서, 사이드바 배치이고 위 안전 영역이 있는 기기(iPad PWA의 가로·세로)의 플레이리스트·연결·도움말·설정 탭은 본문 영역이 위
안전 영역만큼 내려가기만 하고 높이는 화면 전체였다. 그래서 영역이 화면 아래로 24px 넘쳤고 안전한 아래 끝에서는 44px이 가려졌다(1024x768, 위 24,
아래 20에서 [0, 24, 824, 768]. 재생 탭은 [0, 24, 824, 724]로 맞았다). 플레이리스트의 맨 아래 줄과 현재 트랙으로 가기 버튼(아래 끝 786)이 화면
밖이었고, 문서 전체가 24px 스크롤될 수 있게 되어 포커스 이동 같은 스크롤이 앱을 상태 표시줄 밑으로 밀 수 있었다. 가로 휴대폰에서는 그 탭들이
홈 표시줄 밑까지 갔다(21px).

### 4.2 원인

커스텀 스크롤 막대(`src/ui/custom-scrollbar.ts`)는 스크롤 영역을 맡을 때 그 부모가 `position: static`이면 부모에 인라인 `position: relative`를
쓴다. 탭 영역은 보이는 동안에만(`.tab-content.active`) 자리를 잡는 규칙이 있었고, 앱이 뜰 때 숨겨져 있는 네 탭은 그 순간 `static`이라 인라인
값을 받았다. 인라인 값이 사이드바 배치의 `position: fixed`를 이겨서, 네 탭은 운영에서도 고정이 아니라 `body` 안의 흐름 요소였다. 왼쪽에서 오른쪽
언어에서는 우연히 같은 자리라 드러나지 않다가, 이 PR이 `top: var(--safe-top)`을 더하자 그 값이 상대 이동이 되어 영역을 밀어냈다. fixture 명세는
런타임을 돌리지 않아 이 인라인 값을 보지 못했다.

### 4.3 고침

`css/style.css`의 바탕 규칙 `.tab-content`에 `position: relative` 한 줄을 더했다(`430a3b09`). 탭 영역이 숨겨져 있을 때도 자리를 잡은 요소라 커스텀
스크롤 막대가 인라인 값을 쓰지 않고, 사이드바 배치의 `position: fixed`가 다섯 탭 모두에 그대로 적용된다. 휴대폰 배치(`.tab-content.active`가
`relative`)와 넓은 배치(다섯 칸 모두 `relative`를 명시)는 계산값이 같다.

## 12. 하지 않은 것과 확인하지 않은 것

- 실기기(iPad, iPhone, Android)에서 보지 않았다. 안전 영역은 fixture의 주입값과 Chromium의 DevTools 흉내다. 실제 `env()` 값, 회전하는 동안의 배치,
  화면 키보드, 브라우저 자체 전체 화면(`:fullscreen`), iOS의 상태 표시줄 모양은 확인하지 못했다.
- WebKit에서는 fixture 명세와 저장소의 WebKit 레인만 돌았다. 실제 방의 새 명세는 DevTools 명령을 써서 Chromium에서만 돈다.
- 섞인 버전의 방은 따로 시험하지 않았다(§7).
- 배포 뒤 브라우저와 기기 확인은 기록 PR이 적는다. 로컬 결과는 exact-main-SHA 후보를 대신하지 않는다.
