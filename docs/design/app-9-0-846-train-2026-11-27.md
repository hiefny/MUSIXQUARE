## 1. 오너 결정

오너의 말은 옮기지 않고 뜻만 적는다.

- 2026-11-27 9.0.845 배포 뒤 `/status`의 Website and app과 Device connections 줄이 대부분 Not checked로 보였다. 서버 줄(`rooms`·`pro`)은
  02:30 KST 칸부터 15분마다 통과했지만, 브라우저 줄(`website`·`connection`)은 02:15 KST의 손 실행 한 번과 09:45 KST에 시작한 일정 실행 한
  번(16:37 UTC 일정 몫, 약 8시간 늦음)만 적혔다. 오너가 이것을 지금 고치기로 했다.
- 같은 날 오너가 방 `000001`의 Developer API 키를 No expiry로 둘 수 있게 하자고 했다. 그 방은 릴리스 smoke 방이다: target `all`·`developer-api`
  릴리스의 'Smoke Developer API Worker'가 GitHub `production` 환경 비밀 `MXQR_DEVELOPER_API_SMOKE_KEY`로 그 방에 인증하고, 관리자 키는
  길어야 365일이라 키가 끝나면 `all` 릴리스가 다섯 Worker를 배포한 뒤 그 smoke에서 실패한다.
- 고치는 방법(App 분 cron의 dispatch, 저장소 하나·Actions 쓰기만의 토큰, 대비로 남는 일정)은 이 열차의 설계다. 토큰을 만들어 App 비밀로 두는
  일과 배포 뒤 smoke 키를 바꾸는 일은 오너가 한다(§6, 릴리스 기록 §2).

## 3. 사용자에게 바뀌는 것

### 3.1 관리자 화면과 `/status` [화면 바뀜]

1. **관리자 Developer API 키 폼(방 `000001`만)**: `/admin`에서 PRO 방 `000001`(릴리스 smoke 방)을 펼치면 Developer API 칸의 'Expires'
   선택(30 days, 90 days(기본), 180 days, 365 days) 끝에 'No expiry'가 더해진다. 다른 방의 폼에는 없다. 'No expiry'로 발급한 키는 키
   목록에서 'Expires'와 날짜 대신 'No expiry'로 보인다(만든 때와 끝나는 때의 차가 정확히 36,525일인 키). 서버(App Worker의 키 발급)는 No
   expiry를 기존 `days` 칸의 36,525로 받되 방 `000001`에서만 받고, 다른 방의 36,525와 365일을 넘는 다른 수명은 `INVALID_REQUEST`(400)로
   거절한다. Developer API 스키마는 만료가 만든 때보다 늦어야 하고 모든 키 검사가 지난 만료를 거절하므로, No expiry도 만료가 있는 100년
   (365.25일 × 100) 키다(2026년에 만든 키는 2126년에 끝남). 다른 키처럼 취소되고 방의 활성 키 셋에 든다. 운영자 CLI는 1 ~ 365일
   그대로이고, Developer API Worker와 스키마는 바뀌지 않았다.
2. **`/status`의 Website and app·Device connections 줄**: 페이지 모양과 문구는 그대로이고, 두 줄이 15분마다 새 칸으로 채워진다. 9.0.845 배포
   뒤에는 GitHub 일정 실행이 8 ~ 10.5시간 늦게 와서 두 줄이 대부분 Not checked였다(§1). 이 열차 뒤에는 App이 :07·:22·:37·:52(UTC)에 감시
   실행을 직접 시작하고 그 실행이 몇 초 안에 시작되므로, 두 줄도 서버 줄처럼 Normal(또는 실제 상태)로 보인다. 결과는 실행이 시작된 브라우저
   칸에 적히고, 줄의 규칙(두 번 잇달아 실패해야 Problem, 30분 동안 끝난 점검이 없으면 Not checked)은 그대로다.

### 3.2 App의 감시 시작(dispatch) [화면 그대로]

1. **언제**: App Worker의 분 cron(`* * * * *`, 9.0.845에도 있던 trigger)에서 `scheduled()`가 이벤트의 `scheduledTime`이 UTC 7, 22, 37,
   52분일 때(`isStatusDispatchMinute`, `STATUS_BROWSER_CHECK_MINUTES`) `dispatchStatusMonitor`를 `ctx.waitUntil`에 넘긴다. 점검 모드 읽기와
   그 return 앞이고, 분 cron의 다른 일처럼 기다리지 않는다. 점검 모드에도 보낸다: 감시 job이 점검 모드를 스스로 읽어 두 줄을 `m`으로 적는다.
   null cron이나 숫자 `scheduledTime`이 없는 이벤트는 보내지 않는다.
2. **무엇을**: `POST https://api.github.com/repos/hiefny/MUSIXQUARE/actions/workflows/status-monitor.yml/dispatches`, 몸통 `{"ref":"main"}`
   (입력 없음), 머리 `Authorization: Bearer`와 비밀, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`,
   `User-Agent: MUSIXQUARE-status-dispatcher`(사람 이름 없음). redirect를 따르지 않아 토큰은 `api.github.com`에만 가고, 답은 상태와 속도 제한
   머리 둘(`x-ratelimit-remaining`, `retry-after`)만 읽으며 몸통은 읽지 않고 버린다. GitHub는 204(또는 실행 정보와 200)로 받고, 만들어진
   실행은 몇 초 안에 시작한다. 그 실행의 OIDC 토큰은 사건 `workflow_dispatch`를 담는다. 두 OIDC 경로는 9.0.845부터 `main`의 `schedule`과
   `workflow_dispatch`를 받으므로 정책은 바뀌지 않았다(갈래 값만 계약의 `STATUS_MONITOR_BRANCH`에서 읽음). 감시 job은 토큰을 보지 못한다.
3. **한도**: 요청 하나를 15초(`STATUS_DISPATCH_TIMEOUT_MS`)에 끊고(GitHub는 10초 넘게 처리한 요청을 스스로 5xx로 끝내므로 이 한도는 걸린
   연결만 끊음) 타이머는 모든 경로에서 지운다. 한 분 안에서 다시 보내지 않고 다음 점검 분이 다시 시도이며, 거절(reject)하지 않는다. 한
   시간에 네 번이다.
4. **로그**: 실행을 시작하지 못한 dispatch는 경고 하나 `{ diagnostic: 'status_dispatch', outcome, httpStatus }`만 남긴다(토큰, 머리, 몸통
   없음). outcome은 `unconfigured`(비밀이 없거나 출력 가능한 토큰 하나가 아님, 요청을 보내지 않고 isolate마다 한 번만), `unauthorized`(401,
   토큰이 틀리거나 끝나거나 취소됨), `forbidden`(403, Actions 쓰기 권한 없음), `not_found`(404, 저장소에 닿지 못하거나 workflow 파일이 없음),
   `unprocessable`(422, workflow가 꺼졌거나 `workflow_dispatch`가 없거나 `main`이 없음), `rate_limited`(429, 또는 `x-ratelimit-remaining: 0`이나
   `retry-after`가 있는 403), `failed`(5xx, 답 없음, 15초 안에 답 없음), `unexpected`(그 밖, redirect 포함)다. 운영자 설명은
   [admin dashboard operations](../../cloudflare/admin-dashboard-ops.md#status-page)에 있다.
5. **비밀과 토큰**: App Worker 비밀 `MXQR_STATUS_MONITOR_DISPATCH_TOKEN`. 저장소 주인의 fine-grained personal access token으로, Repository
   access는 `hiefny/MUSIXQUARE` 하나, 저장소 권한은 Actions: Read and write 하나(Metadata: Read-only는 GitHub가 붙임), 만료일은 1년 이내(날짜는
   오너의 비공개 메모에 둠)다. `cloudflare/ops-drift.contract.json`과 `cloudflare/config-drift-ops.md`가 이름을 App 비밀 목록에 넣어 App 비밀
   이름은 18개에서 19개가 됐다. 두는 방법과 다루는 규칙은
   [configuration reference](../configuration-reference.md#mxqr_status_monitor_dispatch_token)에 있다.
6. **일정은 대비로**: `status-monitor.yml`의 `schedule`(`7,22,37,52 * * * *`)과 `workflow_dispatch`(입력 없음)는 그대로이고 주석만
   바뀌었다. 늦게 온 일정 실행은 자기가 시작한 칸의 실제 점검 하나가 되고(한 칸에서는 늦은 확인 시각이 이김), workflow의 동시 실행 그룹이
   감시를 한 번에 하나만 돌리므로(진행 중인 실행은 취소하지 않음) 해가 없다. 손 실행도 그대로다.
7. **문서와 레지스트리**: RO-57이 시작 쪽(App 분 cron이 시작, 일정이 대비, 손 실행), dispatch 한도, parity 시험 'starts the browser job from
   the App minute cron at the browser minutes, on a workflow GitHub can dispatch'를 적는다. `docs/hotfix-procedure.md`에 새 절 '### Worker
   secret changes'(비밀 변경이 `git:` 출처 없는 버전을 배포하는 것과 릴리스와의 순서)와 되돌리기 메모가, `cloudflare/admin-dashboard-ops.md`에
   'Starting the browser checks'(경고 분류 포함)와 '## Developer API key lifetimes'(오너의 smoke 키 교체 세 단계)가 생겼다.

## 6. 되돌리기와 남긴 한계

- 기본 되돌리기는 `9.0.847 / v847` 이상으로 앞으로 고치기다. 이 릴리스의 checkpoint는 오너가 비밀을 둔 뒤의 App 버전(9.0.845 코드에 비밀만
  더한 비밀 변경 버전, `git:` 메시지 없음)을 검증되지 않은 기준선으로 잡는다. 그래서 App을 배포한 뒤 실패한 `app` 실행은 자동 복구가 App을
  되돌리지 않고 후보를 둔다(앞으로 고치기, [Worker secret changes](../hotfix-procedure.md#worker-secret-changes)). 급할 때의 손 되돌리기 대상은
  그 비밀 변경 버전이다.
- **비밀은 머지와 릴리스 dispatch 사이에 둔다**:
  1. Worker 비밀을 두거나 바꾸거나 지우면 Cloudflare가 그 자리에서 비밀만 바뀐 새 App 버전을 100%로 배포하고, 그 배포에는 `git:<SHA>`
     메시지가 없다(Wrangler의 Secret Change, 릴리스 이력의 2026-10-20 `YOUTUBE_API_KEY` 행과 같은 종류). 승인된 릴리스가 App을 다시 배포할
     때까지 App 운영 배포는 Git 출처를 증명하지 못한다: App을 빼고 고른 부분 릴리스는 호환 판정에서 멈추고, App의 로컬 긴급 배포도 멈추며,
     다음 App 릴리스가 실패하면 자동 복구가 App을 되돌리지 않는다. 그 창을 가장 짧게 하려고 머지 뒤, dispatch 바로 앞에 둔다. 릴리스가 도는
     동안에는 바꾸지 않는다(checkpoint와 소유 확인이 자기가 만들지 않은 배포를 만남).
  2. 이 열차가 `cloudflare/ops-drift.contract.json`에 이름을 넣으므로, 머지 뒤 비밀이 없는 동안 Operations Drift Audit(매일 03:37 UTC 일정, 늦게
     올 수 있음)은 그 이름을 missing으로 보고한다. 머지 전에 두면 거꾸로 unexpected다.
  3. 운영 9.0.845는 이 비밀을 읽지 않으므로 머지와 릴리스 사이에 두어도 동작은 그대로다. dispatch 전에
     `npm run wrangler -- deployments status --config cloudflare/wrangler.app.toml --json`을 1분 간격으로 두 번 읽어 둘 다 비밀 변경 버전을
     답하는지 본다(목록이 늦을 수 있음). 릴리스가 `git:` 메시지를 되돌리고, 비밀 변경은 릴리스 이력에 자기 행을 받는다.
  4. 비밀 없이 릴리스되면 App은 요청을 보내지 않고 isolate마다 `unconfigured` 경고를 한 번 남기며, 브라우저 줄은 늦은 일정에만 기댄다. Drift
     Audit은 그 이름을 missing으로 보고한다. 비밀을 나중에 두는 것도 비밀 변경이라 위 1의 출처 규칙을 따른다.
- **되돌려도 비밀은 남는다**: Worker 비밀은 뒤 배포에도 남는다. 이 열차를 되돌리는 변경(revert)이 이름을 `cloudflare/ops-drift.contract.json`과
  `cloudflare/config-drift-ops.md`에서 빼면 Drift Audit이 그 이름을 unexpected로 보고하므로, 그 머지와 릴리스 사이에 비밀을 지우거나
  (`secret delete`도 비밀 변경), 이름을 두 파일과 `src/core/__tests__/ops-drift-audit.test.ts`에 남겼다가 나중에 같은 방식으로 뺀다. 비밀을
  아주 지우면 GitHub에서 토큰도 취소한다([Rollback](../hotfix-procedure.md#rollback)). CLI 되돌리기가 비밀 목록을 어떻게 남기는지는 이
  열차에서 재지 않았으므로, 되돌린 뒤에는 Drift Audit으로 App 비밀 이름을 확인한다.
- **경계**:
  1. App을 9.0.845로 되돌리면 그 코드는 비밀을 읽지 않고 감시를 시작하지 않는다. 브라우저 줄은 다시 늦은 일정에만 기대어 대부분 Not checked가
     되고, 서버 줄은 그대로다. 9.0.844 이하로 내릴 때는 [9.0.845 보고서 §6](app-9-0-845-train-2026-11-26.md#6-되돌리기와-남긴-한계)의 경계를
     따른다.
  2. 이미 발급한 No expiry 키는 App을 되돌려도 Developer API가 계속 받는다(Worker와 스키마 그대로, 만료 2126년). 옛 관리자 화면은 그 키를
     'Expires'와 2126년 날짜로 보이고 No expiry를 새로 내지 못한다. 끝내려면 관리자에서 취소한다.
  3. 새 D1, 바인딩, KV namespace, Durable Object 클래스, cron trigger, 계약 표지는 없다. 브라우저 점검을 멈추는 스위치는 GitHub UI에서
     `status-monitor.yml`을 끄는 것이다: 일정이 멈추고 GitHub가 App의 dispatch를 422로 거절해 App이 시간에 네 번 `unprocessable` 경고를
     남긴다. 그 요청까지 멈추려면 비밀을 지운다(위 출처 규칙).
- **토큰은 App Worker 비밀에만 둔다**: GitHub는 토큰을 workflow 하나로 묶지 못한다. Actions 쓰기 권한이면 이 저장소에서 `workflow_dispatch`가
  있는 모든 workflow(`Production Release`, `App Build Floor` 포함)를 어떤 입력으로든 시작하고, 실행을 취소·재실행·삭제하고 로그를 지우며,
  workflow를 끄고 켤 수 있다. 그래서 GitHub Actions 비밀·변수·환경, `.env` 파일, 셸 프로필, 명령 인자, 이슈, 채팅에 두지 않는다. 감시 job은
  토큰을 보지 못한다. 새어 나갔을 수 있으면 GitHub에서 먼저 취소하고(그동안 각 dispatch는 `unauthorized`, 일정은 늦게나마 돎) 새 토큰을
  둔다([configuration reference](../configuration-reference.md#mxqr_status_monitor_dispatch_token)).
- **토큰이 끝나면**: 만료일(1년 이내, 오너의 비공개 메모)이 지나면 모든 dispatch가 `unauthorized`(401) 경고를 남기고 브라우저 줄은 늦은 일정에만
  기댄다. 만료 전에 새 토큰으로 바꾸고, 바꾸기도 Worker 비밀 변경이라 App을 포함한 릴리스 바로 앞에 한다.
- **일정은 대비로 남는다**: `status-monitor.yml`의 `schedule`(`7,22,37,52 * * * *`)은 그대로다. 늦게 온 일정 실행은 자기가 시작한 칸의 실제
  점검 하나가 되고(한 칸에서는 늦은 확인 시각이 이김), workflow의 동시 실행 그룹이 감시를 한 번에 하나만 돌리므로(진행 중인 실행은 취소하지
  않음) 해가 없다.
- **남긴 한계**:
  1. GitHub 일정 지연(7일 동안 일정 실행 111번이 8 ~ 10.5시간 늦음, 2026-08-27 전에는 29 ~ 46분)은 이 열차가 고치지 않고 dispatch로 비켜
     간다. dispatch한 실행이 몇 초 안에 시작한다는 것은 배포 뒤 첫 실행들로 확인한다(§4.2).
  2. dispatch는 한 분에 한 번이고 다시 보내지 않는다. GitHub가 5xx를 주거나 15초 안에 답하지 않으면 그 칸은 비고 다음 점검 분이 다시
     시도하며, 늦게 온 일정 실행이 그 칸을 채울 수도 있다. 잇달아 빠지면 줄이 Not checked가 된다.
  3. 저장소 활동이 60일 없으면 GitHub가 이 workflow를 끄고, 그때 dispatch는 `unprocessable`(422)을 남긴다. GitHub UI에서 다시 켠다.
  4. dispatch로 시작한 실행이 실패하면 GitHub 알림은 실행을 시작한 계정, 곧 토큰 주인에게 간다[추론]. 감시 실행은 감시 자체가 고장 났을 때만
     실패하므로 서비스 장애는 메일이 아니라 `/status`에 보인다.
  5. No expiry 키는 만료로 끝나지 않으므로 새어 나가면 관리자에서 취소해야 끝난다. 방 `000001`의 키는 릴리스 smoke만 쓰고, smoke는 그 키를
     GitHub `production` 환경 비밀로만 받는다.
  6. 관리자 폼의 No expiry는 로컬 JSDOM 시험으로 봤고 실제 기기에서는 보지 않았다. `/status`는 모양이 바뀌지 않았다.
