## 왜 고쳤나

- **오너의 운영 확인에서 나왔다.** 2026-10-23 15:14·15:26 KST 운영 소유권 왕복 이전
  ([release-record](../release-record.md) §2 Phase 1 항목)에서 기존 PIN을 다시 넣은 첫
  시도가 `OWNER_TRANSFER_PIN_REUSE`(409)로 거절됐다. 권리 이동은 없었고 그 `intent`는
  `superseded`로 정리됐다.
- **이전 소유자 PIN 확인 수단이었다.** PREPARE는 새 PIN이 방의 현재 PIN과 같으면
  거절했다. 이전 링크를 받은 사람은 후보 PIN을 넣어 보고 이 거절로 이전 소유자의 PIN이
  맞는지 알 수 있었다(IP당 시간당 10번, 링크 수명 10분 안에서).
- **안내가 틀렸다.** 앱은 이 409를 "안전을 위해 이 링크를 다시 시도하지 않았어요. 방
  관리자에게 새 링크를 요청해 주세요"로 보여 줬다. 실제로는 링크가 소비되지 않아 다른 PIN을
  넣으면 됐다.
- 8.8.0([#281](https://github.com/hiefny/MUSIXQUARE/pull/281),
  [선택형 입장 암호](pro-optional-entry-password-2026-10-10.md))부터 활성화는 PIN을 묻지
  않고 공개 방을 만드는데, 이전만 새 PIN을 요구했다.

## 바뀐 것

### PRO Worker (방 Durable Object)

- PREPARE 본문은 `{claimToken, requestId}`이다. 결정 전 앱이 보내는 `newPin`도 받는다.
  모양(8자리 숫자)은 예전처럼 검사하고 값은 쓰지 않는다. `OWNER_TRANSFER_PIN_REUSE`를
  지웠고, PREPARE에서 PIN 해시(PBKDF2)도 만들지 않는다. PIN pepper 설정 확인은 남겼다:
  열린 방이라도 세션 생성에 필요하므로, 없으면 예전처럼 PREPARE가 아무것도 지우기 전에
  503 `SERVICE_NOT_CONFIGURED`로 거절한다.
- 재생(같은 `requestId`)은 같은 링크·같은 계정·같은 요청 ID로만 맞춘다. PIN 비교와
  `OWNER_TRANSFER_REPLAY_MISMATCH`가 없어졌다. 대기 중인 이전과 완료된 이전 모두 같다.
- 새 대기 레코드에는 `pin`이 없다. 결정 전 PRO Worker가 쓴 레코드(`pin` 있음)는 저장된
  그대로 읽고, 재생하고, 커밋한다. 그 PIN은 쓰지 않는다. 모양이 깨진 옛 `pin`은 예전처럼
  레코드를 무효로 만든다.
- 커밋은 `turnEntryPasswordOff`로 암호를 끈다(`passwordRequired: false`, PIN 기록 없음).
  오너가 방 설정에서 암호를 끌 때와 같은 함수·같은 상태다(그 설정도 이 함수를 쓰게
  바꿨다). PREPARE는 그대로다: 모든 세션을 지우고, 대기 중에는 정지 상태에서
  `passwordRequired: true`로 닫혀 있다.
- 커밋 경로를 `withEntryPolicyResponse` 안에서 돌린다. App이 브라우저의 opt-in 헤더를
  넘기면 이전 응답 스냅샷에 활성화 응답과 같은 추가 필드(`passwordRequired`,
  `playlistSlots`)가 붙는다. 헤더가 없으면 v1 모양 그대로다.

### App Worker (facade)

- 이전 본문을 `newPin` 없이 받는다. 결정 전 앱의 3키 본문(`newPin` 포함)도 같은 모양 검사로
  받는다. 사가 의도 기록에는 본문 해시가 없어 바뀐 것이 없다.
- 커밋 호출에 브라우저의 opt-in 헤더 두 개(`X-MXQR-Pro-Entry-Policy: optional-v1`,
  `X-MXQR-Pro-Playlist-Slots: v1`)를 정확한 값일 때만 넘긴다. 전에는 이전 응답 스냅샷에
  `passwordRequired`가 없어서, 앱은 이를 "암호 켜짐"으로 읽었다(`passwordRequired !== false`).
  암호를 끄는 지금은 새 소유자의 설정이 실제와 반대로 보였을 것이다.

### 브라우저 앱

- 이전 링크는 로그인 뒤 바로 이전을 요청한다. 복구 링크처럼 묻는 창이 없다. 확인 창은 더하지
  않았다: 링크가 대상 계정에 묶여 있고 서버가 계정을 확인하며, 받는 사람이 링크를 연 것이
  곧 의사 표시다. 새 문구는 없다.
- `TransferProRoomOwnerInput`과 요청 본문에서 `newPin`을 뺐다.
- 쓰이지 않게 된 `pro.transfer_title`·`pro.transfer_message`를 42개 로케일과 i18n 키
  목록 테스트에서 지웠다(로케일당 2키, 124줄).
- 오류 안내는 바꾸지 않았다(아래 점검).

## 이전 때 접속해 있던 사람

추가 조치는 없다. PREPARE가 이미 이전 소유자, 위임 관리자, 일반 참여자의 세션을 모두
지운다(권한 경계이므로 바꾸지 않았다). 커밋 뒤에는 암호가 꺼져 있으므로 그 사람들은 방
코드만으로 일반 참여자로 다시 들어온다. 이전 소유자의 계정·소유자 쿠키도 일반 참여자가
될 뿐이다. 기준으로 삼은 "암호 끄기" 설정은 접속한 사람을 그대로 두고 권한을 더 주지
않는다. 이전은 그 전에 모두 내보냈으므로, 끄는 시점에 남아 있는 사람이 없다. 이전으로
내보내진 세션에는 예전처럼 퇴장 사유가 붙지 않는다.

## 오류 안내 점검

PIN과 관련된 거절 두 가지(`OWNER_TRANSFER_PIN_REUSE`, `OWNER_TRANSFER_REPLAY_MISMATCH`)가
사라져, 소비되지 않은 링크에 PIN 때문에 "새 링크 요청" 안내가 뜨는 경우는 없다. 남은
이전 응답의 안내는 다음과 같고, 바꾸지 않았다.

| 응답                                                                                                             | 링크 소비 | 안내                                                                                                 |
| ---------------------------------------------------------------------------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------- |
| `OWNER_TRANSFER_CLAIM_INVALID`·`_EXPIRED`·`_STALE`·`_USED`, 404, 410                                             | 사용 불가 | 링크 만료·사용됨, 새 링크(정확)                                                                      |
| `OWNER_TRANSFER_TARGET_ACCOUNT_MISMATCH`                                                                         | 아니요    | 이 계정으로는 사용할 수 없음(정확)                                                                   |
| `ACCOUNT_PRO_ROOM_LIMIT_REACHED`                                                                                 | 아니요    | 계정 연결 한도(정확)                                                                                 |
| 5xx·시간 초과·`PRO_ROOM_TRANSFER_RECONCILIATION_REQUIRED`                                                        | 모름      | 같은 요청 ID로 다시 시도(정확)                                                                       |
| `RATE_LIMITED`                                                                                                   | 아니요    | 새 링크 요청. 링크당 요청 ID 10개 한도면 정확, IP 한도(1시간)는 링크 수명(10분)보다 길어 사실상 정확 |
| `OWNER_TRANSFER_TARGET_UNAVAILABLE`(커밋 전 대상 계정 비활성)                                                    | 예        | 새 링크 요청(정확)                                                                                   |
| `OWNER_TRANSFER_UNAVAILABLE`·`_TARGET_UNCHANGED`·`_CLAIM_CAPACITY_EXCEEDED`·`OWNER_AUTHORITY_PROJECTION_PENDING` | 아니요    | "새 링크 요청". 관리자에게 알리는 것은 맞지만 새 링크로 풀리지 않는 경우가 있다                      |

마지막 줄은 그대로 둔 한계다. 방이 이전할 수 없는 상태이거나, 링크를 연 계정이 이미
소유자이거나(링크 수명 10분 안에 다른 경로로 소유자가 된 경우), 이전 소유자 계정 삭제 정리가
끝나기 전인 경우다. 이 셋은 링크 발급 때 이미 막히므로 링크 수명 안에 방 상태가 바뀔 때만
생긴다. 사용한 링크 기록 128개 한도는 이전 하나가 끝나기 전에는 다음 링크를 발급하지
않으므로 사실상 닿지 않는다. 정확한 안내에는 새 문구(42개 언어)가 필요해 이번 범위에서
빼고 남겼다.

## 호환성과 배포 순서

- **target `all`, PRO room 먼저.** release.yml은 `all`에서 PRO room을 먼저, App을 마지막에
  배포한다. 새 App Worker·앱은 `newPin` 없이 보내는데, 옛 PRO Worker는 그 본문을 400
  `INVALID_REQUEST`로 거절한다. 그래서 새 앱이 옛 서버를 만나지 않게 PRO가 먼저 올라가야
  한다. 두 Worker 소스가 함께 바뀌어 부분 릴리스 게이트도 단독 배포를 막는다.
- **배포 창과 캐시된 옛 앱.** 옛 앱은 계속 "새 8자리 암호를 설정해 주세요" 창을 띄우고
  `newPin`을 보낸다. 새 PRO는 그 값을 쓰지 않고 방은 열린 상태로 끝난다. 옛 앱(8.8.0 이후)은
  opt-in 헤더를 보내므로, 새 App Worker를 거치면 설정에 "암호 꺼짐"이 바로 보인다. PRO와 App
  배포 사이 몇 분 동안 옛 App Worker를 거치면 응답 스냅샷에 `passwordRequired`가 없어 설정이
  "켜짐"으로 보이고, 다음 스냅샷(리비전이 바뀔 때)에 고쳐진다. 실제 입장 정책은 처음부터
  꺼짐이다.
- **저장 레코드.** 옛 PRO가 쓴 대기 레코드는 새 PRO가 그대로 처리한다(테스트로 고정).
  완료 레코드 모양은 그대로다. 방 상태의 `passwordRequired: false`/`pin: null`은 8.8.0
  선택형 입장 암호 계약이 이미 아는 모양이라 새 표지·floor는 없다.
- **되돌리기.** PRO Worker만 이전 기준으로 되돌리면 새 앱의 이전 링크가 400으로
  막힌다(링크는 소비되지 않고 "이 요청을 완료할 수 없어요"가 뜬다). 그러면 App도 함께
  되돌리거나 앞으로 고친다. 또 옛 PRO는 `pin` 없는 대기 레코드를 무효로 버린다. 그 방은
  `ownership_transfer_pending` 정지로 남고 관리자가 새 이전 링크를 발급해 풀어야 한다.
  대기 레코드는 PREPARE와 커밋 사이에만 있으므로(보통 한 요청 안, 길어야 링크 수명 10분)
  되돌리기 전에 진행 중인 이전이 없는지 본다. App만 되돌리면 옛 facade가 새 앱의
  본문을 400으로 거절한다(캐시된 새 앱).
- 새 비밀·바인딩·D1 스키마·의존성 없음. 통신 형식 변화는 PREPARE 본문의 `newPin`이
  선택이 된 것과, opt-in 헤더가 있을 때 이전 응답 스냅샷에 추가 필드가 붙는 것뿐이다.

## 테스트와 한계

- **테스트 먼저(`ae0c695a`, 고치지 않은 소스에서 통과).** PRO Worker 단위 테스트 3개
  (보호 방: PIN 필수·현재 PIN 거절·재생 PIN 비교·커밋 뒤 PIN 보호, 공개 방이 PIN으로
  보호됨, 재시작 뒤 저장된 대기 레코드 재생·커밋), App facade와 실제 PRO 방을 잇는 sqlite
  테스트 1개, 앱 테스트 2개(PIN 창 취소 시 요청 없음, PIN 재사용 거절에 일반 "새 링크" 안내).
  유지할 것(PREPARE의 세션 전부 해제, 이전 소유자 쿠키·계정의 권한 없음, 같은 요청 ID 재생,
  Developer API 펜스·사가)은 기존 테스트와 함께 고정했다.
- **빨강.** PRO Worker만 고친 상태(`dbc74c18`의 소스)에서 앞 커밋의 테스트 6개가
  실패했다. PIN 없는 PREPARE가 보호 방·공개 방에서 400이 아니라 200(2개), facade를 거친
  재사용 PIN이 409가 아니라 200(1개), 기존 큰 이전 테스트에서 커밋 뒤 옛 PIN 입장이 401이
  아니라 200(2개, 공개·보호), 새 대기 레코드에 `pin`이 없음(1개). App·앱까지 고친
  상태에서는 `dbc74c18`의 테스트 7개가 실패했다. facade의 PIN 없는 본문이 400이 아니라
  200(1개), 앱의 PIN 창·`newPin` 기대(4개), API 본문의 `newPin`·PIN 모양 검사(2개).
- **초록.** 바뀐 동작을 새 기대로 고쳤다. PRO Worker 단위 6개(보호 방이 열림·창 없음·소유자
  쿠키 두 개 유지, 옛 앱의 현재 PIN을 거절도 사용도 안 함, 공개 방 유지, 재시작 뒤 `pin`
  있는·없는 대기 레코드 재생과 커밋, PIN pepper가 없으면 아무것도 지우지 않고 503, 모양이
  깨진 옛 `pin`은 버림), sqlite 3개(PIN 없이 이전·응답의 `passwordRequired: false`와 쿠키,
  옛 앱의 PIN 무시·잘못된 모양 400, opt-in 헤더 없으면 v1 모양), 사가 혼합 버전(옛 App
  Worker 빌드에는 그 시절 앱의 PIN), 앱·API·세션 컨트롤러 테스트.
- 전체 검사: (작성 중)
- 실기기와 운영 이전은 확인하지 않았다. 묶음 배포 뒤 테스트 방에서 이전 링크가 암호를 묻지
  않는지, 새 소유자 설정에 암호가 꺼짐으로 보이는지, 그 자리에서 암호를 켤 수 있는지, 이전 때
  있던 참여자가 코드만으로 다시 들어오는지를 본다. 옛 앱이 캐시된 기기의 PIN 창(값 무시)도
  한 번 확인한다.
