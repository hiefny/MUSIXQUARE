## 1. 오너 결정

오너의 말은 옮기지 않고 뜻만 적는다.

- **2026-11-12, 미디어 고르기 화면의 아래 끝:** 오너가 미디어 고르기 화면만 아래 홈 표시줄 자리를 지키는 것을 결함으로 알렸고, 곧이어 재생
  화면을 뺀 나머지 화면이 모두 그렇다는 것도 알렸다(어느 기기에서 봤는지는 듣지 않음). 재현해 보니 두 가지가 섞여 있었다. 미디어 화면 밑으로
  재생 화면이 비치는 것은 9.0.44가 만든 결함이라 이 열차가 고친다(§3). 목록 탭 넷이 홈 표시줄 위에서 끝나는 것은 9.0.43의 계약이라 그대로
  두고, 재생 화면처럼 화면 아래 끝까지 보낼지를 사진과 함께 오너에게 물었다. 이 보고서를 쓸 때까지 답이 없어 이 열차에 넣지 않았다(§3.5).
  오너는 배포 뒤 같은 날 답했다: 가로로 쓰는 배치에서는 앱 전체를 재생 화면처럼 화면 아래 끝까지 그린다. 그 변경은 다음 App 업데이트가
  싣는다(배포 기록이 덧붙임).
- **2026-11-11, 배포 허가(9.0.42 열차 때의 결정):** 배포는 모두 허가했다. 자동 관문(PR 검사, 자동 코드 리뷰, 병합, exact-main CI, 최소 앱 빌드
  확인)이 통과하면 업데이트 창이 뜨는 열차도 따로 묻지 않고 dispatch한다. 기기 확인은 게이트가 아니다.

만든 쪽이 정한 것(오너 결정 아님): 오른쪽에서 왼쪽 언어의 자리 고침(§4)은 오너가 알린 것이 아니라 위 결함을 확인하다 찾은 기존 결함이다.
같은 규칙에 한 줄씩이고 고친 모습이 분명해 같은 열차에 넣었고, 전후 사진을 오너에게 보냈다. 닫기 버튼의 들여쓰기는 독립 검토가 찾아 그 뒤에
더했다(§11.1).

## 3. 미디어 화면을 화면 아래 끝까지 (9.0.44가 만든 결함의 고침, [화면 바뀜])

### 3.1 사용자에게 바뀌는 것

- 사이드바 배치이면서 아래 안전 영역이 있는 화면(홈 화면에 설치한 iPad의 가로·세로, 홈 표시줄이 있는 가로 휴대폰)에서, 미디어 고르기 화면과
  YouTube 입력 화면이 홈 표시줄 위에서 끝나지 않고 화면 아래 끝까지 덮는다.
- 9.0.44에서는 두 화면이 안전 영역의 아래 끝(1024x768 iPad 가로 PWA에서 세로 748)에서 끝났다. 뒤에 있는 재생 화면은 9.0.44부터 화면 아래
  끝(768)까지 닿으므로, 그 사이 20px 띠에 재생 화면의 맨 아래 Sync·Media 버튼의 아랫부분(748 ~ 761.5)이 미디어 화면 밑으로 보였다. 이제 그
  띠도 미디어 화면의 바탕이 덮는다.
- 두 화면 안에 있는 것의 자리는 그대로다. 제목, 닫기 버튼, 선택지, 입력칸, 아래 버튼 줄의 좌표가 9.0.44와 같고 모두 전처럼 홈 표시줄 위에
  있다.
- 그대로인 것: 재생 화면과 목록 탭 넷(플레이리스트, 연결, 설정, 도움말), 사이드바, 대화상자, 채팅, 전체 화면 영상, 넓은 배치(1280x720 이상),
  휴대폰 세로 배치, 그리고 아래 안전 영역이 없는 모든 화면(일반 브라우저 창과 데스크톱).

### 3.2 바뀐 코드

`css/style.css`의 사이드바 배치 블록에서 두 화면의 규칙을 고쳤다.

```css
#media-source-overlay,
#youtube-url-overlay {
  height: calc(var(--app-height, 100dvh) - var(--safe-top));
  max-height: calc(var(--app-height, 100dvh) - var(--safe-top));
  padding-bottom: var(--safe-bottom);
}
```

- 전에는 두 높이에서 `--safe-bottom`도 뺐고 끝 여백은 없었다.
- 9.0.44는 재생 화면의 본문만 화면 아래 끝까지 늘렸다. 그 보고서는 미디어 고르기와 YouTube 입력 화면을 '그대로인 것'에 적었고 두 화면의
  상자는 실제로 그대로였지만, 두 화면이 재생 화면 위에 뜬다는 것을 놓쳤다. 덮는 화면이 덮이는 화면보다 아래 안전 영역만큼 짧아졌다.
- 새 규칙은 두 화면을 재생 화면과 같은 아래 끝까지 늘리고, 늘어난 만큼을 끝 여백으로 둔다. 내용 상자는 전과 같은 안전 영역 안의 상자라
  안의 구성이 움직이지 않고, 홈 표시줄 자리에는 두 화면의 바탕만 그려진다.
- 아래 안전 영역이 0이면 세 값이 전과 같다(두 높이는 `--safe-bottom`을 빼지 않아도 같고 끝 여백은 0).
- 키보드가 올라와 `--app-height`가 줄어든 동안에도 내용 상자는 전과 같다. 전에는 높이에서 빼던 값을 이제 끝 여백으로 둘 뿐이다[추론: 식의
  대조이고 키보드를 띄워 재지 않음].

- **9.0.44와의 전체 비교:** 실제 방에서 열일곱 가지 화면(안전 영역 있는 일곱, 없는 열)의 242개 장면을 찍어 id가 있는 모든 요소의 자리를
  견줬다(0.5px 넘는 차이만). 요소 자리가 달라진 장면은 14개이고 모두 의도한 것이다. 사이드바 배치이면서 아래 안전 영역이 있는 왼쪽에서 오른쪽
  표본 셋(가로 iPad, 세로 iPad, 가로 휴대폰)의 미디어 고르기·YouTube 입력 장면 6개에서는 그 화면의 높이만 아래 안전 영역만큼 늘었고 안의
  요소는 그대로다. 나머지 8개는 오른쪽에서 왼쪽 두 표본의 장면이다(§4.4). 다른 228개 장면은 요소 자리 차이가 0이고, 사진의 화소 비교(채널마다
  8 넘는 차이)에서 달라진 곳은 방마다 다른 초대 코드와 QR뿐이다.

### 3.5 알려 둘 것과 한계

- 띠의 화소 차이는 작다. 라이트 테마에서 비치던 버튼(흰색)과 미디어 화면의 바탕(`#f8f9fa`)은 채널마다 7 이하로 다르다. 그래서 위 화소
  비교는 이 고침을 잡지 못했고(그 6개 장면이 '같음'으로 나옴), 요소 자리와 확대한 사진으로 확인했다. 다크 테마의 띠는 찍지 않았다.
- hit test 행이 직접 보는 것은 띠에서 포인터가 그 화면에 닿는다는 것이다. 미디어 화면이 열려 있는 동안 뒤쪽 재생 화면은 포인터를 받지 않아,
  고치기 전 그 띠의 hit test는 버튼이 아니라 페이지 바탕을 만났다. 뒤가 비치지 않는 것은 상자가 화면 아래 끝까지 닿고 바탕이 불투명하다는
  데서 따라온다[추론].
- 목록 탭 넷은 그대로 홈 표시줄 위에서 끝난다(9.0.43의 계약). 화면 아래 끝까지 닿는 것은 재생 화면과 그 위에 뜨는 미디어 화면 둘, 그리고 전부터
  그랬던 채팅 창과 사이드바의 바탕이다. 목록 탭도 그렇게 할지는 오너에게 물었고, 오너가 배포 뒤에 그렇게 하기로 정했다(§1, 다음 App 업데이트). 그렇게 하려면 플레이리스트의 선택 막대와
  스크롤 막대의 자리, 9.0.43의 fixture 계약(스크롤된 글이 안전 영역에 들어가지 않음)을 함께 바꿔야 한다(9.0.44 보고서 §3.5).
- 실기기에서 보지 않았다(§12).

## 4. 오른쪽에서 왼쪽 언어의 미디어 화면과 채팅 창 자리 (기존 결함의 고침, [화면 바뀜])

### 4.1 사용자에게 바뀌는 것

- 오른쪽에서 왼쪽 언어로 사이드바 배치를 쓸 때 미디어 고르기 화면, YouTube 입력 화면, 채팅 창이 본문 자리(화면 왼쪽에서 사이드바의 왼쪽
  끝까지)에 놓인다.
- 전에는 셋 모두 사이드바의 폭 200px만큼 오른쪽에 놓였다. 1024x768에서 미디어 고르기 화면은 가로 200 ~ 1024에 놓여 오른쪽 200px이 사이드바
  밑으로 들어갔고(제목과 선택지의 글자가 사이드바에서 잘림), 왼쪽 200px에는 뒤쪽 재생 화면이 보였다. YouTube 입력 화면도 같았다(취소 버튼이
  잘림). 채팅 창은 사이드바보다 위 층이라 사이드바의 아래쪽을 가렸고 왼쪽 200px을 덮지 못했다.
- 미디어 고르기 화면의 닫기 버튼이 선택지와 같은 들여쓰기에 놓인다. 오른쪽에서 왼쪽 언어에서 닫기 버튼은 화면 왼쪽에 놓이는데, 여백이 물리
  오른쪽에 남아 버튼이 선택지보다 28px 바깥(가장자리 쪽)에 있었다.
- 왼쪽에서 오른쪽 언어, 넓은 배치, 휴대폰 세로 배치는 그대로다.

### 4.2 바뀐 코드

`css/style.css`의 사이드바 배치 블록에서 두 규칙에 한 줄씩 더하고, 닫기 버튼 줄의 여백을 글 쓰는 방향을 따르는 것으로 바꿨다.

```css
#media-source-overlay,
#youtube-url-overlay {
  left: 0;
  right: auto; /* 새 줄 */
}

.chat-drawer {
  left: 0;
  right: auto; /* 새 줄 */
}

#media-source-overlay .ob-actions {
  padding: 0; /* 전에는 0 28px 0 0 */
  padding-inline-end: 28px; /* 새 줄 */
}
```

- 사이드바 배치에서 본문은 글 쓰는 방향과 상관없이 화면의 왼쪽, 사이드바는 오른쪽이다(9.0.43). 세 층은 `left: 0`과 폭으로 그 자리에 놓이는데,
  바탕 규칙이 오른쪽도 정한다(`.onboarding-overlay`의 `inset: 0`, `.chat-drawer`의 `right: 0`). 왼쪽, 오른쪽, 폭이 모두 정해지면 브라우저는
  하나를 버린다. 왼쪽에서 오른쪽 문서에서는 `right`를, 오른쪽에서 왼쪽 문서에서는 `left`를 버린다. 그래서 오른쪽에서 왼쪽 언어에서는 상자가
  화면 오른쪽 끝에 붙었다.
- `right: auto`를 주면 두 방향 모두 `left`와 폭이 자리를 정한다. 왼쪽에서 오른쪽 언어에서는 계산값이 전과 같다.
- 9.0.42에도 같은 규칙이었다(그 앞의 시작은 찾지 않음). 9.0.43은 같은 종류의 결함을 탭 본문에서 고쳤고(네 탭이 사이드바 밑으로 200px 밀리던
  것) 이 세 층은 남아 있었다.
- 미디어 고르기 화면의 카드는 사이드바 배치에서 두 칸짜리 격자이고(제목 칸과 닫기 버튼 칸) 칸의 순서가 글 쓰는 방향을 따른다. 닫기 버튼 줄의
  여백은 물리 오른쪽(`padding: 0 28px 0 0`)이라, 오른쪽에서 왼쪽 언어에서는 버튼과 가장자리 사이가 아니라 버튼과 제목 사이에 놓였다.
  `padding-inline-end`로 바꿔 두 방향 모두 가장자리 쪽에 놓인다. 왼쪽에서 오른쪽 언어에서는 계산값이 전과 같다.

### 4.3 시험과 커밋

- 오른쪽에서 왼쪽 언어의 배치를 모두 살핀 것은 아니다. 본 것은 촬영 도구의 열여섯 장면과 폭 500px 넘는 요소의 자리다. 사이드바 배치 블록에서

  기존 것이고 브라우저에서 확인하지 않아 이 열차에 넣지 않았다.
- 실기기에서 보지 않았다(§12).

- 섞인 버전의 방은 따로 시험하지 않았다(§7).
- 배포 뒤 브라우저 확인은 데스크톱 Chromium의 운영 시작 화면, 업데이트 적용, 배포된 CSS뿐이다(§11.3). 운영에서는 안전 영역이 있는 화면, 오른쪽에서 왼쪽 언어의 화면, 기기를 보지 않았다(§9).
- 로컬 결과는 exact-main-SHA 후보를 대신하지 않았다.
