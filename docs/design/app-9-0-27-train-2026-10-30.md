## 증분

### 1. iPhone Safari 청취자의 LAN-direct 쌍 판정과 진단 줄

- 커밋(main `cbbc56d9` 위 브랜치 `agent/lan-ios-listener`, 2026-10-30 14:48 ~ 16:01 KST, 오래된 것부터): 시험 `6eb40a04`,
  구현 `dc704605`(공유 정제 모듈, PRO 규칙, 쌍 확인 줄)과 `f4ac3bf2`(SFU 구독 단계 줄과 서비스의 공유 알림 시각), 문서
  `8e4ac4e6`, 검토 반영 시험 `10431823`, 구현 `85a29f03`, `70cdb078`, `9f013814`, 문서 `aad6e460`. 원인 조사, 세 관점의
  독립 검토, 반영 라운드는 [증분 노트](pro-lan-direct-ios-listener-2026-10-30.md)에 있다.
- 원인(소스 읽기와 Chromium 재현, 기기 측정 아님): iOS Safari는 LAN-direct의 응답자라서 ICE-controlled다. 공유자의 연결
  확인이 Safari가 공유자의 mDNS 이름을 풀기 전에 도착하면 libwebrtc는 상대 후보를 peer-reflexive(prflx)로 만들고, 이름이
  풀리면 같은 연결을 제자리에서 host로 바꾸지만 선택 쌍 바뀜 알림은 없다. 그래서 원래 선택 쌍(`getSelectedCandidatePair()`)은
  host→prflx로 남고 통계(`getStats()`)는 host→host를 보인다. PRO 규칙은 host가 아닌 형을 첫 판독에서 non-local로 끝냈고,
  Standard 방의 `detectConnectionType`은 이 경우를 정제된 통계 쌍으로 확인한다.
- 바뀐 것: Standard의 정제 검사를 동작 그대로 import 없는 잎 모듈 `src/network/ice-selected-pair.ts`로 옮겨 두 규칙이 한
  벌을 쓴다(PRO만 켜는 선택 인자 하나). PRO의 공유자 협상, 수신자 증명, 활성화와 live 재증명이 모두 한 함수를 쓴다. 바뀌는
  것은 (로컬 host, 상대 prflx) 원래 쌍뿐이다: 원래 쌍이 보이는 주소가 host 규칙을 지키고, 통계에서 transport가 하나만 고른
  성공한 host→host 쌍이 이 경로에 더한 엄격한 mDNS UDP 후보로 정제됐을 때만 증명한다(`refined-host`). 정제 전에는
  non-local이 아니라 pending(`prflx-unrefined`)이라 기존 증명 창(수신자 2초, 공유자 응답 뒤 1초) 안에서 정제를 기다린다.
  검토 반영으로 consent 확인 중인 정제 쌍(응답을 받은 'in-progress')을 재증명이 받아들이고, 같은 소켓·포트의 prflx 연결이
  통계에 남아 있으면 pending(`prflx-still-listed`), 통계가 쌍을 둘 이상 고르면 non-local(`stats-ambiguous`)이다. 다른 모든
  비 host 형, 후보 규칙(mDNS UDP host만, 경로당 2개), `iceServers: []`, 모든 시한과 상수는 그대로다.
- 새 info 줄(IP 주소, 포트, foundation, ufrag, mDNS 이름, 방 코드, 참가자 id 전체 없음, 시험이 고정):
  `[ProSysAudioDirect] Receiver pair check <proven|non-local|deadline|disconnected|closed> after <ms> ms by <규칙> (…)`,
  공유자의 `[ProSysAudioDirect] Publisher pair check to <id 끝 4자> …`(그 경로의 `LAN route to …` 줄 바로 앞), 실패한 재증명의
  `[ProSysAudioDirect] Publisher pair reproof to <id 끝 4자> <non-local|pending> by <규칙> (…)`, 그리고 SFU 청취자의
  `[ProSysAudioSFU] Subscription to generation <g> ready <ms> ms after the share notice (start a, config b, session c, tracks d, offer e, track f, answer g, subscribed h)`와
  그 실패 줄(`… failed at <단계> …`, `… failed before start (…)`). 괄호 안에는 연결 시각, 원래 쌍과 통계 쌍의 후보 형과 주소

  `Receiver route ended before live (…)`, `Received stereo track`, `Subscribed to generation` 줄은 글자 그대로다.
- 조건부 수정: 고쳐지는 것은 iOS가 공유자의 이름을 풀고 연결이 정제된 것이 공유자의 수신자 증명 시한(응답 + 1초,
  `DIRECT_PAIR_PROOF_TIMEOUT_MS`) 안일 때뿐이다. 9.0.26 공유 1에서 청취자가 non-local로 끝낸 때(공유자 시계로 약 1.51초)는

지워지는 메시지 묶음의 검토(승인, 낮음 1, 정보 2)가 남긴 낮음을 조립에서 반영했다.

- 변이 확인(저장소 밖 Vitest 설정이 바꾼 사본을 읽게 함, 작업 트리는 그대로): `src/ui/chat.ts`를 `focused !== container`

### 4. 조립 검토 반영 2

열차 머리 `aaead38c`(이 보고서를 처음 더한 문서 커밋)까지의 독립 검토가 지적 셋(중간 1, 낮음 2)과 정보 하나를 냈다. 모두
코드와 9.0.26 배포 직후 확인에 대어 보고 맞다고 봤다. 고친 것은 문서뿐이고 런타임과 시험은 그대로다(이 절을 더한 문서
커밋). 받아들이지 않은 지적은 없다.

- 중간(SFU 대체 지연을 줄여 적고 오너 질문을 빠뜨림): 이 보고서, 릴리스 기록 §2, `docs/README.md`가 "최대 약 0.5초"라고
  적었지만 코드의 한도는 공유자의 증명 창이다. 9.0.26은 정제되지 않은 host→prflx 쌍을 첫 연결 판독에서 non-local로
  거절했고(청취자가 끝내면 공유자는 `receiver-fallback`을 받아 바로 SFU로 감), 이제 `readSelectedPair`가 그 쌍을
  `prflx-unrefined` pending으로 돌려 공유자의 `negotiatePublisherRoute`가 응답 뒤 `DIRECT_PAIR_PROOF_TIMEOUT_MS`(1초)까지
  기다린다. 늦어지는 만큼은 첫 연결 판독부터 그 시한까지라 최대 약 1초이고, 약 0.4초는 늦게 연결된 9.0.26 공유 1의 한
  표본이다. 통계 전용 경로(통계가 고른 host→prflx)와 공유자 자신의 쌍도 같고, 공유는 경로들을 `Promise.all`로 기다리며
  실패한 경로에서만 일찍 끝나므로 기다리는 한 경로가 그 시도 전체의 SFU 대체를 늦춘다. 세 곳을 "최대 약 1초"로 고치고
  어느 끝, 어느 브라우저든 그렇다고 적었다. 증분 노트가 남긴 오너 확인 거리는 '오너 결정'의 열린 질문, '배포 조건과 순서'
  5(머지 전에 오너에게 보임), '확인하지 않은 것', 릴리스 기록 §2로 옮겼다. 증분 노트의 '시간과 섞인 버전'도 같은 한도를
  적는다.
- 낮음(판정 기준에 `stats-host`가 없음): 증명한 판독 때 WebKit의 원래 쌍 사본이 아직 없거나 그 iOS에
  `getSelectedCandidatePair`가 없으면 진짜 같은 LAN 쌍도 통계 전용 경로에서 `by stats-host`로 증명된다(시험 'also waits,
  never refusing at once, when only statistics show a selected host-to-prflx pair'). '판정 기준'의 통과, '원인 확인', '열린
  항목 닫기'와 릴리스 기록 §2의 닫는 근거가 `stats-host`도 받고, 그것도 `native-host`처럼 정제 원인을 보이지 않는다고
  적었다. 증분 노트의 '배포 뒤 확인' 제안도 같다.
- 낮음(증분 노트의 공유 1 시각 둘이 어긋남): 노트의 '시간과 섞인 버전'이 청취자의 첫 연결 판독을 "시한보다 약 0.45초
  앞"(약 1.44초)과 "공유자 시계로 약 1.0초, 시한까지 약 0.85초"로 달리 적었다. 옛 규칙은 첫 연결 판독에서 거절했으므로
  판독과 거절은 같은 때이고, 9.0.26 배포 직후 확인은 청취자 시계를 그 거절과 공유자의 `receiver-fallback` 수신(1,509 ms)이

- 정보(결함 없음, 검토의 확인을 옮김): 검토는 작업 트리를 건드리지 않는 저장소 밖 Vitest 설정으로 정제 경로의 확인을

  시험 54행이 실패함을 보았다. 쌍 확인 줄의 내용(IP, 포트 없음)과 횟수, SFU 단계 표시가 기존 await와 처리기에서만 읽힘,

## 섞인 버전

- LAN-direct: 신호 모양과 서버 계약이 같아 9.0.26과 9.0.27 사이에도 경로가 생긴다. 고쳐지는 쪽은 판정을 하는 끝이다.
  - 9.0.26 공유자와 9.0.27 청취자: 청취자가 정제된 쌍을 증명하면 LAN-direct가 될 수 있다(9.0.26 현장처럼 공유자가 자기
    쌍을 증명할 때). 공유자 콘솔에는 `Publisher pair check` 줄이 없고 예전 `LAN route to …` 줄만 있다. 정제가 늦으면 9.0.26
    공유자의 시한(응답 + 1초)에 SFU로 간다.
  - 9.0.27 공유자와 9.0.26 청취자: 청취자가 예전처럼 host→prflx 쌍을 첫 판독에서 non-local로 거절해 공유자는
    `receiver-fallback`으로 SFU로 간다(9.0.26과 같은 결과). 청취자 콘솔에는 `Receiver pair check`와 SFU 단계 줄이 없다.
  - 어느 쪽이든 SFU가 안전한 끝이므로 바닥은 795 그대로다. 오너 방침상 옛 버전은 설계 제약이 아니다.
- 포커스: 기기 안의 화면 동작뿐이고 메시지, 상태 모양, 저장 키와 데이터는 그대로라 섞인 버전 문제가 없다. 열린 탭은
  업데이트 경로로 새 코드를 받을 때까지 예전처럼 동작한다.
- Worker는 바뀌지 않는다. 이 열차는 바닥에 기대는 것을 더하지 않는다.

## 되돌리기

- 기본은 hotfix 절차대로 더 높은 SemVer와 캐시 epoch의 코드 되돌리기다(9.0.28 / v801 이상).
- 실패 자동 복구: `app`의 실패 복구는 App만 이 릴리스의 recovery checkpoint(dispatch 때 live인 App, 지금은 9.0.26 / v799
  `b8dc4281`, 빌드 799)로 되돌린다. 저장 바닥 795 이상이라 `lower`가 필요 없고, 그 App은 schemaVersion 2를 읽으므로 PRO는
  그대로 둔다. 되돌린 뒤 iPhone Safari 청취자는 다시 host→prflx 쌍을 거절해 SFU로 소리가 나고, 새 진단 줄이 없어지며, 채팅
  시트의 Tab은 다시 손잡이에 머물고, 숨거나 지워지는 채팅 내용의 포커스는 다시 페이지로 떨어진다.
- 다만 `app`의 배포 뒤 smoke(App generation, 익명 계정 경계, PRO 공개 경계, Standard HTTPS 신호)는 HTTP만 보고 시스템
  오디오 공유나 채팅 포커스를 거치지 않는다. 그래서 이 열차의 결함은 커밋 표지를 지나고 그 복구는 돌지 않는다. 그때는 아래
  '배포 직후 확인과 기기 확인'의 '실패하면'대로 App을 손으로 되돌린다.
- 손 되돌리기 경계는 release-record §4 머리의 현재 경계 줄과 9.0.25, 9.0.26 항목이 정본이다. 이 열차는 새 경계를 더하지
  않는다: App을 9.0.22(빌드 795) 이상으로 되돌리는 것은 `lower` 없이 App만이고, PRO를 schemaVersion 2를 처음 보내는 PRO
  Worker 아래로 손으로 되돌리지 않으며, App을 795 아래로 내릴 때는 §4의 합친 순서를 따른다.

## 사용자가 알아챌 변화

- **화면.** 바뀌는 것이 없다. 버튼, 문구, 배치, 색, 포커스 테두리는 그대로다.
- **PRO 시스템 오디오.** 같은 Wi-Fi의 iPhone Safari 청취자가 LAN-direct로 갈 수 있다. 그때는 SFU 구독을 기다리는 시간이
  없어진다(9.0.26 공유 1에서는 SFU 구독에 약 5.4초가 걸려 소리가 시작 뒤 5초 넘어 났다). LAN-direct가 되지 않는 경우에는
  SFU로 가는 것이 최대 약 1초 늦어질 수 있다(한 경로의 문서화된 최대 3초 안). 9.0.26은 정제되지 않은 host→prflx 쌍을 첫
  연결 판독에서 거절했지만, 이제 그 쌍은 pending이라 공유자의 증명 창(응답 뒤 1초, `DIRECT_PAIR_PROOF_TIMEOUT_MS`)이 끝날
  때까지 기다린다. 늦어지는 만큼은 첫 연결 판독부터 그 시한까지라 연결이 응답 직후에 되면 거의 1초다(9.0.26 공유 1처럼
  늦게 연결된 청취자라면 약 0.4초). iPhone만의 일이 아니다: 공유자 자신의 쌍이든 청취자의 쌍이든, 어느 브라우저든(통계
  전용 경로의 Firefox 포함), 한쪽이 상대의 mDNS 이름을 풀지 못하는 LAN이면 모두 이 느린 쪽이다. 공유는 모든 경로의 증명을
  기다리므로 한 경로가 기다리면 그 시도의 모든 청취자가 SFU로 가는 것이 그만큼 늦다. 이 지연을 받아들일지는 열린 오너
  질문이다(위 '오너 결정'). 9.0.26 이하 청취자와 섞이면 지금처럼 SFU다. `?mxqrLog=info`의 콘솔에만 새 줄이 보인다.
- **키보드와 화면 낭독기.** 휴대폰·태블릿 채팅 시트의 Tab과 Shift+Tab이 손잡이, 메시지, 입력, 보내기(공지가 보일 때만 그
  버튼 둘)를 돈다. 고정 공지의 X를 Enter로 닫거나, 공지가 철회되거나, 방 기록이 지워지거나, 200개 상한이 포커스를 가진
  메시지를 밀어내도 포커스가 채팅 시트(데스크톱은 채팅 패널)에 남아 화면 낭독기가 채팅을 떠나지 않는다.
- **업데이트 창.** 한 번 뜬다(9.0.22 ~ 9.0.26 탭은 '나중에'가 있는 보통 창).

## 배포 직후 확인과 기기 확인 (게이트 아님)

LAN-direct 확인은 블라인드로 한다. 확인하는 사람에게는 '나눠 줄 절차'와 '받을 관찰값'만 그대로 건네고 기대값은 주지
않는다. 판정하는 쪽이 받은 값을 '판정 기준'과 견주며, 판정 기준과 '실패하면'은 건네지 않는다. 확인하는 사람과 판정하는
사람이 같은 공유를 실시간으로 이야기하지 않는다(9.0.26 확인은 블라인드가 아니었다). 결과는 QA 라운드에 적되 방 코드와
식별자는 지우고 개수와 필요한 줄만 옮긴다. 키보드 포커스는 아래 '오너 기기 확인 목록'으로 본다.

- 기기는 둘이다. 공유 기기는 방 주인 계정으로 로그인한 Windows 데스크톱의 Microsoft Edge, 청취 기기는 로그아웃한 iPhone의
  Safari다. 두 기기를 같은 Wi-Fi에 두고 VPN을 끈다. 다른 기기는 방에 넣지 않는다.
- 기기마다 MUSIXQUARE 탭을 모두 닫고 새 탭에서 `https://musixquare.com/<PRO 방 코드>?mxqrLog=info`를 열어 방에 들어간다.
  주소 끝에 `?mxqrLog=info`가 있는지 두 기기 모두 처음에 확인한다. PIN을 물으면 넣는다. 업데이트 창이 뜨면 그 사실을 적고
  '적용하기'를 누른 뒤, 그 탭을 닫고 같은 주소로 다시 연다.
- 공유 기기에 소리가 계속 나는 다른 Edge 탭 하나를 열어 둔다(공유할 소리).
- 디버그 글: 채팅에 `/debug sync`나 `/debug console`을 보내면 겹창이 뜨고 그 글이 클립보드에 한 번 복사된다. 메모에 기기
  이름과 지금 시각을 적고 그 글을 붙여 넣은 뒤 겹창 가장자리를 눌러 닫는다. 끝날 때까지 방 탭을 새로 고치거나 닫지 않는다.
- 메모는 확인을 맡긴 사람에게만 넘기고 공개된 곳에 올리지 않는다.

A. 들어가기

1. 두 기기 모두 방에 들어간다.
2. 기기마다 `/debug sync` 글을 붙여 넣는다.
3. iPhone의 iOS 버전(설정 > 일반 > 정보)을 적는다.
4. 공유 기기 Edge에서 주소창 왼쪽의 사이트 정보 단추를 눌러 카메라와 마이크 권한이 무엇으로 되어 있는지 적는다(바꾸지
   않는다).

B. 공유 다섯 번(1 ~ 5번째마다 같은 순서)

1. 공유 기기에서 시스템 오디오 공유를 시작한다: '시스템 오디오 공유' → 소리가 나는 Edge 탭 → '탭 오디오도 공유' 켬 →
   '공유'. 그 시각을 적는다.
2. 청취 기기에서 소리가 들리는지 보고, 처음 들린 때가 시작 뒤 몇 초쯤인지 적는다. 20초 동안 끊기면 그 시각을 적는다. 어느
   기기든 토스트가 뜨면 그 글과 시각을 적는다.
3. 공유를 시작하고 20초 뒤 두 기기 모두에서 `/debug console` 글을 붙여 넣는다(공유마다 두 기기 모두).
4. 공유 기기에서 공유를 멈추고 그 시각을 적는다. 10초 넘게 기다렸다가 다음 공유를 시작한다.

### 받을 관찰값

1. 기기마다: 기기 종류와 브라우저, iPhone의 iOS 버전, 공유 기기 Edge의 카메라·마이크 권한, 업데이트 창이 떴는지, 방 화면이
   떴는지, A 2의 `/debug sync` 글.
2. 공유마다: 시작과 멈춘 시각, 청취 기기에서 소리가 들렸는지와 처음 들린 때, 끊긴 시각(없으면 '없음'), 뜬 토스트와 그 시각,
   두 기기의 B 3 `/debug console` 글.
3. 두 기기가 처음부터 끝까지 같은 Wi-Fi였는지, VPN이 꺼져 있었는지.

### 판정 기준 (나눠 주지 않음)

- 유효: 두 기기의 `/debug sync` 셋째 줄이 `Client build: app=9.0.27 | cacheEpoch=v800`로 시작하고, 두 기기가 같은 Wi-Fi에
  VPN 없이 있었다. 아니면 그 결과는 무효이고 새 탭에서 다시 한다. 그 공유의 두 `/debug console` 글이 모두 있어야 하고, 글의
  첫 줄 시각이 그 공유의 시작보다 늦으면 그 앞은 300줄 고리 밖이므로 그 공유는 다시 한다. 청취자 글에
  `Receiver LAN pair` 줄이 있는데 `Receiver pair check` 줄이 없으면 청취 기기가 9.0.27이 아니므로 무효다.
- 공유 하나의 통과: 공유자의 그 공유 글에 `[ProSysAudioDirect] Publisher pair check to <id 끝 4자> proven …`과
  `[ProSysAudioDirect] LAN route to <id 끝 4자> proven in N ms (…)`가 있고 그 공유의 시작 뒤에
  `[ProSysAudioSFU] Published generation`과 `[PRO SystemAudio] Promoted LAN-direct publication to SFU`가 없으며, 청취자의 글에
  `[ProSysAudioDirect] Receiver pair check proven after <ms> ms by refined-host`, `… by native-host` 또는
  `… by stats-host`와 `[ProSysAudioDirect] Receiver LAN pair proven in N ms`가 있고
  `[ProSysAudioSFU] Subscription to generation`이 없으며, 청취자가 끊김 없이 소리를 들었다. 모두 `?mxqrLog=info`의 info
  줄이다.
- 원인 확인: 통과한 공유의 청취자 줄 규칙이 `refined-host`이고 괄호의 native 쌍이 `… to prflx/…`이면 9.0.26의 막힘이
  증분 노트의 원인(정제되지 않은 원래 쌍)이었고 이 열차가 고쳤다는 근거다. `by native-host`이면 그 공유는 정제 없이 붙은
  것이고, `by stats-host`이면 통계 전용 경로라(증명한 판독 때 WebKit의 원래 쌍 사본이 아직 없었거나 그 iOS에
  `getSelectedCandidatePair`가 없음, 괄호는 `native none`) 원래 쌍을 보지 못했으므로 둘 다 원인은 보이지 않는다.
- 열린 항목 닫기: 다섯 모두 통과하면 release-record §2의 LAN-direct 항목을 이 근거로 닫는다. 통과 줄이 모두
  `native-host`나 `stats-host`이면 정제 경로는 기기에서 보지 못한 것으로 '확인하지 않은 것'에 남긴다.
- SFU로 간 공유: 소리가 났으면 결함이 아니라 안전한 끝이다(9.0.26과 같은 결과). 청취자의 `Receiver pair check … by <규칙>`
  줄과 공유자의 `Publisher pair check …`, `LAN route to … not proven at <단계> after N ms (<원인>; …)` 줄을 QA 라운드에 옮기고,
  항목은 열어 둔 채 다음 결정의 근거로 쓴다. 읽는 법(청취자의 `added`는 공유자의 `sent`와, 청취자의 `received`와 맞춰 읽음):

  | 청취자 줄                                                  | 공유자 줄                                     | 읽는 법                                                            |
  | ---------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------ |
  | `closed … by prflx-unrefined … added 1`                    | `not proven at receiver-proof … (deadline …)` | 정제가 공유자 시한보다 늦음. 다음은 증명 창에 대한 RO-20 오너 결정 |
  | `… by prflx-unrefined … received 0, added 0`               | `… candidates sent 0, refused 1 이상 …`       | 공유자가 mDNS 후보를 보내지 않음(A 4의 권한과 맞춰 읽음)           |
  | `… by prflx-unrefined … received 1, added 0`               | `… candidates sent 1 …`                       | 후보는 왔지만 더하기가 끝나지 않음                                 |
  | `… by refined-key-pending … added 1`                       |                                               | 통계에 상대 foundation이 없음(iOS 버전과 맞춰 읽음)                |
  | `… by prflx-still-listed …`                                |                                               | 같은 소켓·포트의 prflx 연결이 남음                                 |
  | `non-local … by native-address (native host/public to …)`  | `… proven`                                    | 청취자의 로컬이 전역 IPv6(남은 한계, 오너 결정 거리)               |
  | `non-local … by native-address (… to host/private-ipv4 …)` |                                               | WebKit이 mDNS 상대를 숫자 주소로 보임(남은 한계)                   |
  | `non-local … by native-type` 또는 다른 규칙                |                                               | 형과 규칙이 다른 원인을 말함                                       |

  청취자의 `[ProSysAudioSFU] Subscription to generation <g> ready <ms> ms after the share notice (start a, config b, session c, tracks d, offer e, track f, answer g, subscribed h)`
  줄에서 가장 오래 걸린 단계를 적는다(9.0.26 공유 1의 구독 약 5.4초의 까닭). `… failed at <단계> …`나
  `… failed before start (…)` 줄이 있으면 그 단계와 오류 이름을 적는다.

- 공유 도중 승격: LAN-direct로 시작한 공유에 뒤이어 `Publisher pair reproof to … <non-local|pending> by <규칙>`과
  `Promoted LAN-direct publication to SFU`가 있고 소리가 이어졌으면 결함이 아니다. 그 공유는 통과가 아니고, 줄의 규칙을 적는다.
- 사생활: 새 줄 어디에든 IP 주소, 포트, mDNS 이름(`….local`), 참가자 id 전체가 보이면 진단 줄의 결함이다(되돌리기 사유는
  아니고 앞으로 고친다). 그 줄은 QA 라운드에 옮기지 않고 종류만 적는다.
- 결함: 공유를 시작했는데 청취자가 10초 넘게 소리를 듣지 못하고 SFU로도 가지 않았거나(공유자의 `Published generation`과
  청취자의 `Subscription to generation … ready`가 없음), 공유가 시작되지 않거나, 소리가 공유 중에 멈춰 돌아오지 않는 일이
  두 번 이상이면 이 열차의 결함이다. 한 번이면 그 공유만 한 번 다시 한다.

### 실패하면 (배포 직후 확인)

이 소절도 건네지 않는다. 판정 기준의 결함이면 이 열차가 LAN-direct 소리를 깨뜨린 것이다. 그 결함은 HTTP smoke를 지나 커밋
표지를 지났고 실패 자동 복구는 돌지 않았으므로(위 '되돌리기') 손으로 한다:

1. App을 이 릴리스 recovery checkpoint의 App(dispatch 때 live였던 App, 9.0.26 `b8dc4281`)으로 되돌린다.
   hotfix-procedure의 [Rollback](../hotfix-procedure.md#rollback) CLI 되돌리기다(`versions deploy <그 버전 ID>@100%`,
   `--config cloudflare/wrangler.app.toml`, message `Rollback: <이유>`). 저장 바닥이 795인 동안 `lower`는 필요 없다.
2. PRO Worker와 다른 Worker는 그대로 둔다(release-record §4 현재 경계).
3. release-record §1과 `Last source review`를 덮어쓰고 `release-history.md`에 한 행을 더한다.
4. 앞으로 고친다. 되돌린 App 버전은 `Rollback:` 메시지라 git 출처가 없으므로 다음 수리 릴리스는 `all`이다
   ([hotfix-procedure의 출처 문단](../hotfix-procedure.md#normal-hotfix)).

SFU로만 가는 것, 진단 줄의 사생활 결함, 키보드 포커스의 결함(포커스가 채팅 밖으로 떨어짐 등)은 되돌리기 사유가 아니다.
소리가 나는 한 기본 되돌리기(더 높은 SemVer의 코드 되돌리기)나 앞으로 고치기로 다룬다.

## 확인하지 않은 것

- 실기기 LAN-direct: 이 열차의 수정은 Windows에서 소스 읽기와 Playwright Chromium 153 재현(받는 쪽 원래 쌍이 끝까지
  host/mdns → prflx/redacted, 통계는 후보 추가 약 60 ms 뒤 host→host)으로만 봤다. Windows의 Playwright WebKit에는
  `RTCPeerConnection`이 없어 시험의 WebKit 모양 통계는 본뜬 것이다. 실제 iOS가 정제를 공유자의 증명 시한 안에 마치는지,
  어떤 iOS가 통계의 상대 foundation이나 `transportId`를 빼는지, libwebrtc가 consent 확인 동안 선택 쌍을 in-progress로
  표시하는지(소스 읽기)는 재지 않았다. 브라우저 시험(E2E)에는 PRO LAN-direct 행이 없다.
- 남은 원인(고치지 않음, 줄로만 가름): 공유자가 mDNS 후보를 보내지 않음(출처가 카메라나 마이크 권한을 가지면 Chromium이
  숫자 주소 후보를 모음), iPhone이 이름을 늦게 풀거나 못 품, Safari가 mDNS 상대를 숫자 주소로 보임, 청취자의 로컬이 전역
  IPv6. 통제 측 공유자가 증명 뒤 다른 쌍으로 재지명하는 것은 수신자가 다시 증명하지 않는 기존 한계다.
- SFU 대체 지연: 정제되지 않은 host→prflx 쌍이 공유자의 증명 창 끝까지 기다려 SFU 대체가 최대 약 1초 늦어지는 것은
  코드 읽기와 단위 시험으로만 봤고 기기에서 재지 않았다. 받아들일지는 열린 오너 질문이다('오너 결정', '배포 조건과 순서' 5).
- 섞인 버전: 9.0.26과 9.0.27 사이의 경로는 단위 시험의 모의 끝으로만 봤다.
- 실기기 포커스: 실제 휴대폰·태블릿의 바깥 키보드, 화면 낭독기(VoiceOver, TalkBack, NVDA), WebKit E2E 레인(Tab 순환 행만
  임시 설정으로 돌림), Chromium 79 TV. 사진은 Windows Chromium이다. 메시지 안의 컨트롤로 연 창이 열린 채 그 메시지가
  지워지는 경우는 해 보지 않았다.
- 화면이 바뀌는 후보(고치지 않음, 오너 사진 먼저): 넘친 메시지 목록에서 Tab으로 간 말풍선이 화면 밖에 남음, YouTube 창의
  검색 버튼에서 Enter를 누르면 버튼이 비활성되며 포커스가 페이지로 떨어짐. 미디어 소스와 YouTube URL 창의 Tab 후보 거르기는
  지금 결함이 없지만 같은 모양으로 단단히 할 수 있다(동작은 그대로).
- 버전 올리기와 그 뒤 가드, PR CI, 자동 코드 리뷰, exact-main CI, Linux, 커버리지 레인, `check:worker-bundles`, 보안 검사,
  `test:e2e:candidate`, 전체 직렬 E2E, PRO 시스템 오디오 E2E 묶음.
