## 왜 고쳤나

2026-10-22 자원 소유권 조사에서 페이지 이동(재설정, 문서 재로딩, 뒤로 가기 캐시, 나가기 경고)과
화면 셸(전체 화면, 재생목록 조작, 계정 신호)은 같은 자원을 여러 흐름이 따로 다루는 곳이었다.
[자원 소유권 장부](resource-ownership-registry.md)의 RO-22~RO-30이 그 기록이다. Phase 2는 각 자원에
주인 하나를 두고, 오너가 정한 규칙(로드맵의 Phase 2 오너 결정 1~13)으로 그 사이의 어긋남을
정리한다. 오너가 운영 이전 확인 중 발견한 문제(이전 링크가 항상 PIN을 묻고, 같은 PIN을 거절해 이전
주인의 PIN을 드러냄)도 같은 묶음에 싣는다.

## 바뀐 것

### 페이지 이동 (C6-1, 3, 4, 5, 6, 7, 8, 11, 12, 13, 14)

- **주인 하나:** `src/core/session-reset.ts`가 이동 상태(`idle`, `painting`, `navigating`, `left`)와 정확히
  한 번 끝나는 정리, 재로딩 대기열, 페이지 전환(`pagehide`, `pageshow`, 화면 보임) 처리를 모두 가진다.
  `document-reload.ts`는 PRO 링크 보호(claim fence)만 남는다. 홈 이동과 방 시작 화면 복귀는 각각
  의도 하나(`navigateHome`, `returnToRoomStart`)로 모였다. 시간 값과 다음 문서 표지는
  `navigation-contract.ts`가 이름을 갖는다.
- **재로딩 바쁨 규칙(결정 1, 13):** 다른 이동 중, 다른 재로딩 뒤, 실패한 재로딩 뒤의 재로딩 요청이 모두
  기다렸다가, 앞 이동이 이 문서에서 끝나면 실행된다. 같은 안내 문구의 요청은 하나로 합친다.
  **사용자 영향:** 예전에는 버려지던 재로딩이 이제 실행된다.
- **캐시 복귀(결정 13):** 뒤로 가기 캐시로 돌아온 페이지가 어차피 재로딩하면 대기 중인 재로딩은 버려 두 번
  재로딩하지 않는다. 버린 요청의 호출자는 그 재로딩이 페이지를 잡거나 PRO 링크 보호 뒤 대기열 맨 앞에 선 뒤
  한 번 응답을 받는다. 캐시 복귀가 재로딩하지 않는 경우(방 밖이고 진행 중인 이동이 없을 때, 한 번 허용된
  재시도를 이미 쓴 두 번째 복귀)에는 대기 재로딩을 버리지 않고 예전처럼 한 번 실행한다. 원래 결정은 "대기
  재로딩을 버린다"였지만, 이 두 경우는 결정의 이유("캐시 복귀 재로딩이 어차피 새로고침한다")가 맞지 않아
  요청한 재로딩이 1번에서 0번이 되므로 좁혔다.
- **이동 마감(결정 2):** "이동 완료" 2초 마감이 실제 이동 직전부터 시작된다. 로고 재설정은 SW 승격을
  최대 2.5초 기다린 뒤 처음 화면으로 간다. **사용자 영향:** 예전에는 승격이 늦으면 아무 일도 없었다.
- **나가기 경고 면제(결정 3):** 하나의 공유 플래그 대신 면제마다 따로 붙잡고 놓는다. 재설정이 복구돼도
  진행 중인 구글 로그인 이동의 면제를 지우지 않고, PRO 링크 보호 뒤에서 막힌 캐시 복귀 재로딩이 나가기
  경고를 꺼 두지 않는다.
- **재설정 화면 순서(결정 4, 13):** 재설정 화면이 대화상자 위에 있고 대화상자는 그 아래에서 조작되지 않는다.
  전체 화면 중에는 전체 화면을 빠져나가지 않고 그 안에 뜬다.
- **뒤로 가기 다시 걸기(결정 5):** 이동이 복구되면 뒤로 가기 보호가 자동으로 다시 걸린다.
- **이동 가드(결정 7):** `scripts/check-navigation-sinks.mts`가 이동을 일으키는 코드 위치를 고정한다.
  언어 바꾸기 이동은 이유와 함께 허용 목록에 있다. 게스트 화면 뒤로 버튼은 push를 유지한다(결정 6).

### 전체 화면 (C8 I2, I5, I6, I8, I9, I13)

- 도우미가 `src/core/fullscreen.ts`로 옮겨 왔다(결정 8). 나가기는 이 파일 한 곳에서만 하며, 화면 보호기와
  YouTube가 함께 쓰는 "진행 중인 나가기 하나"를 둔다. 같은 요소의 두 번째 나가기는 앞의 것에 합류한다.
- **결정 9 ①, 12:** 화면 보호기가 전체 화면을 닫는 동안 YouTube 전체 화면 버튼은 흐려지고(불투명도 0.15,
  최대 1.5초) 탭을 받지 않다가, 나가기가 끝나면 돌아온다. YouTube가 연 나가기는 버튼을 막지 않는다.
- **결정 9 ②, 12:** YouTube도 화면 보호기와 같은 규칙으로 들어온 방식대로 나간다(표준 전체 화면이면 표준,
  아니면 webkit). 나가기를 일찍 끝내는 오류도 자기 나가기 방식의 오류만 본다. 구형 iPad 위험은 오너가
  수용했고 이 항목의 iPad 확인은 면제됐다. 접두어 전체 화면 삭제(C8-I0)는 이 묶음에 없다.
- 옛 WebKit에서 전체 화면 요청의 시간 제한이 방 나가기로 지워지던 문제(I6), 옛 WebKit 판정(I5)을 고쳤다.

### 재생목록 (C8 I3, I7, I11, I12, 결정 10·11)

- 끌기 자동 스크롤·행 움직임·동작 줄이기를 지연 로딩 모듈 하나로(I3), 조작 상태 판단을 관문 하나로(I7)

  기본 문구 쓰기를 정리했다.

### 이전에서 바뀐 것

#### PRO Worker (방 Durable Object)

- PREPARE 본문은 `{claimToken, requestId}`이다. 결정 전 앱이 보내는 `newPin`도 받는다.
  모양(8자리 숫자)은 예전처럼 검사하고 값은 쓰지 않는다. `OWNER_TRANSFER_PIN_REUSE`를
  지웠고, PREPARE에서 PIN 해시(PBKDF2)도 만들지 않는다. PIN pepper 설정 확인은 남겼다:
  열린 방이라도 세션 생성에 필요하므로, 없으면 예전처럼 PREPARE가 아무것도 지우기 전에
  503 `SERVICE_NOT_CONFIGURED`로 거절한다.
- 재생(같은 `requestId`)은 같은 링크·같은 계정·같은 요청 ID로만 맞춘다. PIN 비교와
  `OWNER_TRANSFER_REPLAY_MISMATCH`가 없어졌다. 대기 중인 이전과 완료된 이전 모두 같다.
- 새 대기 레코드에는 `pin`이 없다. 결정 전 PRO Worker가 쓴 레코드(`pin` 있음)는 저장된
  그대로 읽고, 재생하고, 커밋한다. 그 PIN은 쓰지 않는다. 모양이 깨진 옛 `pin`은 예전처럼
  레코드를 무효로 만든다.
- 커밋은 `turnEntryPasswordOff`로 암호를 끈다(`passwordRequired: false`, PIN 기록 없음).
  오너가 방 설정에서 암호를 끌 때와 같은 함수·같은 상태다(그 설정도 이 함수를 쓰게
  바꿨다). PREPARE는 그대로다: 모든 세션을 지우고, 대기 중에는 정지 상태에서
  `passwordRequired: true`로 닫혀 있다.
- 커밋 경로를 `withEntryPolicyResponse` 안에서 돌린다. App이 브라우저의 opt-in 헤더를
  넘기면 이전 응답 스냅샷에 활성화 응답과 같은 추가 필드(`passwordRequired`,
  `playlistSlots`)가 붙는다. 헤더가 없으면 v1 모양 그대로다.

#### App Worker (facade)

- 이전 본문을 `newPin` 없이 받는다. 결정 전 앱의 3키 본문(`newPin` 포함)도 같은 모양 검사로
  받는다. 사가 의도 기록에는 본문 해시가 없어 바뀐 것이 없다.
- 커밋 호출에 브라우저의 opt-in 헤더 두 개(`X-MXQR-Pro-Entry-Policy: optional-v1`,
  `X-MXQR-Pro-Playlist-Slots: v1`)를 정확한 값일 때만 넘긴다. 전에는 이전 응답 스냅샷에
  `passwordRequired`가 없어서, 앱은 이를 "암호 켜짐"으로 읽었다(`passwordRequired !== false`).
  암호를 끄는 지금은 새 소유자의 설정이 실제와 반대로 보였을 것이다.

#### 브라우저 앱

- 이전 링크는 로그인 뒤 바로 이전을 요청한다. 복구 링크처럼 묻는 창이 없다. 확인 창은 더하지
  않았다: 링크가 대상 계정에 묶여 있고 서버가 계정을 확인하며, 받는 사람이 링크를 연 것이
  곧 의사 표시다. 새 문구는 없다.
- `TransferProRoomOwnerInput`과 요청 본문에서 `newPin`을 뺐다.
- 쓰이지 않게 된 `pro.transfer_title`·`pro.transfer_message`를 42개 로케일과 i18n 키
  목록 테스트에서 지웠다(로케일당 2키, 124줄).
- 오류 안내는 바꾸지 않았다(아래 점검).

### 이전 때 접속해 있던 사람

추가 조치는 없다. PREPARE가 이미 이전 소유자, 위임 관리자, 일반 참여자의 세션을 모두
지운다(권한 경계이므로 바꾸지 않았다). 커밋 뒤에는 암호가 꺼져 있으므로 그 사람들은 방
코드만으로 일반 참여자로 다시 들어온다. 이전 소유자의 계정·소유자 쿠키도 일반 참여자가
될 뿐이다. 기준으로 삼은 "암호 끄기" 설정은 접속한 사람을 그대로 두고 권한을 더 주지
않는다. 이전은 그 전에 모두 내보냈으므로, 끄는 시점에 남아 있는 사람이 없다. 이전으로
내보내진 세션에는 예전처럼 퇴장 사유가 붙지 않는다.

### 오류 안내 점검

PIN과 관련된 거절 두 가지(`OWNER_TRANSFER_PIN_REUSE`, `OWNER_TRANSFER_REPLAY_MISMATCH`)가
사라져, 소비되지 않은 링크에 PIN 때문에 "새 링크 요청" 안내가 뜨는 경우는 없다. 남은
이전 응답의 안내는 다음과 같고, 바꾸지 않았다.

| 응답                                                                                                             | 링크 소비 | 안내                                                                                                 |
| ---------------------------------------------------------------------------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------- |
| `OWNER_TRANSFER_CLAIM_INVALID`·`_EXPIRED`·`_STALE`·`_USED`, 404, 410                                             | 사용 불가 | 링크 만료·사용됨, 새 링크(정확)                                                                      |
| `OWNER_TRANSFER_TARGET_ACCOUNT_MISMATCH`                                                                         | 아니요    | 이 계정으로는 사용할 수 없음(정확)                                                                   |
| `ACCOUNT_PRO_ROOM_LIMIT_REACHED`                                                                                 | 아니요    | 계정 연결 한도(정확)                                                                                 |
| 5xx·시간 초과·`PRO_ROOM_TRANSFER_RECONCILIATION_REQUIRED`                                                        | 모름      | 같은 요청 ID로 다시 시도(정확)                                                                       |
| `RATE_LIMITED`                                                                                                   | 아니요    | 새 링크 요청. 링크당 요청 ID 10개 한도면 정확, IP 한도(1시간)는 링크 수명(10분)보다 길어 사실상 정확 |
| `OWNER_TRANSFER_TARGET_UNAVAILABLE`(커밋 전 대상 계정 비활성)                                                    | 예        | 새 링크 요청(정확)                                                                                   |
| `OWNER_TRANSFER_UNAVAILABLE`·`_TARGET_UNCHANGED`·`_CLAIM_CAPACITY_EXCEEDED`·`OWNER_AUTHORITY_PROJECTION_PENDING` | 아니요    | "새 링크 요청". 관리자에게 알리는 것은 맞지만 새 링크로 풀리지 않는 경우가 있다                      |

마지막 줄은 그대로 둔 한계다. 방이 이전할 수 없는 상태이거나, 링크를 연 계정이 이미
소유자이거나(링크 수명 10분 안에 다른 경로로 소유자가 된 경우), 이전 소유자 계정 삭제 정리가
끝나기 전인 경우다. 이 셋은 링크 발급 때 이미 막히므로 링크 수명 안에 방 상태가 바뀔 때만
생긴다. 사용한 링크 기록 128개 한도는 이전 하나가 끝나기 전에는 다음 링크를 발급하지
않으므로 사실상 닿지 않는다. 정확한 안내에는 새 문구(42개 언어)가 필요해 이번 범위에서
빼고 남겼다.

### 호환성과 배포 순서

- **target `all`, PRO room 먼저.** release.yml은 `all`에서 PRO room을 먼저, App을 마지막에
  배포한다. 새 App Worker·앱은 `newPin` 없이 보내는데, 옛 PRO Worker는 그 본문을 400
  `INVALID_REQUEST`로 거절한다. 그래서 새 앱이 옛 서버를 만나지 않게 PRO가 먼저 올라가야
  한다. 두 Worker 소스가 함께 바뀌어 부분 릴리스 게이트도 단독 배포를 막는다.
- **배포 창과 캐시된 옛 앱.** 옛 앱은 계속 "새 8자리 암호를 설정해 주세요" 창을 띄우고
  `newPin`을 보낸다. 새 PRO는 그 값을 쓰지 않고 방은 열린 상태로 끝난다. 옛 앱(8.8.0 이후)은
  opt-in 헤더를 보내므로, 새 App Worker를 거치면 설정에 "암호 꺼짐"이 바로 보인다. PRO와 App
  배포 사이 몇 분 동안 옛 App Worker를 거치면 응답 스냅샷에 `passwordRequired`가 없어 설정이
  "켜짐"으로 보이고, 다음 스냅샷(리비전이 바뀔 때)에 고쳐진다. 실제 입장 정책은 처음부터
  꺼짐이다.
- **저장 레코드.** 옛 PRO가 쓴 대기 레코드는 새 PRO가 그대로 처리한다(테스트로 고정).
  완료 레코드 모양은 그대로다. 방 상태의 `passwordRequired: false`/`pin: null`은 8.8.0
  선택형 입장 암호 계약이 이미 아는 모양이다. 반대 방향은 그렇지 않다. 새 PRO가 쓰는
  `pin` 없는 대기 레코드를 옛 PRO는 무효로 버린다. 그래서 아래 계약 표지를 올렸다.
- **계약 표지.** `cloudflare/pro-room-entry-policy-contract-version.txt`를
  `pro-room-optional-entry-password-v1+pro-owner-transfer-pinless-v1`로 올렸다(`ff0b6d14`).
  9.0.0이 시스템 오디오 표지에 `heartbeat-state-v1`을 붙인 방식과 같다. release와 독립
  recovery 워크플로가 이 표지를 이미 읽고(`pro-room-entry-policy-forward-floor`), 그 floor는
  PRO room과 App을 함께 묶는다. 이 릴리스의 PRO나 App 후보가 기준선을 한 번이라도
  대체했거나 지금 버전을 읽지 못하면, 자동 복구는 둘을 되돌리지 않고 후보에 남긴다
  (`forward-repair-required`). 후보가 올라가기 전에 실패한 릴리스와, 기준선이 이미 이
  표지를 가진 이후 릴리스는 예전처럼 되돌린다. 표지가 바뀐 커밋은 target `all`만 배포할
  수 있고(release.yml의 PRO 입장 정책 `all` 요구 단계), 로컬 긴급 배포는 표지 변경을 넘지
  못한다(code-only 경계).
- **되돌리기는 앞으로 고치기로.** 후보가 올라간 뒤에는 PRO와 App 어느 쪽도 이 표지 아래로
  손으로도 되돌리지 않고 target `all`로 앞으로 고친다. 옛 PRO는 `pin` 없는 대기 레코드를
  버려 진행 중인 이전의 방을 `ownership_transfer_pending` 정지로 남기고, 재시도도 크론도
  그 이전을 끝내지 못해 관리자가 새 이전 링크를 발급해야 한다. 또 새 앱의 `newPin` 없는
  본문을 400 `INVALID_REQUEST`로 거절해 이전 링크가 막힌다(링크는 소비되지 않는다). 옛
  App facade도 캐시된 새 앱의 본문을 400으로 거절한다.
- 새 비밀·바인딩·D1 스키마·의존성 없음. 통신 형식 변화는 PREPARE 본문의 `newPin`이
  선택이 된 것과, opt-in 헤더가 있을 때 이전 응답 스냅샷에 추가 필드가 붙는 것뿐이다.

  있는·없는 대기 레코드 재생과 커밋, PIN pepper가 없으면 아무것도 지우지 않고 503, 모양이

  Worker 빌드에는 그 시절 앱의 PIN), 앱·API·세션 컨트롤러 테스트.
- **계약 표지(`ff0b6d14`).** Codex 리뷰(P2): 새 PRO가 올라간 뒤 릴리스가 실패하면 자동
  복구가 옛 PRO를 되살려, 진행 중인 이전의 `pin` 없는 대기 레코드를 버리고 방을 정지로
  남길 수 있었다. 보고서의 수동 확인 메모는 자동 복구가 읽지 않는다. release-deployment-state
  테스트를 먼저 고쳤다. 빨강: `30097d5b`에서 2개 실패(표지가 그대로). 표지 파일만 올린
  상태에서도 2개 실패: release.yml에 PRO 입장 정책 `all` 요구 단계가 없었고, 워크플로가
  부르는 CLI가 옛 표지 내용을 요구해 아직 올라가지 않은 릴리스까지 `true`(항상 앞으로
  고치기)로 판정했다. 초록: 임시 git 저장소에서 PIN 기준선(`pro-room-optional-entry-password-v1`)
  위의 `all` 릴리스가 PRO 후보를 올린 뒤 실패하면 floor `true`, 복구 계획이 `pro-room`·`app`을
  건너뛰고, rollback 보고서 `forward-repair-required`(PRO `skipped-compatibility-floor`, 나머지
  `already-restored`, 복구 명령 없음), 최종 경계 검증 `verified`다. 버전을 읽지 못해도
  `true`다. 후보가 올라가기 전 실패는 floor `false`, 건너뛰기 없음, 보고서 `succeeded`다.
  기준선이 이미 표지를 가진 이후 릴리스는 올라간 PRO 후보를 `restored`로 되돌린다.
  워크플로 CLI는 새 표지에서 `false`, 표지 없는 릴리스에서 `true`다. 릴리스 도구 14개
  파일 282개 테스트 통과(병렬 부하에서 `ci-quality-gates` 1개가 15초 시간 초과, 단독 재실행
  17/17 통과), typecheck·lint·format:check·자원 소유 가드 통과, 전체 단위 629개 파일
  14,230개 통과(`--maxWorkers=6`, 문서 포함 트리). Worker 프로필과 실제 릴리스 실패 복구는
  돌리지 않았다.
- 실기기와 운영 이전은 확인하지 않았다. 묶음 배포 뒤 테스트 방에서 이전 링크가 암호를 묻지
  않는지, 새 소유자 설정에 암호가 꺼짐으로 보이는지, 그 자리에서 암호를 켤 수 있는지, 이전 때
  있던 참여자가 코드만으로 다시 들어오는지를 본다. 옛 앱이 캐시된 기기의 PIN 창(값 무시)도
  한 번 확인한다.

## 묶음 호환성

- 통신 형식, D1, 비밀값, 바인딩, 의존성은 그대로다. 예외는 이전 절의 PREPARE 본문(`newPin` 선택)과

  고친다([호환성과 배포 순서](#호환성과-배포-순서)). 표지가 바뀌므로 target `all`(PRO 먼저)만 된다.
- 업데이트 적용 때의 재로딩이 새 이동 주인을 거친다. 옛 버전(9.0.3)에서 이 묶음으로 넘어가는 적용은 옛
  코드가 하고, 새 주인이 하는 적용은 다음 배포 때 처음 운영에서 돈다. 갈래에서 v771→v772 빌드로 헤드리스
  Chromium 적용을 확인했다.
- 옛 탭과 새 탭, 이벤트 페이지는 같은 계정 신호를 그대로 주고받는다(9.0.3 탭 코드를 고정한 테스트).
- 첫 로딩 JS는 478.0 → 478.7 KiB(gzip)이다. 로드맵 목표(+0.2 KiB)를 넘었지만 오너가 수용했고 예산은
  통과한다(결정 13).

## 한계와 실기기 확인

jsdom과 헤드리스 Chromium(일부 WebKit iPhone 에뮬레이션) 결과다. 실제 뒤로 가기 캐시 순서, 설치한
앱, iOS·TV 기기, 운영 이전은 확인하지 않았다. 배포 뒤 다음을 본다.

- iPhone Safari: 방에서 다른 페이지로 갔다가 뒤로 가기 캐시로 돌아올 때 재로딩이 한 번만 일어나는지.
- 홈 화면에 설치한 앱: 뒤로 가기, 구글 로그인 완료 뒤 돌아오기.
- 로고 재설정: SW 업데이트가 걸린 상태에서 2.5초 안에 처음 화면으로 가는지.
- 전체 화면: 화면 보호기를 연 채 방장이 YouTube로 바꾸고 전체 화면 버튼을 누르면 1초 남짓 흐려졌다가
  다시 누를 수 있는지. YouTube 전체 화면에서 뒤로 가기, 전체 화면 중 다음 트랙(로컬 파일). iPhone의
  가짜 전체 화면과 뒤로 가기. TV 빌드 전체 화면.
- 재생목록: 편집 모드에서 끌어 놓자마자 삭제(방장, 일반방 게스트 관리자). 끌기 도중 시스템 오디오 시작.
- PRO 소유권 이전: 테스트 방에서 링크가 PIN을 묻지 않는지, 새 소유자 설정에 암호 꺼짐이 보이고 켤 수
  있는지, 이전 때 있던 참여자가 코드만으로 들어오는지, 옛 앱이 캐시된 기기의 PIN 창(값 무시).
