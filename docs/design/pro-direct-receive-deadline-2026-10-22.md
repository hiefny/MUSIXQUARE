## 왜 고쳤나

9.0.1은 PRO SFU 수신에서 게스트 쪽 30초 수신 감시를 빼고, 구독과 재시도가 마감을
맡게 했다. PRO 같은 네트워크 직접 연결(LAN-direct) 수신은 그 감시를 그대로 썼다.
감시가 울리면 수신 대기 화면이 사라지는데, 코디네이터의 구독 키는 그대로라 같은
공유를 다시 시작하지 않았다. 그 뒤 늦게 온 직접 연결 트랙은 붙을 곳이 없어 소리 없이
남았다(늦게 들어온 청취자, 잠들었던 배포자 페이지 등). 구조 개선 계획의 수정 레인
G5이고, [자원 소유권 장부](resource-ownership-registry.md)의 시스템 오디오 수신 슬롯
기록과 같은 원칙(시도마다 마감 주인 하나)을 따른다.

## 바뀐 것

- PRO LAN-direct 경로도 게스트 감시 없이 수신 대기에 들어간다
  (`beginTrustedSystemAudioReception(..., { receiveWatchdog: false })`). 늦게 온 트랙도
  같은 수신 대기에 붙는다.
- 마감은 코디네이터가 가진다. 공유마다 게스트 수신 시간
  (`SYSTEM_AUDIO_RECEIVE_TIMEOUT_MS`, 게스트 모듈에서 가져오며 다시 적지 않는다) 안에
  트랙이 붙지 않으면 "연결이 불안정" 알림을 발행 세대마다 한 번 보여 주고, 수신 대기는
  유지한다. 트랙이 붙거나, 경로 실패(이미 따로 알림), 공유·상태 변경, 강제 중지, 나가기,
  정리 때 마감을 취소한다. 강제 중지 뒤에 온 트랙은 붙이지 않는다(기존 오너 결정).
- 9.0.1 보고서의 "PRO 같은 네트워크 직접 연결은 감시를 유지한다"는 이번 열차로 바뀌었다.
- 소유권 가드의 "감시를 켠 수신 시작" 기준선에서 LAN-direct 항목을 지웠다(3곳 → 2곳).
  이 경로가 다시 감시를 켜면 가드가 실패하고, 가드 테스트가 그 경우를 확인한다. 장부의
  RO-04 마감 주인과 상태도 맞췄다.

## 그대로 둔 것

- 같은 발행 세대 안에서 알림이 두 번 나올 수 있는 경로가 있다. 직접 연결 경로는 활성화가
  끝날 때마다 실패 알림 기록을 지우고, 하트비트 재조정이 활성화를 다시 돈다. 이 동작은
  9.0.1 이전부터 있었고, 그때는 수신 실패와 연결 불안정이 따로 나왔다.
- PRO SFU 재시도마다 재생 정지 처리와 수신 시작 알림이 다시 도는 문제(G6)는 다음 열차다.

## 호환성

통신 형식, 저장 레코드, D1, 비밀값, 바인딩 변경 없음. 브라우저 앱과 App Worker의 관리자
버전 표기만 바뀌므로 target `app`이다.

## 검증과 한계

- 재현: 새 테스트 4개 중 3개(34초 뒤 도착한 직접 트랙, 3분간 제안 없음, 경로 실패)가
  `c08b6c39` 소스에서 실패하고 수정 후 통과했다. 강제 중지 테스트는 양쪽에서 통과하는
  보호 테스트다. 보완(코디네이터 마감)은 두 테스트가 수정 전 실패했고, 트랙이 마감 전에
  붙거나 공유가 먼저 끝나면 알림이 없다는 테스트를 더했다.
- 검토: 회귀, 테스트 타당성, 소유권·설계 세 관점이 G5와 보완 모두 1라운드에서 승인했다.
- 전체 검사(`6097666b`, 로컬): 타입 검사, lint, 서식, 빌드 통과. 단위 테스트 619개 파일
  13,927개 통과. 가드(dead-exports, bus-pairing, import-graph, lifecycle-writes,
  release-identity, sw-cache-version, resource-ownership) 통과. 핵심 브라우저 검사 59개
  통과(Chromium). 로컬 결과는 정확한 main SHA 배포 후보를 대신하지 않는다.
- 실기기는 확인하지 않았다. PRO 방에서 LAN-direct로 늦게 들어온 청취자와 잠들었던 배포자
  페이지가 실기기 확인 항목이다.
