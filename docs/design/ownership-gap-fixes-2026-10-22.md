## 왜 고쳤나

한 자원을 서로 다른 흐름 둘 이상이 각자 진행 상태를 들고 조작하는 곳을 `1bd9cd6f`에서
7개 영역으로 나눠 조사했다. 그중 코드를 읽어 틈이 확인된 4건을 고쳤다. 각 틈은 먼저
기준 코드에서 실패하는 테스트로 재현했고, 고친 뒤에는 서로 다른 관점의 독립 검증자
세 명(회귀, 테스트 타당성, 소유권·설계)이 반박을 시도했다. 검증자가 찾은 문제는
고친 뒤 다시 검토했고, 마지막 라운드에서 네 건 모두 세 명 전원이 승인했다.

## 바뀐 것

### G1. PRO 시스템 오디오 수신이 30초마다 실패로 떨어짐 (9.0.0 회귀)

- 증상: PRO 방에서 공유 음원 구독이 계속 실패하면, 약 1분 뒤부터 30초마다 "수신 실패"
  알림이 뜨고 대기 상태로 떨어졌다가 다시 수신 대기로 돌아왔다. 30초보다 오래 걸린 뒤
  성공한 연결은 아무 데도 붙지 않아 소리 없이 남았다.
- 원인: 9.0.0이 구독 재시도 간격을 2.5초 고정에서 2.5초→30초 백오프로 바꿨다. 그런데
  재시도마다 수신 대기 화면에 들어가면서 게스트 쪽 30초 수신 감시도 다시 걸었다.
  재시도 간격이 감시 시간에 닿자 감시가 먼저 울렸다.
- 수정: PRO SFU 경로는 게스트 감시 없이 수신 대기에 들어간다
  (`beginTrustedSystemAudioReception(..., { receiveWatchdog: false })`). 마감은 구독과
  백오프 재시도가 맡고, 실패 알림은 발행 세대마다 한 번("연결이 불안정") 그대로다.
  일반 방과 PRO 같은 네트워크 직접 연결은 감시를 유지한다.
- 보완: 통합 검토에서, 구독 요청이 나가기 전에 바로 거절되는 경로(기기 시계가 공유
  만료 시각을 이미 지난 것으로 볼 때)는 실패 신호가 없어 감시도 재시도도 없이 수신
  대기에 남는다는 점을 찾았다. 이 거절도 일반 실패와 같은 재시도 경로를 타게 했다.
  처음 구독, 재시도, 하트비트 재조정, 이미 연결된 구독의 재조정 모두에 적용된다.

### G2. 화면 복귀 직후 게스트의 YouTube 일시정지가 풀림

- 증상: 일반 방 게스트가 화면으로 돌아온 뒤 약 10초 안에 직접 일시정지하면, 복귀
  재정렬 재시도가 다시 재생을 걸었다.
- 원인: 복귀 재정렬 흐름(`background-return-sync.ts`)은 재시도 사이에 사용자의
  일시정지를 보지 않았고, 재정렬은 일시정지 방지 장치를 통과해 재생한다.
- 수정: 이미 다른 재합류 흐름을 멈추는 같은 일시정지 의도
  (`'youtube:set-local-paused'`)를 받으면 재시도를 끝낸다. 보이는 상태에서 게스트가
  iframe으로 직접 누른 일시정지도 이 의도를 낸다. 숨은 상태에서 브라우저가 멈춘 것,
  실패한 재생 뒤 되돌려 놓은 일시정지, PRO 참여자는 일시정지 표시만 남긴다.
  처음 두 시도안(일시정지 표시를 그대로 보기, 표시에 세대 번호 달기)은 검증자가
  각각 브라우저 정지·되돌린 일시정지와 구분하지 못한다는 반례를 찾아 버렸다.

### G3. PRO 일시정지 직후 소리가 잠깐 샘

- 증상: PRO 방에서 일시정지를 누른 직후, 서버 확정 전에 다른 전환이 들어오면 소리가
  잠깐 났다.
- 원인: 일시정지를 누르면 서버 확정 전까지 iframe을 음소거하는데(일시정지 게이트),
  직접 커밋 경로만 이 게이트를 지켰다. 권한 준비(authority-arm) 경로는 마스터 볼륨만
  보고 음소거를 풀었다.
- 수정: 게이트를 권한 준비가 되살릴 오디오 상태에 포함했다. 준비 요청, 볼륨 변경,
  일시정지 대기 시작과 확정 네 곳 모두에서 반영한다.

### G4. 세션 리셋이 화면 잠금을 직접 써서 화면 전체가 잠긴 채 남을 수 있음

- 증상: 리셋 중 대화상자가 열리고 페이지 이동이 끝나지 않으면, 대화상자를 닫은 뒤
  화면 전체가 눌리지 않는 상태로 남을 수 있었다.
- 원인: 세션 리셋이 `inert`를 직접 켜고 되돌렸다. 모달 스택과 채팅은 주인 장부로
  잠금을 관리하는데 리셋만 장부를 거치지 않아, 장부가 리셋의 잠금을 "원래 잠김"으로
  기억했다.
- 수정: 장부를 `src/core/inert-ownership.ts`로 옮기고 리셋도 자기 주인 키로 잠그고
  푼다. 리셋은 `inert`만 잡고 `aria-hidden`은 창들이 계속 쓴다. 리셋이 풀린 뒤
  `app.ts`가 주입한 처리기가 모달 스택을 다시 계산하고, 창이 덮고 있는 대상에는
  포커스를 되돌리지 않는다. 모달 스택은 리셋 안내 화면을 잠그지 않는다(리셋 중에
  열린 창이 안내 문구를 가리거나 포커스를 막지 않도록).

## 그대로 둔 것

- G1: PRO SFU 수신 대기 자체에는 별도 마감이 없다. 각 SFU 제어 요청의 15초 제한과
  실패 시 재시도로 묶여 있고, 공유가 끝나면 코디네이터 상태가 수신 대기를 정리한다.
  그래서 시계가 서버보다 크게 앞선 기기는 9.0.0처럼 30초 뒤 대기 상태로 떨어지지
  않고, 공유가 끝날 때까지 알림 한 번과 함께 수신 대기에 머문다. 만료 비교를 서버
  시각 기준으로 바꾸는 일은 이번 범위 밖이다. PRO 같은 네트워크 직접 연결 경로에는 30초 감시 뒤 소리
  없이 남는 같은 모양이 있고, 재시도마다 재생 정지 처리를 다시 도는 동작도 9.0.0 전부터
  있다. 둘 다 후속 수정 후보로 남기고 [릴리스 기록](../release-record.md)의 9.0.1 열린
  항목에 적었다.
- G2: 보이는 상태의 iframe 일시정지는 이제 잠금 화면 일시정지와 같은 효과(대기 중인
  재합류·자동 동기화 취소)를 낸다. iOS가 숨은 iframe의 정지 콜백을 화면이 보인 뒤에
  늦게 보내면 사용자 일시정지로 처리될 수 있는데, 실기기에서 확인하지 않았다.
- G3: "PRO iframe이 원하는 오디오" 계산이 여러 곳에 있다. 하나로 모으는 일은 이번
  수정 범위 밖이다.

## 호환성

통신 형식, 저장 레코드, D1, 비밀값, 바인딩 변경 없음. 바뀌는 것은 브라우저 앱과 App
Worker의 관리자 버전 표기(`cloudflare/app-worker.ts`)뿐이고 둘 다 `app` 대상에 속한다.
다른 Worker의 런타임 입력은 바뀌지 않으므로 target `app`, Developer API D1 끔이다.
구버전과 섞인 방에서도 각 기기의 로컬 동작만 달라진다.

- 재현: 네 건 모두 새 테스트가 `1bd9cd6f`의 소스에서 실패하고 수정 후 통과한다.
  검증자가 소스만 기준으로 되돌린 임시 워크트리에서 다시 확인했다. G3은 운영 코드
  수정 네 곳을 하나씩 빼면 각각 정확히 테스트 하나가 실패한다.

  그 뒤 G1·G3은 테스트 정리(서비스 연결이 테스트마다 유지되게, 모듈 상태 정리를
  afterEach로)만 한 라운드를 더 거쳐 다시 승인됐다.
- 통합 검토: 네 수정을 합친 브랜치를 수정 간 상호작용, 사용자 동작, 릴리스·문서
