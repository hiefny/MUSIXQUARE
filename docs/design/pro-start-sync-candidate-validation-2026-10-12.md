## 1. 확정한 시계 경로

### C2 — 정밀 보정 결과를 단일 갱신 샘플이 덮어씀

`src/pro-room/network-bridge.ts:820`은 30초 갱신 때 최소 RTT를 Infinity로
초기화하고 핑 하나를 보낸다. `:778`의 샘플 채택은 갱신 직후 첫 응답을 받아들이며,
READY 정밀 보정 시각(`:797`)은 그대로 둔다. `:882`의 5초 신선도는 이제 다른
샘플로 바뀐 오프셋에도 적용된다.

`src/pro-room/playback-controller.ts:694`, `:1017`, `:1251`, `:1308`은 미디어
준비 이후 COMMIT을 처리할 때 현재 오프셋을 읽는다. 따라서 다중 기기 코호트에서
다른 참가자의 READY 등을 기다리는 동안 갱신이 끼면 다음 순서가 가능하다.

| 단계 | 통제한 조건과 실제 결과 |
| --- | --- |
| 정밀 보정 | RTT 20ms, 실제 시계 차이 0ms, 채택 오프셋 0ms |
| 30초 갱신 | 상행 10ms / 하행 190ms, RTT 200ms |
| 갱신 채택 | 오프셋 −90ms, READY 신선도는 계속 유효 |
| COMMIT | 정상 대기 700ms가 원본 파일·YouTube 컨트롤러에서 모두 790ms로 전달 |
| 대조군 | 동일 RTT 200ms라도 상행·하행 각각 100ms이면 오프셋 0ms |

이는 **90ms 늦은 예약**의 재현이다. 음향 장치까지 연결한 실측은 아니다.
READY API는 시험 경계에서 waiting 응답으로 대체했다. 단일 기기가 곧바로
서버 COMMIT을 받는 방보다 다른 참가자를 기다리는 실제 다중 기기 상황을 표현한다.

같은 revision의 정상 heartbeat는 `playback-controller.ts:1911–1918`에서
취소된 재생 복구만 확인하고, 취소 표시가 없으면 `:2006–2008`에서 끝난다.
일반방 파일 보정은 `network.hostConn`이 필요한데 PRO는 이를 null로 둔다.
따라서 나중에 좋은 시계 샘플이 와도 이미 잘못 예약된 건강한 재생을 자동으로
다시 맞춘다는 보장은 없다. 다음 전환·수동 보정·복구 등으로 달라질 수 있으므로
"반드시 곡 끝까지 지속"이라고 하지는 않는다.

30초 갱신 본체의 blame은 `d4b208cc4`(2026-07-20 KST)로 이어진다. 이것만으로
모든 관련 상호작용이 그날부터 동일했다고 단정하지는 않는다. 최근 길이 저장 기능이
새로 만든 경로는 아니다.

### C10(a) — 첫 시계 보정 전 라이브 COMMIT의 전달 시간 누락

새 소켓은 `network-bridge.ts:476`에서 미보정 상태로 시작한다. `serverNowForFrame`
(`playback-controller.ts:694`)의 fallback은 서버 프레임 timestamp에 **수신 이후**
경과만 더한다. 서버에서 브라우저까지 이동한 시간은 포함하지 않는다.

원본 `joinProRoom` → 세션 컨트롤러 → 실제 브리지 → WebSocket message → 재생
컨트롤러 경로로 확인했다. API와 미디어 준비·출력 경계만 시험 대역을 사용했다.

- 서버 프레임 시각 10000ms, 실행 시각 10700ms.
- 실제 수신 시각 10180ms, 첫 유효 시계 응답은 아직 없음.
- 올바른 남은 대기는 520ms. 실제 미디어 commit hook에는 700ms가 전달됨.
- 따라서 **180ms 늦은 예약**. 먼저 보정된 대조군은 520ms로 정상.

기존 PREPARE가 없는 초기 입장에서도 재현돼, 재접속의 PREPARE 취소 장치만으로
반박되지 않는다. runtime의 라이브 COMMIT 수신(`runtime.ts:3881–3908`)에는
스냅샷 복원(`playback-controller.ts:1923`)과 같은 보정 대기 장벽이 없다.

단, **미디어 준비가 첫 유효 시계 응답보다 먼저 끝나야 한다.** 즉시 준비되는
미디어 대역을 쓴 시험이 보통 YouTube 워밍보다 핑이 느리다고 증명하지는 않는다.
이미 같은 소켓에서 일반 시계 샘플 하나라도 받은 정상 연결에는 이 fallback을
적용하면 안 된다. READY용 정밀 보정 실패와 완전 미보정도 서로 다른 상태다.

### C4 — 짧은 샘플 선택 창의 정밀도 절충

0/80/180ms 핑, 2응답 또는 220ms 결정 창은 실제 정책이다. 통제 시험에서는
첫 RTT 160ms / offset −60ms가 220ms에 확정되고, 230ms에 도착한 더 좋은
RTT 150ms / offset 0ms 응답은 닫힌 라운드 때문에 버려졌다.

그러나 RTT 334ms 대칭 경로는 샘플 하나여도 offset 0ms였다. 보고서의
"140ms 이상이면"은 비슷한 RTT와 제시간 타이머를 가정한 근사치다. 지연 자체와
지연의 비대칭을 구분해야 한다. 관측된 기존 `RTT 334ms / offset +817ms` 역시
두 시계의 관측 차이이며 **817ms의 동기화 오차가 관측됐다는 뜻이 아니다.**

최근 #295는 응답이 220ms 뒤에 오면 계속 실패하던 문제를 고친 것이다. 이를 다시
짧은 고정 실패로 되돌리면 느린 경로에서 Sync 버튼이 막히던 문제가 재발한다.
샘플 수·품질·시간 예산을 함께 다루는 개선이 필요하다.

## 3. YouTube 상세 반박과 재현

### 추가 관찰에 따른 C1 판단 보완

오너는 Android YouTube에서 화면보다 소리가 항상 약 250ms 늦으며 모든 경로에
보정해야 한다고 이해했다고 설명했다. `pro-lead-learner.ts:43`, `:73`, `:141–142`도
250ms를 고정 출력 보정으로 정의하고, 의도적으로 앞선 미디어 시계를 학습기가
되돌리지 않도록 한다. `authority-arm.ts:393–400`은 scheduled-control에서 이
고정값과 학습값을 모두 0으로 만든다. `local-offset.ts:174–204` 및
`player.ts:997–1039`의 변환은 수동 오프셋 등을 처리하며 대체 250ms base는 없다.

따라서 C1을 단순히 "의도된 정책"으로 분류하는 것은 불충분하다. 지속 출력 지연이
해당 전환에서도 유지된다는 전제에서는 적용 범위가 고정 출력 모델과 일치하지 않는다.
각 실제 전환·기기에서의 수치는 아직 측정하지 않았고, 모든 Android의 보장된
상수라는 뜻도 아니다. 고정 출력 보정과 시작 지연 학습의 적용 범위를 분리해
검토해야 한다. 즉시 따라잡기에는 미래 예약 여유가 없을 수 있어 gate 변경만으로
끝나지 않으며, 위치 보정과 조기 호출을 중복 적용하면 안 된다.

룸의 소리를 맞추기 위해 iframe을 먼저 진행시켜도 그 기기 자체의 화면과 소리
사이 간격은 남을 수 있다. 이는 보정이 실패했다는 뜻이 아니다. 평가 기준은 다른
참가자와 실제로 들리는 내용이 일치하는지다.

원본 controller → hooks → iframe arm → player의 통제 추적:

- 복원: 340ms에 23초로 준비 seek, 621ms에 33.620초로 seek하고 같은 tick에 play.
- 수동 Sync: 1340ms에 34초로 준비 seek, 2320ms에 35.320초로 seek하고 같은 tick에 play.
- 수동 Sync의 준비·확정 위치 차이 1.320초. 즉시 응답 iframe에서는 미디어 시계 오차 0ms.
- 같은 revision 복원 후 60초를 흘려도 추가 seek는 없었다.
- arm에 별도로 120ms seek 후 시작 지연을 주입하면 그 모델에서는 120ms 늦어진다.
  이 지연을 실제 기기에 존재한다고 가정해 결론을 만들지는 않는다.

근거: `playback-controller.ts:714`, `:1883`, `:2133`, `:2154–2173`와
`youtube/authority-arm.ts:410–412`, `:693–705`.

C8에서 잘못 묶은 출력 재합류는 `player/local-output-rejoin.ts:175` →
`playback-controller.ts:2409–2421`의 랑데부 경로다. 직접 경로는 unchanged Play
(`:1673–1683`)와 foreground 복구(`runtime.ts:3359–3363`)에 남아 있다.

`authority-arm.ts:689–691`의 40ms release 지터 허용, `:600–617`의 120ms
착지 허용, 이후 학습 결합은 확인했다. 이것을 없애려고 모든 release에 seek를
추가하면 오히려 추가 버퍼링이 생길 수 있다. 2026-09-19 수정은 학습 관측 간격이
한순간에 접히는 문제였고, 모든 지연 학습을 금지한 결정은 아니었다.

## 4. 파일·플랫폼 주장 정정

파일 메모리 추정은 `duration × max(48000, context.sampleRate) × channels × 4 × 1.25`다.
44.1k와 48k 컨텍스트는 동일 기준이고, 48k보다 클 때만 달라진다. 일반 Android/Mobile
UA는 reported RAM과 무관하게 constrained 티어다.

스테레오 PCM 기준 엔진 전환 경계는 iOS 약 6.99분, constrained 9.32분,
standard 13.98분, high-memory 18.64분이다. 인코딩 파일 크기의 두 배를 포함하는
별도 작업 메모리 조건으로 더 일찍 전환할 수도 있다. 이는 디코딩 시간이 몇 초
걸리는지 측정한 결과가 아니다.

`transport-large-file.test.ts:1036–1051`은 실행 여유 200ms에 준비가 650ms 걸렸을
때 위치 40초 대신 40.45초에서 시작하는 보상을 확인한다. 이번에도 통과했다.
bounded `createPlayback`은 준비 위치에서 최대 1초 앞선 위치를 재사용하는 추가
경로도 있다(`bounded-track.ts:207–219`). 원 보고서는 이 경로를 빠뜨렸다.

원 보고서의 "파일에는 플랫폼 선행이 전혀 없다"는 문장은 틀렸다.
`transport.ts:67`, `:464–469`에 Windows +20ms 선행이 있다. 또한 프리로드와 본
재생이 같은 엔진 선택 함수를 쓴다는 사실이 항상 동일한 결과를 보장하지는 않는다.
메타데이터 측정 실패는 재시도할 수 있어, 이후 확보한 길이가 선택을 바꿀 수 있다.

실제 Windows Chromium PCM 비교에서는 native와 bounded의 길이 차이·샘플 지연이
검사 허용치(출력 샘플 1개 이내)를 만족했다. raw ADTS AAC LC/HE/HEv2도 포함하고,
별도 MP3 도전 시험은 실제 208바이트 Xing 메타데이터 프레임을 제거했다. Safari의
CoreAudio, 임의의 모든 MP3/AAC, 실제 스피커 출력에 대한 보장은 아니다.

[Web Audio 명세](https://www.w3.org/TR/webaudio-1.1/#dom-audiocontext-getoutputtimestamp)는
렌더 시계와 출력 장치 시계를 구분한다. `currentTime`을 하드웨어 콜백 주기와 그대로
동일시해 독립적인 균등분포 오차나 최대 20ms를 도출할 수 없다. 내장 스피커에도
출력 경로 지연은 있다. recorder의 timestamp pair와 outputLatency 등을 함께
측정해야 한다.

Android 데스크톱 모드의 Linux UA와 client hint 변경은
[Chrome 공식 문서](https://developer.chrome.com/blog/desktop-mode)에 명시돼 있다.
[Samsung 공식 문서](https://developer.samsung.com/browser/user-agent-string-format.html)는
24.0 이후 데스크톱 UA를 Linux로 설명한다. 현재 분류 누락은 재현했지만, 터치 가능한
모든 Linux/Windows 기기를 Android로 바꾸는 수정은 정당화되지 않는다.

## 5. 전달 공백과 복구

`cloudflare/signaling-worker.ts:6127–6159`는 현재 맞는 incarnation의 소켓만
eligible로 센다. 원본 signaling DO로 다음을 확인했다.

- 대상 중 1명만 현재 소켓이 있으면 응답은 eligible=1, sent=1.
- 대상이 새 incarnation이고 소켓은 아직 이전 incarnation이면 eligible=0, sent=0.
- PREPARE/COMMIT의 대상 제외만으로 이전 소켓을 강퇴하지는 않는다. 권위 있는
  presence snapshot에서는 제외된 소켓을 끊는 별도 정책이 있다.

원본 `pro-room-worker.ts:11789–11797`의 outbox 수신 판정은 두 응답 모두 성공,
eligible=2/sent=1은 실패였다. 이것은 기기별 application ACK가 아니다.

다만 `runtime.ts:3068–3078`은 소켓 복구 뒤 새 ticket의 pending PREPARE도 소비한다.
스냅샷과 COMMIT 사이의 경합은 남지만 "재접속이면 항상 PREPARE를 놓친다" 또는
"무조건 최대 15초"는 부정확하다. C14 자체는 늦은 합류 설명이고, 지속 오차를
설명하려면 C10(a)·C3 같은 적용 경로와 결합한 증거가 필요하다.

## 6. 수정 우선순위 제안 — 미구현

1. **C2:** 보정 값과 품질·획득 시각을 일관된 하나의 상태로 관리한다. 단일 저품질
   갱신이 검증된 READY 값을 덮고 그 신선도를 물려받지 않게 한다. 오래된 값의
   영구 고정도 피해야 한다. 전환 중의 기준 변경을 제어하고 진단에 남긴다.
2. **C10(a):** 라이브 COMMIT도 유효한 서버 시계 확보 후 최신 revision에 맞춰
   적용한다. 기다리는 중 곡 변경·취소·퇴장이 생겼는지 다시 확인하고, 마감이
   지났으면 올바른 현재 위치로 따라잡는다. 수신 시간을 서버 송신 시간처럼 쓰지 않는다.
3. **C4:** 기존 호출자의 예산 안에서 이미 보낸 응답을 더 잘 활용하는 방향을 검토한다.
   고 RTT를 무조건 거절하거나 모든 사용자를 오래 기다리게 하는 변경은 피한다.
4. **C1/C3/C7/C11:** 고정 출력 base를 zero-start에만 적용하는 불일치를 우선
   검토하고 실제 YouTube에서 미디어 시계와 음향 시작을 분리 측정한다.
   미래의 고정된 합류 위치를 미리 준비하는 설계, 요청 선행과 실제 확보 선행의
   진단, 학습에서 예외적인 callback 지터를 취급하는 기준을 검토한다. 모든 경로에
   호출·위치 양쪽에 250ms를 일괄 중복 추가할 근거는 없다. 오너의 지속 출력 지연
   관찰을 전제로, Android가 실제 재생을 시작·재정렬하는 각 경로에 base 보정이
   한 번씩 유지되는지 검증해야 한다.
5. **C6/C9:** 같은 불변 파일의 재디코딩 회피와 실제 목표 위치의 사전 준비는 후순위
   성능 개선 후보다. 취소·권한·리소스 수명 검증을 보존해야 한다.

오너가 본 두 사건에는 C2가 가장 잘 맞는 공통 후보이며, 입장 직후라면 C10(a)도
유력하다. 하지만 실제 당시의 보정·예약·출력 기록 없이 사건 원인을 확정하지 않는다.
보고서의 발생률 5–12%, 항상 한 기기만, 4–8곡 수렴은 실측 근거가 없다.

## 8. 재토론 검토 — 2026-10-12

검토 SHA와 환경은 동일하다. C2/C10(a)의 앞선 재현은 재실행하지 않고 코드와

### C1/C5: 과거 범위 제한의 근거와 두 종류의 지연

`3454421b`에는 한 줄 commit message 외에 실측을 설명하는 본문이 없다.
당시 runtime 주석은 이미 현재 위치를 따라잡은 기기에 일회성 lead를 적용하면
앞서게 된다는 논리이며, 실제 Android 출력 측정 결과는 아니다. 최초
scheduled-control 테스트는 iOS만 다뤘고 `399ee30d`에서 Android로 확대됐다.
현재 `authority-arm.test.ts:521`은 `c3eae88c`의 음수 수동 오프셋 검사에서 생겼다.
두 테스트 모두 호출 시각·인자를 검증하며 스피커 지연을 모델링하지 않는다.
GitHub의 해당 커밋 연결 PR 조회에서도 추가 토론 기록을 얻지 못했다.

인접 변경에서 확인된 "선행 때문에 빨라짐" 근거는 iOS zero-start의 과거 270ms
seed다. 이를 Android 재개에도 적용할 수 없다. 반대로
`docs/system-sync-compensation.md:74`에는 2026-06-03부터 Android YouTube의
출력이 desktop/iOS보다 늦다는 관찰과 250ms 조기 호출을 유지하고 있다.

재워밍 뒤 **명령→미디어 진행 시작** 지연이 줄어드는지와, 진행 중
**미디어 위치→실제 소리** 간격이 유지되는지는 별개다. 전자의 측정 없이
zero-start의 학습값을 모두 재사용해서는 안 되지만, 전자가 작아졌다고 후자의
고정 보정까지 0이 된다는 결론도 성립하지 않는다. 재개별 별도 학습 lead가
반드시 유일한 수정안이라는 근거는 없으며, 고정 출력 base와 가변 시작 보정을
분리해 실제 경로별로 검증해야 한다.

### C2/C4: 늦은 pending을 보존하는 것만으로는 해결되지 않음

C2는 확정값·품질·신선도의 일관성 문제이고, C4는 유한한 샘플 선택 예산의 문제다.
같은 시계 추정기를 쓰지만 원인이 동일하지 않다. 앞선 C2 재현에서는 READY 응답이
20/100ms에 끝나 아직 보내지 않은 180ms 요청이 취소되므로 살릴 늦은 응답도 없다.

`network-bridge.ts:814`의 삭제만 없애면 다음 위험이 남거나 늘어난다.

- 수신부 `:660`은 활성 라운드 검사보다 먼저 일반 시계에 샘플을 적용한다.
  READY 뒤에 늦은 응답이 COMMIT에 쓰일 시계를 다시 바꿀 수 있다.
- `:941`의 타임아웃·취소도 같은 close 함수를 쓴다. 성공한 라운드만 보존하는
  조건 없이 바꾸면 취소된 응답도 일반 시계 후보가 된다.
- pending 16개 제한은 시간 제한이 아니다. 같은 소켓의 오래된 응답이 이후
  RTT 초기화 뒤 채택될 수 있다. 소켓 generation 검사는 여전히 유효하다.
- 낮은 RTT가 더 정확하다는 보장은 없다. 80/80ms 경로는 RTT 160ms·오차 0,
  10/140ms 경로는 RTT 150ms·오차 −65ms다. 이 수치는 산술 반례이며 실측이 아니다.

현재 전환의 확정 보정과 계속 수집하는 후보를 분리하는 방향이 우선이다.
늦은 샘플을 보존한다면 성공한 라운드·같은 소켓 generation·명시적 유효시간을
검사하고 다음 선택의 후보로 사용한다. 현재 전환에서 두 번째 응답까지 쓰려면
READY 반환 전에 남은 예산 안에서 기다려야 한다. 기존 느린 경로를 다시 무조건
실패시키는 변경은 피한다.

### C3: Sync 반복은 원인을 단독 확정하거나 배제하지 못함

`playback-controller.ts:2133–2173`의 Sync는 이전의 실제 음향 오차를 측정해
반복해서 줄이는 제어기가 아니다. 매번 서버 타임라인으로 재합류한다.

- 매번 실패해도 C1 출력 보정 누락이나 시계 오차만으로 설명될 수 있다.
- 반복 후 성공해도 C3의 seek→play 경로가 사라졌다는 뜻은 아니다. 캐시·버퍼링·
  callback 조건이 달라질 수 있다. 앞선 즉시 응답 iframe 대조군에서도 C3 경로의
  시간 오차는 0이었다.

같은 기기·영상·수동값에서 zero-start/재개/seek/Sync를 비교하면서 서버 기준
미디어 시계 차이와 실제 소리 차이를 각각 기록해야 한다. 미디어는 서버와 같고
소리만 250ms 늦으면 C1으로 설명 가능하다. 미디어 자체가 추가로 늦으면 C3·시계
등을 더 구분해야 한다. 미디어가 250ms 앞서고 소리가 맞으면 고정 출력 보정이
작동하는 것이다. 귀로 듣는 Sync 반복은 증상 확인에는 유용하지만 원인 판별의
필요충분조건이 아니다.

### C10(a)/C14 및 최종 후보 목록

C2와 C10(a)는 앞선 설명의 첫 두 항목이며 생략된 후보가 아니다. 마지막 후보
목록에서도 C10(a)를 유지해야 한다. 첫 시계 응답 전에 live COMMIT을 처리하는
조건은 파일·YouTube 공통이며, 이후 재정렬까지 오차가 남을 수 있다. 빈도나
무조건 곡 끝까지 지속한다는 주장은 검증하지 않았다.

C14는 미디어와 무관한 전달·복구 경로다. YouTube에서 C3로 이어질 수 있지만,
새 소켓에서 첫 시계 보정 전 COMMIT이 도착하는 C10(a)와도 결합할 수 있다.
그러므로 C14의 지속 오차가 오직 C3를 통해서만 발생한다는 결론은 부정확하다.
C6/C9는 지속 싱크 오차와 구분한 준비 성능 항목으로 유지한다.

### C11: 작은 타이머 지연과 학습을 구분할 근거

`c242bfd1`에서 추가된 `pro-manual-zero-start.test.ts:484–516`은 1.5초 타이머
backlog를 따라잡은 뒤 다음 정상 전환의 선행값이 바뀌지 않아야 한다고 검사한다.
`:504–505`는 "Timer backlog is not a device-start latency observation"이라고
의도를 명시한다. 반면 `authority-arm.test.ts:712–729`는 25ms 지터를 seek로
보정하지 않고 `releaseLatenessMs:0`으로 반환하는 정책을 고정한다.

작은 지연이 사라진 뒤에도 해당 곡의 타임라인은 그만큼 뒤에 남으므로 0.8초·2초
관측은 서로 안정적일 수 있다. `player.ts:874–917`과 `pro-lead-learner.ts:173–200`
에는 이 두 값을 실제 출력 지연과 구분할 원래 callback 지연 정보가 없다. 앞선
원본 player 통합 재현의 일회성 35ms→다음 lead 8.75ms는 이 경로를 확인한다.

따라서 C11 전체를 "의도된 학습"으로 처리하는 것도 부정확하다. **40ms 이하에서
추가 seek를 피하는 정책**과 **그 일회성 지연을 다음 곡의 기기 보정으로 전파하는
문제**를 분리해야 한다. 보정에 사용한 callback 지연과 관측한 원래 지연을 별도로
전달해 학습 자격을 판단하는 방향을 검토할 수 있다. 단, 매번 동일하게 발생하는
지연은 실제 보정 가능한 잔차이므로 모든 작은 지터를 무조건 제외하는 규칙도
최종 정답으로 확정하지 않는다. 수치의 실제 청감 영향은 이번 시험 범위 밖이다.

## 9. 수정 구조 제안 재검토 — 2026-10-12

HEAD `eb51ed73ab9561a4b30583127213471ba82bd88f`를 대상으로 세 영역을 병렬
코드 리뷰했다. 이번 절에서는 새 unit/E2E를 실행하지 않았다. 아래 수치 반례는
명시한 단순 모델의 계산이며 실기 재현 결과가 아니다. 제품·테스트 코드는
수정하지 않았고, 커밋·푸시·배포도 하지 않았다. 앞선 검사 결과와 구분한다.

### 확정 시계·후보 풀과 유효기간

후보와 확정값 분리는 C2의 직접 원인을 막고 C4의 늦은 응답을 다음 선택에
보존할 수 있는 공통 구조다. 다만 이미 종료한 선택 창에 늦은 응답을 넣을 수는
없으므로, 현재 시작의 C4 오차까지 사라진다고 보장하지 않는다.

5초는 새 작업에서 확정값을 재사용할 수 있는 기준으로 다룬다. 예를 들어
나이 4.9초인 값을 READY에서 확보하고 0.3초 뒤 COMMIT을 계산할 때 만료를
이유로 후보값으로 교체하면 다시 서로 다른 시계가 사용된다. 전환 밖 fallback을
제안한 취지는 맞지만, 수동 Sync·복원·직접 COMMIT도 자기 작업에서 쓸 시계
추정값과 generation을 확보해야 한다. `activeTransition` 유무만으로 구분하면
이 작업들을 놓친다. 취소·재접속·시계 불연속은 별도로 무효화해야 한다.

minRTT 후보에는 수신 시각·generation·유효기간·출처가 필요하다. 후보 사용을
READY 정밀 보정 완료로 표시하거나 확정 시각을 갱신해서는 안 된다. 낮은 RTT가
항상 정확한 offset이라는 보장은 §8의 비대칭 경로 반례처럼 성립하지 않는다.
현재 근거는 `network-bridge.ts:279,660,785,823,882` 및 준비를 기다린 뒤 시계를
읽는 `playback-controller.ts:1308`이다.

### C10(a)의 대기와 따라잡기

live COMMIT도 첫 시계 확보를 기다리는 방향에 동의한다. 연결 burst는 이미
`network-bridge.ts:706`에 있고 별도 관찰 대기를 만들면 요청 중복을 줄일 수
있다. 그러나 미보정 상태에서 정확한 "남은 700ms"는 알 수 없다. 발행 당시
여유에서 알 수 없는 전송 시간이 이미 소비됐으며 재전송은 마감을 지났을 수도
있다. wire zero-start 표지는 699ms다.

시계가 확보되면 그때 예약 지연·따라잡을 위치를 다시 계산한다. 시계 없이
대기만 만료된 경우 정확한 따라잡기는 여전히 불가능하므로, 예전 fallback을
그대로 호출해서는 C10(a)가 닫히지 않는다. 최신 checkpoint의 보류·재시도 및
bounded UI 처리가 별도로 필요하다.

기존 `waitForFreshClockCalibration()`은 그대로 재사용할 수 있는 "첫 응답
관찰기"가 아니다. `:289,305`에서 READY burst를 시작하고 첫 응답만으로 항상
반환하지 않으며, `executeAtMs`를 deadline으로 주면 따라잡기에 쓸 수 있는
늦은 시계 응답도 실패로 판정한다. 시계 확보와 제시간 시작 가능 여부를 분리한다.
새 pause/stop·revision, 소켓 교체·퇴장은 대기를 즉시 취소해야 한다. 완료 뒤
검사만 하면 `playback-controller.ts:1466`의 직렬 COMMIT 큐를 불필요하게 막는다.

### C1/C7과 `callToPlayingMs`

고정 출력 지연이 검증된다면 미래에 예약하는 제어에서는 조기 호출, 이미
늦은 합류에서는 목표 위치 선행으로 보정한다는 방향은 타당하다. C7에서는
시간으로 이미 확보한 선행을 제외한 부족분만 위치로 보정해야 한다. 항상 전체
250ms를 추가하면 중복 보정한다. 새 seek 때문에 생기는 시작 지연, 수동값과
곡 끝 경계는 이 고정 출력 보정과 별도로 검증해야 한다.

`callToPlayingMs`는 유용한 관측값이지만 순수한 미디어 시작 지연은 아니다.
`authority-arm.ts:703`은 seek 명령 뒤 시각을 기록하고 `:707–711`은 이미
PLAYING으로 관측되면 즉시 성공한다. 그 외에는 `:448–453`의 PLAYING 이벤트
관측 시각을 `:736`에서 뺀다. 이는 명령→관측된 상태 응답이며 iframe/메인
스레드 이벤트 전달 지연을 포함할 수 있다. 0이라고 실제 seek 완료나 미디어
진행 지연이 0이라는 뜻도 아니다. 기존 identity 보호가 없어졌다는 주장이나
별도 실기 레이스의 확정으로 확대하지 않는다.

또한 `player.ts:1043–1048`의 해당 로그는 zero-start에만 남는다. 결과 필드가
매 실행에 있다는 것과 재개별 비교 데이터가 이미 쌓여 있다는 것은 다르다.
경로·실제 예약 여유·raw callback 지연·보정량·미디어 진행 표본을 같은 작업
식별자로 기록하는 계측은 유용하지만, 이 값만으로 고정 출력 base를 분해하거나
250에서 기계적으로 빼서는 안 된다. YouTube 공식 API는 PLAYING 상태와 영상
경과 시간을 제공하며 스피커 출력 시각을 제공하지 않는다.

### C11의 부호·잔여 지연·감쇠

raw callback lateness와 실제 적용한 catch-up을 따로 전달하는 것은 타당하다.
관측 drift의 정의는 `player.ts:889`의 로컬 canonical − 예상 canonical이다.
정상 진행·충분한 예약 여유·경계값 문제가 없는 단순 모델에서 다음과 같다.

`D − B = L − S − J + C`

`D`는 관측 drift, `B`는 고정 base, `L`은 기존 학습 lead, `S`는 실제 시작
지연, `J`는 callback 지연, `C`는 이미 적용한 callback catch-up이다. 따라서
callback 영향을 제거한 관측은 `D + (J − C)`다. "지연의 기여를 뺀다"는 취지는
맞지만 양수 raw 지연을 drift에서 그대로 빼면 부호가 반대다.

- 일회성 30ms 지연은 drift에 −30ms로 나타난다. 다시 30을 빼면 −60ms가
  되어 잘못된 학습이 두 배가 된다.
- 60ms 지연은 기존 코드가 위치를 따라잡으므로 raw 60을 다시 더하면 이미
  보정한 값을 중복 계산한다. 필요한 값은 미보정 잔여분이다.
- 별도 timer EMA도 한 번의 30ms를 gain 0.25로 받아들이면 다음 정상 시작을
  7.5ms 앞당긴다. 반복성·이상치 처리가 없으면 문제를 다른 상태값으로 옮긴다.
  기존 큰 지연 catch-up과 timer 선행을 함께 쓰는 경우의 중복도 검증해야 한다.
- 학습 lead를 무조건 0으로 감쇠하면 실제 지속 지연의 정상 보정도 지워진다.
  실제 시작 지연 100ms, gain 0.25, 매 갱신 후 5% 감쇠를 가정하면
  `L_next = 0.95 × (L − 0.25 × (L − 100))`의 평형은 약 82.61ms다.
  모델에서는 약 17.39ms 지연이 남는다. Android deadband 안에서만 감쇠해도
  정상 보정을 지우다 다시 배우는 반복이 생길 수 있다.

그러므로 C11의 우선 범위는 지연 출처·적용량 전달과 학습 자격/입력의 수정이다.
timer EMA와 무조건적인 0 감쇠는 별도 검증 없이 묶지 않는다. 타이머 영향을
제외해도 미디어 drift 관측이 스피커 출력 지연의 직접 측정으로 바뀌지는 않는다.

### 세 원인의 관측은 배타적인 판정표가 아님

명령/상태 응답, 공통 기준 대비 미디어 진행, 실제 소리의 세 관측을 나누는 것은
좋다. 그러나 현재 로컬 canonical deadline은 예약에 사용한 추정 시계에서
나온다(`player.ts:1012,877`). 계산 예로 시계 오차가 −90ms여서 90ms 늦게
시작하고 그 늦은 로컬 deadline과 비교하면, 실제 미디어는 90ms 늦어도 로그
drift는 0일 수 있다. 시계 표본의 RTT·offset·나이·선택 출처와 독립 기준을
확인하지 않은 로컬 로그만으로 C2/C10을 배제할 수 없다.

C3와 관련된 release 시점 seek는 target 증가나 callback 지연에 따라 발생한다
(`authority-arm.ts:410,689–705`). 곡 위치가 0인지 아닌지나 버튼 이름만으로
분리할 수 없다. 올바르게 보정된 Android라면 미디어 자체가 base만큼 앞서는
것이 기대 상태일 수 있으며 C1/C3/C7/시계 오차가 함께 존재할 수도 있다.

C13은 C1 작업과 함께 살필 수 있지만 Linux UA와 터치만으로 Android를 확정하면
실제 터치 Linux 데스크톱에 잘못된 250ms를 적용할 위험이 있다. 현재 판별은
`src/core/platform.ts:26`이며, 모호한 기기를 확정하는 광범위한 휴리스틱은 피한다.

검토 우선순위는 C2/C10(a)의 시계 일관성과 안전한 대기, 전 경로 계측, 실측에
근거한 C1 보정, 출처를 구분하는 C11 순으로 유지한다. 이는 수정안 검토 결과이며
사용자 관측의 단일 원인이 확정됐거나 제품 수정이 완료됐다는 뜻은 아니다.
