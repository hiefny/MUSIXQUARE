- **2026-11-14, 아이폰의 디자인 시스템:** 같은 때 오너가 아이폰에서 디자인 시스템의 컴포넌트가 영원히 나타나지 않고, 윈도우와 아이패드에서는

  게이트가 아니다.

만든 쪽이 정한 것(오너 결정 아님): 앱 문서의 목록(위). 공개 페이지는 시간 한도 없이 끝까지 기다리고, 연결이 실패할 때만 그 페이지 자신의 저장된

오프라인 응답). 검토가 찾은 둘(§3.2)을 같은 열차에 넣은 것. 디자인 시스템 쪽은 '구역의 어느 부분이든 화면 아래 80px 선을 넘으면 나타남'으로

## 3. 공개 페이지가 앱 첫 화면으로 바뀌지 않게 ([화면 바뀜], 늦거나 끊긴 연결에서만)

### 3.1 사용자에게 바뀌는 것

- 전: 공개 페이지를 열 때 서비스 워커가 3초 안에 페이지 전체를 받지 못하면, 그 주소에서 앱 첫 화면(루트와 같은 화면)이 대신 떴다. 그 페이지의
  저장된 사본이 있으면 사본이 떴지만, 업데이트마다 저장된 사본이 지워지고 블로그처럼 서버가 저장을 막은 페이지는 사본이 없었다.
- 뒤: 공개 페이지는 서비스 워커가 없는 페이지처럼 연결이 끝날 때까지 기다린다. 연결이 실패할 때만 그 페이지 자신의 저장된 사본을 보여 주고, 사본도
  없으면 오프라인 응답으로 끝난다. 앱 화면으로 바꿔 끼우는 일은 없다. 그 페이지가 쓰는 CSS와 JS도, 업데이트 직후처럼 캐시에 없을 때는 끝까지
  기다려 받는다(전에는 5초에 끊겨 503이 될 수 있었다).
- 그대로: 앱 문서는 전처럼 3초 한도 뒤 설치된 앱 화면을 연다. 캐시에 있는 안정 경로 자산은 전처럼 바로 쓰고 뒤에서 5초 한도 안에 새로 확인한다.
  빠른 연결에서는 어느 페이지도 달라지지 않는다.

### 3.2 바뀐 코드

`browser/service-worker.ts` 하나.

- `isInstalledShellNavigation`: 앱 문서인지 가린다. `/`와 `/index.html`, 로그인 완료 경로, 여섯 자리 방 주소(`isRoomNavigation`), 그리고
  `/<코드>/`(App Worker의 `localizedStaticRoute`와 같은 꼴, 소문자로 비교)에서 코드가 설치 목록의 매니페스트 언어(`APP_LANGUAGE_ENTRY_CODES`,
  `APP_SHELL`의 `./manifests/<코드>.webmanifest`에서 뽑음, 앱 언어 42개)인 것.
- `respondWithPublicDocument`: 공개 페이지의 길. 연결을 시간 한도 없이 그대로 쓰고 머리가 오면 바로 돌려준다. 실패하면 같은 주소의 사본(활성
  세대의 runtime 캐시, 민감한 질의는 제외)이나 오프라인 503을 돌려준다. 사본으로 답할 때는 앱 문서와 같은 대체 표지(`X-Musixquare-Navigation-Source:
cache-fallback`과 탐색 상태 기록)를 남긴다. 백그라운드 일은 fetch 사건이 도는 동안 등록한다. `canonicalNavigationShell`에서 번역, 사이트맵, 화면
  보호기의 따로 된 분기를 뺐다.
- 검토 반영 1, `readCacheCopyWithin`: 서비스 워커가 캐시에 넣을 자기 사본만 한도 안에서 읽는다(공개 페이지는 `NAVIGATION_NETWORK_TIMEOUT_MS` 3초,
  안정 경로 자산은 `STATIC_REVALIDATION_TIMEOUT_MS` 5초). 한도를 넘으면 그 사본만 취소하고 쓰지 않는다. 페이지는 원래 응답을 한도 없이 받는다. 첫
  고침에서는 캐시 쓰기가 몸통 전체를 기다려, 몸통이 멈추면 fetch 사건이 끝나지 않고 승인된 업데이트의 전환을 붙잡을 수 있었다(이 저장소의 5초
  한도가 막으려던 바로 그 일, `docs/hotfix-procedure.md`).
- 검토 반영 2, 안정 경로 자산: 캐시에 있으면 전처럼 바로 답하고 뒤에서 5초 한도 안에 새로 확인한다. 캐시에 없으면 그것이 페이지 자신의 로드라서
  연결이 머리를 주는 대로 페이지에 넘기고(해시 자산이 캐시에 없을 때와 같음), 캐시 사본만 5초 한도를 지킨다. 전에는 캐시에 없을 때도 5초에 끊고
  옛 세대 사본이나 503을 돌려줘서, 업데이트 직후 느린 연결에서는 공개 페이지가 스타일 없이 뜨거나 구역이 다 숨은 채로 남을 수 있었다. 네트워크는
  이제 활성 캐시 조회가 끝난 뒤(마이크로태스크 하나 뒤) 시작한다.

### 4.1 사용자에게 바뀌는 것

## 12. 하지 않은 것과 확인하지 않은 것

- 실기기(iPhone, iPad, Windows의 실제 느린 연결)에서 보지 않았다. 느린 탐색과 멈춘 몸통은 단위 시험의 가짜 시계와 가짜 fetch로만 만들었다.
- 검토 반영(`5aac95a3`)은 두 번째 독립 검토를 받지 않았다. 검토자가 제안한 그대로이고, 단위 시험과 최종 관문, PR의 자동 코드 리뷰가 본다.
- WebKit에서는 저장소의 WebKit 레인과 서비스 워커 WebKit 레인(앱 문서의 대체를 봄)만 돌았다. 공개 페이지의 느린 탐색은 WebKit에서 따로 돌지 않았다.
- 섞인 버전의 방은 따로 시험하지 않았다(§7).
- 배포 뒤 브라우저 확인은 이 작업 컴퓨터의 헤드리스 Chromium 둘(휴대폰 크기의 나타남, 데스크톱에서 응답을 늦춘 공개 페이지)뿐이다(§11.3). 실기기, WebKit, 실제 느린 연결은 보지 않았다(§9).
- 로컬 결과는 exact-main-SHA 후보를 대신하지 않았다.
